## 本轮发现

### P1-1. dry-run 预检不跳过 flag/flag 值：任何带可选 flag 的命令恒 not_ready + exit 3
- **位置**:cli_top.py:876-885(dry-run 预检循环)
- **发现**:`tbtools tool-run --dry-run --json expr volcano --pval-cutoff 0.01 examples/data/deg.txt /tmp/v.svg` → `status=not_ready / inputs_valid=false / problems=["missing input: --pval-cutoff","missing input: 0.01"]`,**exit 3**。dry-run 预检对 `_skip` 之后的所有 token 做 `os.path.isfile` 检查，不识别 flag 也不跳过 flag 的值——任何带可选参数的命令 dry-run 必然误报。而 60 行后的执行预检 `_precheck_input_flags`(cli_top.py:841)已是 flag-aware(v1.4.87 两轮修正的成果)。**同一文件内两套预检规则再度分裂**——v1.4.81 P1-3(_OUT_EXTS vs _OUT_EXT_PRE)被修后，同类问题在 dry-run vs _precheck_input_flags 之间原样复发。
- **挑战**:dry-run 是 Agent 规划入口(评审 #37 的定位),"带 flag 就报输入缺失"让规划层对所有参数化调用得出 not_ready 结论；exit 3 在 quickstart 语义里是"输入格式错误"，与"文件缺失"混用。v1.4.87 注释里写明"启发式猜 positional 已三度误伤"的教训，恰恰没被应用到 dry-run 侧。
- **建议**:dry-run 的输入检查直接复用 `_precheck_input_flags`(共用 helper 已存在，dry-run 换个调用即可);est 产物预估逻辑不变。加契约测试：带 `--pval-cutoff 0.01` 的 dry-run 必须 ready(在 JAR 就绪环境下)。
- **严重度**:P1

### P1-2. 失败运行返回幻影子产物(artifacts 含从未生成的文件)
- **位置**:cli_top.py:1045-1048(`_art = _afrom(_o) or _abuild(_o)`)+ artifact.py:80(build 对不存在路径返回 size:0/sha:"" 的 Artifact)+ runtime/java.py 末段(失败也写 provenance outputs)
- **发现**:实测两例——①`tool-run --json expr volcano examples/data/deg.txt /tmp/o.svg`(JAR 缺失→ClassNotFound)→ `exit_code:1 + error:TB302`,但 `artifacts:[{path:/tmp/o.svg, size:0, sha256:""}]`;②`tool-run tool tableCollapse ...` 同样。机制：run_java 失败也写 `<out>.tbtools.json`(outputs=[out]);tool-run 读 provenance,`from_provenance` 因产物文件不存在返回 None，落到 `_abuild(_o)` 兜底——build() 不检查文件存在性，直接造出幻影 Artifact。
- **挑战**:Agent 协议里 artifacts 是"这次运行产出了什么"的事实层。失败运行返回非空 artifacts,Agent 会把幻影传给下游步骤(cat 一个 0 字节不存在的文件),或误判"部分成功"。v1.4.81 修的是"产物真实但 artifacts=[]"(漏报),本轮是反方向"产物不存在但 artifacts 非空"(谎报)——漏报修成了谎报。
- **建议**:tool-run 装配 artifacts 时统一过滤 `os.path.isfile(path) and getsize>0`(失败时 provenance 的 outputs 不应直接进 artifacts)；或在 exit_code!=0 时 artifacts 恒空、产物信息挪到 error.expected_outputs。
- **严重度**:P1

### P1-3. 快照保护两个实测盲区:mastrun 型末位输入被剔除 + eggnog 型 hint 指向输入
- **位置**:runtime/java.py `_true_positional_files`/`snapshot_inputs`(保守兜底)+ auto_commands.py `_out_hint`(尾部向前)
- **发现**(单元级实测，不依赖 JAR):
  - **盲区 B(workingDir 模式)**:mastrun `<meme.xml> <seq.fasta> <workingDir>` 无 out 类占位符→hint=None;workingDir 是目录不进 positional 集；末位真 positional = seq.fasta(.fasta 在 _PRODUCT_EXT)→ **被保守兜底当输出槽剔除出快照**。实测 `snapshot_inputs([...motifs.xml, seq.fasta, wd])` 只快照 motifs.xml,**seq.fasta 完全无写穿保护**。mast 同理(motifs.xml 被剔除,.xml 双角色)。v1.4.67 教训注释说".fa/.tsv 双角色误伤"只防了"≥1 不启用"，没防"≥2 时末位是输入"。
  - **盲区 C(flag 值带产物扩展名+输出为目录/前缀)**:eggnog 型 `[in.fa, -o, prefix, --output_dir, outdir]` → _out_hint 尾部向前找"非 flag 且产物后缀"的 token，**跳过 `-o` 但不跳过它的值**,prefix/outdir 无扩展名 → 命中 in.fa(输入!)→ output_hint=输入 → snapshot_inputs 将其显式剔除。实测快照列表为空，**主输入零保护**。
  - 已修好的对照:v1.4.89 的目标场景(flag 交错 `--threads 8 in.fa out.svg`)实测正确；多输出重跑(in.txt outA.svg outB.svg 均存在)实测 outA 被末位兜底+outB 被 hint 双重排除，无回滚。
- **挑战**:输入保护是本项目 P0 级招牌特性("系统性防御引擎写穿")。这两个盲区意味着特定参数形态下保护静默消失——正是"保护在但不在该在的地方"。盲区 C 与 v1.4.89 changelog 宣称的"flag 交错下仍指向真正的产物 token"直接冲突：该宣称只对"flag 值不是文件"成立。
- **建议**:①_保守兜底加白名单反向条件——末位 positional 若是 doc 占位符声明的输入位(如 mastrun 的 seq.fasta 位)不排除；或要求"末位产物扩展名 AND 占位符序号=输出位"双条件。②_out_hint 跳过 flag 值(维护 prev-flag 状态，值 token 不作候选),与 snapshot_inputs 主循环同一套 flag 状态机。③为两盲区各加一条单测(现有测试只覆盖 flag 交错正向场景)。
- **严重度**:P1

### P1-4. tool-submit 无命令存在性校验 + 预检 flag 白名单覆盖窄
- **位置**:cli_top.py:1184-1200
- **发现**:①`tbtools tool-submit seq fetch --inSeq /nonexist2.fa --out /tmp/o2.fa` → **正常返回 job_id/status running(exit 0)**——`fetch` 根本不是 seq 组命令(真名 seqfetch),job 晚期 failed(exit 2)。tool-run 同参数立即报错，tool-submit 照单全收。②预检正则白名单(`--?([i]|in|input|inFile|inFa|inFasta|inGff|inGff3|inTxt|inNwk|inTab|query|subject|pep|cds|genome|reads|read|ref|reference|fasta|fq|fa)`)实测不匹配 `--inSeq`、`--queryFasta`、`--inPaf` 等真实输入 flag——v1.4.89 宣称的"缺失输入直接 TB002/exit 2 拒提交"对这些 flag 不生效。
- **挑战**:tool-submit 是 Agent 长任务入口，"提交即成功"的假信号比同步失败更难处理(job 轮询成本+晚期失败归因)。v1.4.89 修了预检存在性和 ignore_unknown_options,但"命令存在性"这一最基础的校验两条路径仍不对称。
- **建议**:submit 前用 metadata/注册表校验 `<group> <cmd>` 存在(复用 tool-run 的解析层);flag 白名单改从 command_metadata 的 inputs 契约反推(FULL 工具有声明),正则只作无契约工具的兜底。
- **严重度**:P1

### P1-5. 错误归因层三处说谎:exit 5/6 未注册、命令不存在→"文件缺失"、JAR 缺失永不归因
- **位置**:cli_top.py:1071-1075(`_ec_map` 反查)+ errors.py ERROR_CODES(无 exit 5/6 条目)+ classify_error(无 JAR 缺失模式)
- **发现**(全部实测):
  - ①`tool-run --json seq notacmd foo bar` → click 报"not a command"(exit 2)→ JSON 反查 exit 2 → **TB102/TB002_FILE_NOT_FOUND "check the input file path exists"**。命令名错误被报成文件缺失，suggested_action 完全误导。
  - ②venv 安装态 `tool-run expr volcano <真实输入> /tmp/o.svg` → 桥编译失败(JAR 缺失)→ ensure_bridge `sys.exit(6)` → `_ec_map` 无 exit 6 → 默认 **TB101/TB001_INVALID_ARGUMENT "check argument names/values"**。agent-protocol.md §8 明确写着 exit 6 = bridge compile failed，但同一载荷里 exit_code=6 与 error.code=TB101 自相矛盾。exit 5(policy 拒绝)同样未注册。
  - ③本机无 JAR 时：dev 环境(桥已编译)→ ClassNotFoundException → TB302 "engine-level defect; see PITFALL/docs";venv 环境 → TB101。两条路都不说"JAR 未配置",而 `tbtools doctor` 明明能诊断并给出 fetch-jar 路径——**首跑用户/Agent 拿到的是"引擎缺陷"或"参数错误"，永远到不了 doctor**。
- **挑战**:错误契约是 Agent 可编程处理的核心(error-codes.json 的定位)。三类高频首跑失败(命令名打错/没装 JAR/桥编译失败)全部归因错误，retryable/suggested_action 均不可信。这是本轮"失败路径说谎"主题的集中体现。
- **建议**:①命令解析失败单独立码(如 TB401_UNKNOWN_COMMAND,exit 2 但与 TB102 区分)——tool-run 在 cli.main 返回前捕获 click UsageError 文本特征。②ERROR_CODES 补 exit 5/6 条目(TB_POLICY_DENIED/TB_BRIDGE_COMPILE_FAILED)。③run_java/ensure_bridge 入口检测 `not JAR or not isfile(JAR)` → 直接 TB005_DEPENDENCY_MISSING + "run tbtools doctor / tbtools fetch-jar",优于一切晚期归因。
- **严重度**:P1

### P1-6. `tbtools engine list` 死指针×2 + README "tbtools engine <命令>(170 个)"与实际不符
- **位置**:README.md:405 + cli_top.py:1799(list plots 口径注释)

### P1-7. 安装态 meta_guard 假告警:PyPI 产品每次 Agent 调用带"投影过期"警告
- **位置**:meta_guard.py(sources_mtime_fingerprint 用 ROOT 布局)+ 5 处消费端
- **发现**:干净 venv 装 wheel 后，`tbtools version --json`/`tool-describe` 每次 stderr 打 `⚠️ 告警: command_metadata.json 投影过期(源码变更未重跑 gen_metadata --render)`。根因：指纹在**仓库布局**(ROOT/tbtools_cli/*.py + ROOT/bridges/*.java,render 期 mtime)生成，消费时 ROOT=site-packages(bridges 在 sys.prefix/tbtools_cli/bridges 不在扫描集，pip 重设 mtime)——布局+mtime 双重失配，**安装态恒假阳性**(实测 stored f956b748… ≠ now 25a2beb4…)。dev 仓库 HEAD 不告警。
- **挑战**:v1.4.91 的主题之一是 PyPI 发布，而安装态正是这个守卫的目标用户(Agent)唯一会遇到的形态——每个 version/describe/tool-run/search 调用都带一条假警报。警告疲劳比没有警告更糟(真过期时没人信)。这正是"安装态才暴露的问题"。
- **建议**:安装态检测(无 ROOT/bridges 且存在包内 sidecar)→ 跳过守卫或改用"包版本+构建指纹"比对(wheel 构建期把指纹固化，运行时只验 sidecar 与 command_metadata.json 的配对哈希，不碰 mtime)。
- **严重度**:P1

### P1-8. `list rpc --json` 仍静默空(count:0 exit 0)+ list tools 人读 191 vs --json 188
