## 发现一：schema-capable 跨文件权威——GPT 三声称两假一真，残余缺口定 **P1**

GPT 声称：(a) version --json 无 schema_capable 字段；(b) README "64" 与 counts.md 无自动约束；(c) 测试未比较运行时 JSON/counts.md/README 三方。

**独立核实**：

- **(a) 属实** ✅。`cli_top.py` version --json 输出 11 个字段（version/cli_commands/auto_commands/rpc_methods/tools/bridges/pitfall_hints/metadata_commands/execution_verified/conformance_verified），**确无 `schema_capable`**。counts.md 有 `schema_capable: 64`（十三轮 P3-1 已入权威数字），runtime JSON 面缺失 → Agent 消费 `version --json` 拿不到该口径。
- **(b) 不属实** ❌。`tests/test_doc_consistency.py::test_schema_capable_consistent`（F-NEW-7 守卫）实证存在：README `Schema-capable (\d+)` == `command_metadata.json` 有 inputs 契约的命令数。且 `gen_metadata.py --check` 对 counts.md 做**逐字节重生成比对**（含 schema_capable 行），`test_gen_metadata_check_passes` 把 --check 纳入 pytest。README↔metadata、counts.md↔live 两腿均有机器约束。
- **(c) 部分属实** ⚠️。schema_capable 链路为 README↔metadata（测试）+ counts.md↔源（--check 字节比对），**确实没有一个测试把 version --json 纳入 schema_capable 比对**——但根因就是 (a)：JSON 里根本没这个字段。execution_verified 已有三方闭环先例（`test_execution_verified_consistent` 比对 version --json ↔ README；`test_counts_equals_live_census` 比对 counts.md ↔ 运行时 census），schema_capable 只是没跟上同款待遇。

**定级 P1**（非 P0）：数字本身已有两条独立守卫腿，漂移会被 --check 或 test_schema_capable_consistent 拦下；缺的是 Agent 消费面（version --json）的口径完整性与三方同测的对称性，属"闭环形状不完整"而非"无守卫"。

**方案**：
1. version --json 增加 `"schema_capable": sum(1 for s in build_command_specs().values() if s.inputs)`（与 gen_metadata L293 同源）；
2. `test_doc_consistency.py` 增一条：counts.md schema_capable == version --json schema_capable == README `Schema-capable N`，仿 `test_execution_verified_consistent` 三方模式；
3. README_EN 的 `schema-capable` 表述（若有）纳入同一正则扫描。

## 发现二：旧架构退役成果锁定——GPT 夸大为 P0，实际守卫已在，残余缺口定 **P2**

GPT 声称：无测试禁止 cli.py/cli_top.py 新增 CATEGORY_MAP 直读；入口一致性测试只盖静态来源文本，不比对实际注册命令。

**独立核实**：

- **第一声称不属实** ❌。`tests/test_registry_discipline.py::test_no_new_legacy_imports` 以正则扫描 `tbtools_cli/**/*.py + scripts/*.py + tests/*.py`，禁止非白名单文件 `from ... import` ENGINE_REGISTRY / CLI_TOOLS / CATEGORY_MAP；白名单中 cli.py/cli_top.py 已在 Phase 3（2026-09-26）**清零**（注释明载 "grandfather 清单清零"）。实证 grep：cli.py/cli_top.py 当前对 CATEGORY_MAP 零功能引用（仅 cli_top.py:105 一处 docstring 提及）。本轮 29 个守卫测试全绿。
- **第二声称部分属实** ⚠️。`test_entrypoint_consistency.py` 确实只做**正向**（CATEGORY_MAP 键 ⊆ specs、tbplot.sh 命令 ⊆ specs、总量 298±22），不反向比对"specs ↔ 实际 click 注册命令"。但 GPT 漏看了 `test_metadata.py::test_metadata_covers_runtime_commands`：该测试用 CliRunner 实调 `list plots/tools --json` 拿**真实注册命令集**比对 metadata，外加 `test_impl_reflection_matches_registry` 守注册表↔反射命名。实际注册命令的比对**存在**，只是落在 metadata 层而非 entrypoint 测试里。

**真实残余缺口（P2）**：
1. `test_registry_discipline` 是 **import 行正则**，非 AST——`_LG.CATEGORY_MAP.get(...)` / `import tbtools_cli.cli_load as L; L.CATEGORY_MAP` 属性式访问可绕过。当前零违规，属假设性逃逸通道；
2. specs（298）与 click 实际注册命令总数之间无**直接**比对测试（经 metadata 间接闭环）。

**方案**：将 LEGACY_PATTERNS 升级为 AST 检查——ban `ImportFrom(cli_load, names=[CATEGORY_MAP])` + `Attribute(value=Name('cli_load'|'_LG'), attr='CATEGORY_MAP')` 两类节点（白名单不变），~30 行；entrypoint 测试增 `len(specs ∩ click-registered) == len(click-registered)` 反向腿（可复用 test_metadata 的 CliRunner 采集代码）。均属加固，不阻断发布。
