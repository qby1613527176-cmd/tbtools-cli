## 发现

### P1-1【新发现,本轮最重】v1.4.99 发布态全量套件红——targeted 子集门禁漏杀自己引入的 README 变更

- **事实**: HEAD(==tag v1.4.99)全量 pytest 1 FAILED:`TestReadmeStructure::test_toc_anchors_exist`。
- **根因链**: 29fac00(v1.4.99 内容提交)新增 README 受众导航锚点块(product P2 闭环项),其中链接 `#-按任务找命令what-do-you-want-to-do`(GitHub GFM slug,emoji 剥离后前导 `-` + 中英混排)。守卫测试对非纯 ASCII 锚点走「anchor in 原始标题」分支,slug 化混排锚永不命中 → 确定性红。
- **为何发布时没抓到**: 本轮门禁只跑 targeted 子集(守卫14+doc10+onboarding1[+metadata15]),**不含 test_cli.py 的 TestReadmeStructure**;README 改动正是本轮自己做的——「改面」与「跑面」无交集检查。
- **与 GPT 发现的关系**: 独立新发现,GPT 两份评价均未指出(它们盯着数字口径,没实跑全量)。
- **定级 P1**: 已发布 tag 全量红;任何克隆者跑全量即见红;且证明「targeted 子集 + 发版」流程存在结构性盲区。
- **方案**: ①修锚点或修测试(建议测试侧:混排锚点先做 GFM slug 归一再比对,或对 headers 也 slug 化后集合比对);②RELEASING.md 发版门禁强制「若本轮 diff 触及 README*/docs 门面 → 必须含 test_cli.py::TestReadmeStructure + test_doc_consistency」的**变更面驱动子集规则**,或发版前全量一次(720 tests 本机 6 分钟,成本可接受)。

### P2-1【GPT 增量 P2 复核:属实一半】40 vs 25 算术可复原,但构成式仍未写清,+1 身份不可考

- **独立分解结果**: Release 40 = 守卫14+doc10+onboarding1+metadata15;CHANGELOG 25 = 前三项。**差异恰好 = metadata 15**,与 GPT 猜测(40=14+10+15+1)算术一致——本轮我实跑 14+10+15+6(onboarding 全类)=45、14+10=24,可锁定 40 与 25 同源、差一个 metadata 文件。
- **仍属实部分**: ①任何一处文档都没写「40 = 25 + metadata 15」这层对应,读者必须自行实跑分解;②「onboarding 1」身份无法复原(TestAgentOnboarding 实为 6 条,那 1 条是哪条无记录);③RELEASING.md 模板(核验 #14)仍是根因——上轮 v6 报告已给出模板方案,**未被采纳**,v1.4.99 第三次复现同类口径问题(24 vs 39 → 25 vs 40)。
- **定级 P2**(不升 P1:两数字算术自洽,非造假,是可追溯性缺陷)。
- **方案**(与上轮一致,再催):RELEASING.md 第 2 步模板改为强制构成式:`**门禁**: 全量 N passed+M skipped+K xfailed / 本轮子集 M=守卫a+docb+metadata c(+cli d),命令: pytest <精确选择子>`,Release notes 与 CHANGELOG 同模板;「+1」类零散测试必须写 nodeid。

### P2-2【GPT 整体 P1 复核:降级为 P2】默认 CI 不证真实引擎 + 覆盖 35% + cli_load.py 排除——三者均属实但均有在案缓解

- **逐条核实**: ①CI 无 JAR 时 Tier2/EXECUTION_VERIFIED skip——属实(核验 #10),但 test.yml 已显式注释该口径且 `-rfs` 报告 skip 数,非静默;②fail_under=35——属实,全量实测 37.78%,**缓冲仅 2.78pt**(注释自称 37% 基线,实测略升),windows 腿曾因 3.12/3.14 路径差贴线红过(注释在案),仍偏脆;③cli_load.py omit——属实,但有注释理由(元数据加载逻辑被间接覆盖),且 gen_metadata --check 本身对其分组推断有端到端校验。
- **「真实 JAR 集成与快速 CI 分开」建议评估**: **已实现大半**——nightly-e2e(每日真实 JAR×真实数据×产物断言+writeback)与 onboarding-e2e(每周全新机 E2E)就是独立集成路径;push 时快速 CI 不跑 JAR 是合理分层。真正缺口是:**nightly/onboarding 最近一次状态未作为发版硬门禁被机器强制**(RELEASING.md 仅文字提醒「⚠️ 发版前信号」,无 gh api 核验步骤)。
- **定级 P2**(GPT 定 P1 过重:把「分层设计的已知代价」当成了「无验证」;但缓冲薄+发版门禁未机器化是真缺陷)。
- **方案**: ①coverage fail_under 提到 36(实测 37.78,留 1.78pt)或补 cli_load.py 直接单测后提 38;②RELEASING.md 前置加机器步:`gh run list --workflow=nightly-e2e --limit 1 --json conclusion` 必须 success 才许发版;③cli_load.py 维持 omit 可接受,但建议补 1-2 个直接单测后移出 omit。

### P3-1 「onboarding 1」表述误导

CHANGELOG 写「onboarding 1」而 TestAgentOnboarding 实为 6 条——若真跑了该类应写 6,若只跑 1 条应写 nodeid。下轮门禁行一并规范。

## 总体结论

- **GPT 增量 P2(40 vs 25)**: ✅ 算术可复原(差=metadata 15),但构成式缺失+「+1」不可考+RELEASING.md 模板根因三连未除,维持 **P2**。
- **GPT 整体 P1(CI 不证引擎/35%/cli_load.py)**: 三条全属实但均有在案缓解,独立集成路径(nightly/onboarding)已存在;**降级 P2**,真缺口是发版未机器强制 nightly 绿 + 覆盖缓冲 2.78pt 偏薄。
- **本轮独立新发现 P1-1**: v1.4.99 tag 全量套件 1 红(TOC 锚点守卫 vs 本轮自加的受众导航块),targeted 子集门禁对「本轮自己的改动面」无覆盖检查——这是比口径数字更实质的门禁漏洞,建议下轮优先闭环。
