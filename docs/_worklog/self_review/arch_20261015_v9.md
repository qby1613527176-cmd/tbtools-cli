## 发现 1（核实 GPT 审查一 P1）：CATEGORY_MAP 仍参与 CommandSpec 构建 —— **属实，维持 P1**

**实证（探针）**：
- `command_spec.py:854`：ENGINE_REGISTRY 170 个命令的 `group=CATEGORY_MAP.get(name, "engine")`。其中 **154 个命中 CATEGORY_MAP，16 个未命中 → 静默落入默认 `"engine"`**。
- `command_spec.py:889`：manual 命令装饰器前缀推不出分组时回退 `CATEGORY_MAP.get(_n, "engine")`。
- `command_spec.py:999-1001`（`specs_from_scans`）：gen_metadata 投影路径同样 `CATEGORY_MAP.get(name, "engine")`。
- 消费端（`_group_of`，cli_load.py:46-49）已是 CommandSpec 优先、CATEGORY_MAP 兜底——十三轮清理有效；但**生产端**（构建）仍把旧表当分组真源。

**与 GPT 评价的差异/补充**：GPT 只说了 "group= 来自旧表"。探针发现两个更具体的架构事实：
1. **16 个 ENGINE_REGISTRY 命令的分组根本不是"来自 CATEGORY_MAP"，而是来自硬编码默认值 `"engine"`**——这 16 个命令的分组没有任何表记录，是纯 fallback 产物（group census 中 engine=21，其中 16 个即此类 + 5 个 manual 回退）。这意味着即使把 CATEGORY_MAP 清空，这 16 个命令分组仍依赖一个字符串字面量兜底。
2. 当前 **0 mismatch** 是因为消费端与生产端读同一张表；一旦启动"逐类迁出 CATEGORY_MAP"，生产端（854/889/999）与消费端（cli_load._group_of）必须同批迁移，否则 spec.group 与 _group_of 立即分裂——现有守卫无一覆盖这个方向（守卫只测"KEY ⊆ specs"，不测"构建期 vs 消费期分组一致"）。

**定级：P1**（不是 P0：行为正确、无双写漂移，属渐进迁移的既定中间态；但旧表仍是 3 处构建路径的分组真源，"退役"未完成）。

**路线（按来源逐类迁移 + 旧表缩小，不一次推翻）**：
1. **第一步（零行为变化）**：把 `CATEGORY_MAP.get(name, "engine")` 的解析收敛为 command_spec 内部单一函数 `_resolve_group(name)`，854/889/999 三处改调它——先消"三处各自读表"，再谈迁表。
2. **第二步**：分组数据迁入 contracts YAML（或 KNOWN_GROUPS 表），按 census 小组逐批搬：gxf(21)/syn(21)/tree(16)/blast(11)/asm(10) 等小批量先行，seq(45)/table(25) 殿后；每搬一类，从 CATEGORY_MAP 删该类键，跑 `test_cmap_keys_subset_of_specs` + 本轮探针的 `_group_of vs spec.group` 全量比对。
3. **第三步**：16 个默认 "engine" 命令显式标注分组（进 KNOWN_GROUPS），消灭字符串字面量兜底。
4. **收尾**：CATEGORY_MAP 缩为空 dict 后降级为 `assert not CATEGORY_MAP` 的退役守卫。
5. **新增守卫**（第二步配套）：`test_group_consistency` —— 全量命令 `_group_of(n) == build_command_specs()[n].group`，防迁移期生产/消费分裂。

## 发现 2（核实 GPT 审查二 P1）：schema-capable 权威未闭环 —— **部分属实，P1**

**实证**：
- `version --json`（cli_top.py:128-142）**根本没有 schema_capable 字段**；"tools" 统计谓词 `sum(1 for s in build_command_specs().values() if s.kind == "tool")` 是**内联写在 cli_top.py 里的一份拷贝**。
- `gen_metadata.py:290-294`：tools 与 schema_capable 两个谓词又**各写一份内联拷贝**（`s.kind == "tool"`、`s.inputs or s.outputs or s.output_slots or s.parameters`）。
- 即：**同一函数（build_command_specs）是复用的，但统计谓词是三份内联拷贝**（tools×2 + schema_capable×1）。当前数值一致（80/80、64）纯属巧合性同步——改任何一处谓词（如 schema_capable 加 `or s.relations`），另一处静默漂移，且无守卫比对这个谓词本身（counts.md 守卫只比对数字，不防两处公式分叉后数字碰巧仍相等的过渡态）。

**定级：P1**（漂移源真实存在，三份拷贝已数清；但当前数字一致，未造成事实错误）。

**方案（单一统计函数复用）**：
在 `command_spec.py` 新增：
```python
def command_stats() -> dict:
    """权威统计谓词唯一定义——version --json / gen_metadata / readiness 全调这里。"""
    specs = build_command_specs()
    return {
        "metadata_commands": len(specs),
        "tools": sum(1 for s in specs.values() if s.kind == "tool"),
        "schema_capable": sum(1 for s in specs.values()
                              if s.inputs or s.outputs or s.output_slots or s.parameters),
    }
```
- cli_top.py version --json 改为 `from tbtools_cli.command_spec import command_stats`，**顺带补上缺失的 schema_capable 字段**（counts.md 有、version --json 无，本身已是口径面不完整）；
- gen_metadata.py counts 改调同一函数；
- 守卫：`test_doc_consistency` 增一条 —— version --json 输出 ⊇ command_stats() 键且值相等。

**风险评估**：直接收益是导航性；但有三点须防——
1. KNOWN_* 注册表（~500 行数据）才是体积大头，GPT 方案没提它。只搬函数不搬数据，文件仍 800+ 行，拆分收益减半。

3. 拆出的模块必须仍是**同一条构建链**，禁止出现"spec_models 一套定义 + contract_registry 又一套分组兜底"的第二权威。

**拆分计划（分步，每步可独立合入）**：
1. **S1（纯搬数据，零逻辑改动）**：KNOWN_* 12 张表 → `spec_registries.py`；command_spec.py `from .spec_registries import *` 再导出。行数立降到 ~790。
2. **S2**：readiness_census/verification_census/_load_verification_report → `spec_assessment.py`（~180 行，依赖仅 build_command_specs + KNOWN_*，依赖方向单向）。
3. **S3**：to_metadata_entry/specs_from_scans → `spec_export.py`。
4. **S4（可选，暂缓）**：模型类外移——InvocationSpec.build_argv 被 compiler.py/executor 直接引用，外移收益低、触动面大，建议留到最后或不拆。

## 发现 4（核实 GPT 审查一）：入口守卫盲区 —— **部分属实，P2**

**实证**：
- **tbplot.sh 正则解析**：`test_tbplot_sh_cmds_subset_of_specs` 用 `^  ([a-zA-Z][a-zA-Z0-9]+)\)$` 抓 case 标签。本轮实测：宽松模式与守卫模式均抓 140 条、**无遗漏、无复合 `a|b)` 形式**。当前是安全的；但正则是脆弱面——tbplot.sh 1614 行，任何新写法（`cmd|cmd2)`、缩进变化、命令名带 `-`/`_`）都会静默逃出守卫。盲区的"盲"不在当下漏抓，在**漏抓时无报警**（守卫只断言抓到的东西 ⊆ specs，不断言"该抓的抓全了"）。
- **直读禁令**：cli.py/cli_top.py 当前 **0 处直读 CATEGORY_MAP**（cli_top.py:105 仅为 docstring 提及；auto_commands.py:263 是注释）。事实干净，但**没有机器守卫**——DEPRECATED 注释（cli_load.py:52）是唯一防线，任何人新增一行 `CATEGORY_MAP[x]` 无任何测试会红。

**定级：P2**。

**方案（AST 防回归，可行）**：
```python
# tests/test_registry_discipline.py 追加
def test_no_direct_cmap_read_in_entrypoints():
    """入口层(cli.py/cli_top.py/auto_commands.py)禁止直读 CATEGORY_MAP——
    分组只能经 _group_of()/CommandSpec(十三轮 v1.5.2 纪律, 防旧表复活)。"""
    import ast
    for f in ("cli.py", "cli_top.py", "auto_commands.py"):
        tree = ast.parse(open(f"tbtools_cli/{f}", encoding="utf-8").read())
        for node in ast.walk(tree):
            if isinstance(node, ast.Name) and node.id == "CATEGORY_MAP":
                raise AssertionError(f"{f}:{node.lineno} 直读 CATEGORY_MAP")
            if isinstance(node, ast.Attribute) and node.attr == "CATEGORY_MAP":
                raise AssertionError(f"{f}:{node.lineno} 直读 CATEGORY_MAP")
```
AST 方案对"import 别名"（`from cli_load import CATEGORY_MAP as CM`）需补 ImportFrom 节点检查，约 20 行可覆盖；可行且无运行时成本。tbplot.sh 侧补一条反向断言：抓到的命令数 ≥ 一个下界（如 ≥130），写法变化导致漏抓时守卫变红而不是静默放过。
