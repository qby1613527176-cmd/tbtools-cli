## 发现

### 🔴 P1: 金链 pass 分支把旧执行指纹绑进新 conformance 证据(GPT 发现, 独立实证属实)

**代码**: tests/test_conformance_verified.py L416 `_allow_conf = (_gold == "pass") or (_old_conf and _gold != "fail" and _fp_same)`——`_gold == "pass"` 短路, **不要求 _fp_same**。

**实证链**(探针 8): Tier2 fail → 继承路径(L314-333)把旧条目 fp A/X + 旧时间戳原样拷入 `_exec_entries` → `_verified_tools` 建 EXECUTION_VERIFIED 条目(fp A/X) → 金链 pass → L419 直接把该条目 level 改写 CONFORMANCE_VERIFIED, **fp/verified_at/last_passed_at 全是旧值**。本次金链观测(在当前契约 B/环境 Y 下通过)与条目身份(A/X)脱钩; `conformance_verified` 名单同步收录。

**现实触发面**: ① 写入器独立调用时 `_TIER2_RESULTS` 空(结果缺失也走继承); ② Tier2 skip/fail 与金链 pass 的组合(hook 捕获缺口/环境分叉); ③ 契约或引擎变更后首跑: Tier2 尚未 pass 但金链已 pass。

**加载端缓解(部分, 不充分)**: command_spec.py `_load_verification_report` 对 contract_fp 不匹配 discard(契约变→误伤降级, 可用性损失); env_fp 仅在 `TBTOOLS_JAR` env 设置且文件存在时比对——**契约不变 + 引擎变 + TBTOOLS_JAR 未设**时, 错误 env 绑定的金链证据照常通过加载端被消费。

**修复方案**(二选一, 建议①):
1. **身份重绑**: `_gold == "pass"` 升级分支内, 用当前 `_fpfn(SPECS[_t])` / `_env_fp`(有 JAR 时)覆盖被升级条目的 contract_fingerprint/env_fingerprint, 并刷新 `last_passed_at`(注意 `_now_iso` 当前只在 Tier2 pass 分支定义, 需在升级分支就地重算 `datetime.now(timezone.utc)`); 若覆盖前条目已有 fp 且与当前不等, 视同"继承条目被本次观测重验", verified_at 按双条件政策处理。
2. **保守拒升**: `_allow_conf` 改为 `(_gold == "pass" and _fp_same_or_no_entry) or (...)`——金链 pass 但条目携异源旧 fp 时, 以当前 fp 新建条目而非升级旧条目。

**回归守卫**: 新增测试=旧证据(fp=A/X) + Tier2 fail + 金链 pass → 断言最终条目 fp==当前 fake fp 且 last_passed_at 被刷新(方案①), 或断言不升级(方案②)。

### 🟠 P2: 插件 JAR 枚举顺序不稳定 → env_fingerprint 非确定(GPT 发现, 独立实证属实)

**代码**: identity.py L213 `for _jar in _os.listdir(_plugins_dir)` 无排序, 直接 append 进 `_paths`; L222-226 按 `_paths` 顺序 `h.update(...)`——**总哈希输入顺序 = listdir 枚举顺序**。

**实证链**(探针 9): 相同插件集两种 listdir 顺序 → 指纹不同。os.listdir 顺序 POSIX 不保证(文件系统/创建序依赖)——同环境跨机/跨文件系统/目录重建后指纹漂移 → 加载端 env_fp 比对误判"引擎变了" → 历史证据全降级(arch F3 政策: 有 JAR 才比对, 本地机全中)。

**修复**: L213 一行 `sorted(_os.listdir(_plugins_dir))`。**边界化记录**: 修复后 env_fp 值域变化 → 既有报告 env_fp 全部 mismatch 一次 → 需 nightly/本机 `TBTOOLS_WRITE_REPORT=1` 重跑刷新一批证据(一次性换血, 与 FP_SCHEME_VERSION 语义兼容——也可选择 bump fp_scheme 明示)。
