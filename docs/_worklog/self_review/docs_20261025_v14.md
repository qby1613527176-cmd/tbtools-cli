## 1. 🟠 GPT P1: validate_artifact 校验结果层级标注 —— **独立核实: 成立, 定级 P3**

### 现状核实(executor.py:440-488 / cli_top.py:1657-1678)

`validate_artifact` 返回 `tuple[bool, str]`, 详情字符串**无层级标注**, 但实际隐含三层:

| 实际层级 | 现有 detail 样例 | 证据强度 |
|:--|:--|:--|
| existence | `file missing` / `exists(.xyz, no parser)` | 仅证明文件在 |
| structural | `fasta seqs=2` / `gff features present` / `newick parseable` / `rows=N` / `svg xml valid` | 头部 8KB 格式解析 |
| contract | cli_top artifact inspect 追加的 `contract_columns`(契约列名) | 列名对契约 |

问题属实: Agent 拿到 `{"valid": true, "detail": "exists(.xyz, no parser)"}` 与 `{"valid": true, "detail": "fasta seqs=2"}` 时, `valid: true` 字面相同但证据强度差两档。协议 §5 示例(docs/agent-protocol.md:67)`"validation": {"valid": true, "detail": "svg xml valid"}` 同样无层级字段。workflow 侧 `validation_warning` 也直接透传裸字符串(executor.py:233/257)。

### 成本与兼容评估(关键事实: **零测试锁定**)

- 全 tests/ 无任何用例断言 detail 字符串内容(`fasta seqs`/`no parser`/`gff features` 等 grep 零命中)——**改字符串零测试破坏面**。
- 改动点仅 1 函数(executor.validate_artifact)+ 2 消费点字符串透传(无需改)+ 协议 §5 示例。
- 兼容: detail 是人/Agent 可读字符串, 加前缀(如 `structural_check: fasta seqs=2`)为纯增量; 更干净的做法是 cli_top 的 `d["validation"]` dict 加 `level` 字段(结构化, 向后兼容的 additive 字段)。
- **独立补充**: v1.5.7 压缩修复后, 未映射扩展名(非 fa/gff/nwk/tsv/svg)仍走 `exists(...)` 放行——层级标注正好把这个残留模糊点显式化, 与 GPT 建议方向一致且互补。

### 最小方案(P3)

1. `validate_artifact` 返回 detail 加层级前缀: `existence_check:` / `structural_check:`(7 处 return);
2. cli_top artifact inspect 的 `validation` dict 加 `"level": "existence|structural|contract"`(取最高通过层);
3. 协议 §5 示例同步 + §6.2 边界表加一行(见 §3)。

不建议本轮做 semantic_check 层(validate_artifact 无语义断言能力, semantic_checked 是工具级证据, 混进产物校验会稀释语义)。
