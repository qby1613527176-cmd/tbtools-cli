### P1

1. **(P1,独立核实 GPT 属实并扩展)金链 pass env 回退违背证据身份不变量,且被"三端判定不对称"放大。**
   - 代码事实:L289 `_env_fp = _envfp() if os.path.isfile(_JAR) else None`;L337 Tier2 pass 回退 `_old.get("env_fingerprint")`;L437-441 金链 pass 重绑回退旧 env + 刷新 last_passed_at=now。
   - 架构判定:**「env 身份必须来自本次可确认观测」在金链 pass 路径可被违背**——但触发条件比 GPT 描述更窄也更尖锐:金链 pass 意味着引擎本次真跑过(六步断言有产物),此时 env 身份**客观上可观测**;仅因 `_JAR`(core.JAR 全链)不可文件化就回退旧值,是「判定源」而非「可观测性」缺失。具体可复现场景:引擎经 `TBTOOLS_JAR` env 提供(测试实际跑通),但 config.toml/候选路径均无 JAR → `_env_fp=None` → 金链 pass 绑定旧 env_fp + 新时间戳。
   - 与加载端 discard 的对齐缺口:加载端(L1195-1214)在 env-var 有 JAR 时**必然比对** env_fp,失配即 discard(连 CONFORMANCE 一并)。于是上述场景产出的证据,在任何 env-var 部署且 env≠旧值的机器上加载即 discard——**写入端用旧身份签发的"新"证据,对加载端是即时死证据**,只差一台机器。
   - 架构级建议(不推翻回退设计,收窄其适用域):① env 可观测性判定统一为「本次实际执行引擎的 JAR 源」(与 TestTier2 执行判定同源,即 TBTOOLS_JAR env 优先——加载端已是此口径,写入端反向收窄即可对齐);② **金链 pass 且 env 可算时禁止旧 env 回退**(金链观测强度高,绑定未观测身份的证据比没有证据更危险);③ 若 env 确不可观测(envfp 抛异常),金链条目应写 `env_fingerprint: null` 而非旧值——让加载端走"无 env 字段=不比对"的既有宽容支路,而不是伪造同源。
   - 守卫建议:新增 `test_gold_pass_no_env_fallback_when_env_computable`——monkeypatch core.JAR 不可文件化 + TBTOOLS_JAR env 指向真实 JAR + 旧证据 env_fp=OLD,断言金链 pass 产物 `env_fingerprint != OLD and env_fingerprint == 当前 envfp()`;以及 `test_gold_pass_unobservable_env_writes_null`(envfp 强制异常 → 断言 null 而非旧值)。

2. **(P1,独立核实 GPT 属实并加重)--threads 全链路静默丢弃:不是"透传语义模糊",是"用户输入被吞"。**
   - 机器事实:cli.py 80 个静态命令函数体 threads 使用=0;动态 `_cmd_impl` threads 使用=0;且 click option 拦截使 ctx.args(引擎透传唯一通道)不含 --threads(探针③)。**两条通道都断**:声明通道(threads 参数)无人消费,透传通道(ctx.args)被 option 拦截。肌肉记忆型用户 `tbtools tool muscle --threads 8` 得到默认 4,无任何警告。
   - alias 语义冲突(cli.py L60-62):`--threads/-t/--runtime-threads` 同一参数三 alias,help 声称 --runtime-threads 是"显式命名空间避免与引擎 --threads 歧义"——但 Click 层面三者是**同一个 option**,无法区分用户写的是哪个 alias,命名空间分离是文字幻觉;而引擎原生 --threads(如 fqTrim/muscle 的 usage 明写)反而因为被此 option 拦截永远到不了引擎。
   - CommandSpec 层缺席:契约无 runtime_params/engine_params 分离字段,机器可读层无法表达"此参数归 CLI 运行时,不透传"。
   - 方案(三选一,推荐 A):**A. 消费而非透传**——动态 `_cmd_impl` 把 `threads` append 为 `--threads N` 进 args(引擎不认的会被引擎 usage 拒绝,但绝大多数带 threads 的引擎都认;静态命令同理在 args 拼装处消费),短期最小改动止住"吞输入";**B. 让位透传**——从动态 option 清单移除 --threads(ignore_unknown_options 下自然落入 ctx.args 透传给引擎),Agent 运行时并发控制另立 `--jobs` 之类的真运行时参数;**C. 契约层分离**——CommandSpec 增加 `runtime_params` 集合,cli_load 按集合决定 option 是否消费/透传(长期正解,但需 contracts 全量回填)。建议 A 立即止血 + C 列入契约演进;无论选哪个,加守卫:`tbtools tool muscle --threads 8`(mock impl 捕获 args)→ 断言引擎收到 8。

### P2

3. **(P2,独立核实 GPT 属实,结论:文档化当前定义,不推翻)env_fp = 内容集合身份,名称身份缺位。**
   - 机器事实:哈希只进内容字节(identity L241),sorted listdir 使顺序确定;探针②实证「同内容不同名=同指纹 / 同名不同内容=异指纹」。
   - 架构评估:当前定义自洽且有其正当用途——防**内容漂移**(JAR 被换/二进制被升级),这是 verified_at 失效判定的核心诉求。名称缺位的实际风险面:插件 JAR 与外部二进制**均按名称寻址**(auto_commands 显式文件名 + which 按名),重命名同内容文件会导致「加载失败但 env_fp 不变」——证据标签指向一个无法复现加载的环境,且静默。反之,新插件 JAR 落进 plugins/lib(加名加内容)会改变 fp → 触发 discard,方向正确。
   - 取舍判定:**定义澄清 > 算法增强**。算法上把名称入哈希(如 `h.update(p.encode())` 或 `h.update(os.path.basename(p).encode())`)会使「JAR 移动路径但内容不变」也失效全部证据——移动路径在 onboarding/fetch-jar 流程里是常态(下载到指定位置),误伤面大于收益;basename 入哈希则对 which 解析出的绝对路径同名二进制无增量信息。
   - 结论:**文档化当前定义**(在 envfp docstring 与 verification_tiers_note 明示"env_fp=引擎内容集合身份,防内容漂移,不防重命名/路径移动;重命名风险由按名加载失败的显式报错覆盖")+ 未来若插件机制改为「按名从多候选选择加载」(名称成为选择键而非仅定位键),再把名称入指纹。不推翻现有算法。

### P3

4. **(P3,观察项)envfp() 的 `_paths[0]` 与加载端判定 JAR 可能不是同一个文件。** envfp hash core.JAR(env→config→候选链的第一个命中);加载端判定用 TBTOOLS_JAR env。env 与 config 指向不同 JAR 时,envfp 哈希的是 config JAR,加载端却认为"有 JAR 可比"并拿它比对——比较成立但语义上 hash 的未必是跑测试那个 JAR。与 P1-1 同根(三端判定源),修复应一并统一,不单列 P1。
5. **(P3,口径注记)守卫数 12→14 的增量未在任务书口径体现。** TestEvidenceWriteGuard 现 14 项(含此前各轮新增),任务书"守卫 14/14"已同步;前几轮报告写 12/12,属计数时点差异,非回归。

## 总体结论

**有条件通过(0 P0 / 2 P1 / 1 P2 / 2 P3)。** GPT 两份评价的三个架构面**全部独立核实属实**,且两处比 GPT 描述更重:① 金链 env 回退不仅有「保留历史证据 vs 新观测分开记录」的设计问题,还存在写入端(core.JAR 全链)/加载端(仅 TBTOOLS_JAR env)/envfp 内部(core.JAR)三端判定源不对称,使"无 JAR 回退"在「env 实际可观测」时也会触发,产出对加载端即时死亡的证据——建议统一判定源 + 金链 pass 禁止 env 回退 + null 替代旧值,并补两条守卫;② --threads 不是 alias 语义模糊,是静态/动态/透传三通道全断的输入静默吞没(muscle 实测走默认 4),建议动态回调消费 threads 止血、CommandSpec 增加 runtime_params 做长期分离。③ env_fp 内容身份定义自洽,结论为文档化(防内容漂移/不防重命名),不推翻现有算法。常规复核全绿:census 80 三源一致、details 两容器字段组合唯一、守卫 14/14、mypy 27 文件零问题、strict 门禁 exit=0、_record_stage 双容器与 sorted listdir + ctime 缓存键核验落实。两个 P1 均不改变现有证据的合法性边界(无 JAR 继承与加载端宽容支路自洽),属下一轮必修项而非阻断项。
