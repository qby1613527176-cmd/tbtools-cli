## 发现

### P1-1（核实 GPT P1-A 成立）semantic_checked 数据流：继承证据不自包含，重建时用当前静态集合推导

**独立核实（非照抄）**：`test_conformance_verified.py:319-326` 继承分支 `_exec_entries[_t]` 只投影 6 字段（contract_fingerprint / env_fingerprint / verified_at / last_passed_at / corpus / domain_note），**丢弃旧证据 verified_tools 条目里已有的 semantic_checked**（旧报告该字段存在，实测 volcano 条目即含 `"semantic_checked": false`）。随后 `:369` verified_tools 重建对所有条目（本次 pass 与继承一视同仁）执行 `semantic_checked = _t in SEMANTIC_CHECKS`——继承证据的该字段不再来自证据本身，而来自**重建时刻的测试代码静态集合**。GPT 声称属实。

**git 溯源补充（GPT 未提及）**：`git log -L` 显示 `_t in SEMANTIC_CHECKS` 推导式自 c040227（verified N7 时序修复）引入后从未变过——即**断裂不是第五轮 F2② 新造成的**。F2②(52f8b78) 规整继承条目去掉 level/semantic_checked，其影响是：此前继承条目在 `_exec_entries`/details 层还残留旧证据的 semantic_checked（虽然 verified_tools 重建层照样覆盖它），F2② 之后**连 details 层也不带该字段**——断裂从"重建层覆盖"扩大为"全链路无一处保留观测值"。所以 F2② 没有创造断裂，但**加剧并固化**了它：现在想恢复观测语义必须同时改两个分支的 schema。

**语义边界判定**：semantic_checked 的诚实语义应是**观测**——"该证据产生时，内容级语义断言真的跑了且过了"。理由：SEMANTIC_CHECKS 的断言函数在 Tier2 测试体内执行（`:519-520`），断言失败即测试 fail → 无新证据；故对 fresh pass 条目，`_t in SEMANTIC_CHECKS` 恰好等价于"观测到语义断言通过"，是**巧合的正确**。对继承条目则不等价：SEMANTIC_CHECKS 的增删/断言加强都发生在证据冻结之后，静态推导会把"现在代码里有没有这个检查"误述为"证据当时观测到了什么"。例：若明天给 tool X 新增语义断言而 X 本次 fail，继承条目会被标 semantic_checked=true——证据未观测过该断言。

**架构建议（两案取舍）**：
- **A. 证据自包含（推荐）**：两个分支都写 semantic_checked——fresh 分支 `_t in SEMANTIC_CHECKS`（此时=观测），继承分支 `_o.get("semantic_checked", _t in SEMANTIC_CHECKS)`（旧证据缺字段时回退推导兼容 763e55c 前报告）；verified_tools 重建改读 `_exec_entries[_t]["semantic_checked"]`。成本：约 4 行；与 F2② 规整目标**不冲突**——两个分支都带该字段则 details schema 依然统一（F2② 反对的是"只有继承条目带"造成的新旧字段集不一致）。顺带把 level 也从重建层移除推导。
- **B. 维持推导+注释降级**：承认 semantic_checked 是"工具当前是否有内容级断言"的静态属性而非证据观测，改字段名或在 verification_tiers_note 里明示。成本 0，但标签诚实性让位于实现便利，与该项目"证据=观测"的整体设计哲学（verified_at/last_passed_at 拆分、fail 不刷新）方向相反。
- 风险评估：A 案无兼容性问题（surface 哈希忽略时间戳类字段的先例已在；semantic_checked 加入 details 需同步 test_doc_consistency/守卫断言一处，即本轮新守卫 `:780` 的 `"semantic_checked" not in det` 断言需反转——该断言恰是 F2② 规整的化石）。

### P1-2（核实 GPT P1-B 成立）CONFORMANCE_VERIFIED 无独立结果来源，与 Tier2 架构不对称

**独立核实**：`CONFORMANCE_VERIFIED = {"volcano"}`（`:250`）是模块级静态集合；报告写入器 `:371-393` 升级条件仅要求 `_t in _verified_tools or _t in _exec_entries`——即 volcano 只要 **Tier2 执行验证**通过（或继承），level 即升 CONFORMANCE_VERIFIED。而真正的金链六步断言（compile→execute→artifact→sha256→provenance→artifact_id）在 `tests/test_conformance.py:48 TestExecutableConformance.test_volcano_golden_chain`，其结果**无任何收集通道**：conftest.py hook 只匹配 `item.cls.__name__ == "TestTier2ExecutionVerified"` 且要求 callspec 含 "tool" 参数（金链测试用 tmp_path 无参数化，即使类名匹配也收集不到）。

**架构不对称确认**：Tier2 层 = hook 观测 → TIER2_RESULTS → 证据刷新/继承，证据链闭环；conformance 层 = 静态名单 → 直接升级，**"本次金链通过"这一观测从未进入报告构建**。后果场景：金链测试回归（如 provenance 结构破坏）而 Tier2 volcano 仍 pass 时，报告照常声明 CONFORMANCE_VERIFIED——层级声明与它声称代表的测试脱钩。六步断言中 ③④⑤⑥（artifact/sha256/provenance/artifact_id）是金链独有、Tier2 不覆盖的，脱钩有实际信息损失，不是纯形式问题。

**修复成本评估（低风险，可行）**：仿 Tier2 加 `_CONFORMANCE_RESULTS` 收集——
- hook 侧：conftest.py 增一个分支匹配 `item.cls.__name__ == "TestExecutableConformance"`，工具名从 nodeid 派生（`test_volcano_golden_chain` → strip 前后缀），三阶段终判逻辑可整体复用（把现有判断提为 `_final_verdict(stages)` 辅助函数，两收集点共用）。约 +15 行。
- 报告侧：`:371` 循环加门禁 `_conf_res = _CONFORMANCE_RESULTS.get(_t)`，`_conf_res == "pass"` 才升级；`fail` 时降级保留 EXECUTION_VERIFIED + 不更新 conformance_verified 名单；`skip`（无 JAR 环境）继承旧 level（与执行证据继承逻辑同构）。约 +10 行 + 1 守卫测试。
- 兼容性注意：金链测试 `@pytest.mark.integration` 且非参数化，nightly（`.github/workflows/nightly-e2e.yml:60` 全量 tests/ + `:72` 单独跑 conformance_verified）有 JAR 时会真跑；本地无 JAR 环境 skip → 走继承路径，不破坏现有"无 JAR 不洗证据"语义（与 env_fp 保留逻辑同哲学）。
- 结论：**低风险**，结构上是把已验证的 Tier2 模式平移到第二个类，无新模式引入。建议 P1 排期——这是"层级声明必须有对应观测来源"原则的最后一块缺口。

### P2-1 TTL 回退判龄：`_age` 变量复用存隐患（轻度）

gen_metadata.py:455-466：`_age` 在 try 块赋值、`_va2 is not None and _age > 90` 在分支外引用。当前逻辑正确（`_va2` 非 None 时 `_age` 必已赋值），但**靠两变量隐式耦合维持**——后续若有人在 last_passed_at 解析成功的分支与回退分支之间插入代码改动 `_age`，判龄静默错。且 `_bad_ts` 记录后 strict 模式 return 1 在循环外，正确。建议把 `_age` 收进 `_va2` 同分支作用域或改为 `(_va2, _age2)` 元组同赋值。纯健壮性，非缺陷。

### P2-2 hook `_TIER2_STAGES` 残留：nodeid 键跨重跑/重复收集不清理

conftest.py `_TIER2_STAGES` 按 nodeid 累积且**teardown 终判后不弹键**。单进程单次运行无害；但 pytest-repeat / --lf 重跑同一 nodeid 时，第二轮的阶段记录会叠在第一轮残骸上（dict 覆盖同 key 其实会逐阶段覆写，仅当第二轮某阶段未报告时才读到旧值——如第二轮 setup skip 后 call 不报告，则 call 读第一轮 "pass" → 终判误差）。当前 CI 无 repeat 插件，风险低；建议在 teardown 终判后 `_TIER2_STAGES.pop(_node, None)`，一行消除状态残留，符合"状态机用完即焚"原则。

### P3-1 conftest 模块 docstring 与实际内容轻微漂移

docstring 只讲"红队 P1-3 hook 移位修复"，未提六轮三阶段终判（该说明在 hook 函数 docstring 里有）。模块级叙事滞后于代码半代。建议下次顺手补一行。不影响行为。

### P3-2 monkeypatch 兼容性确认无问题（记录而非发现）

`from conftest import TIER2_RESULTS as _TIER2_RESULTS`（`:264`）+ 守卫测试 `monkeypatch.setattr("test_conformance_verified._TIER2_RESULTS", ...)`（`:707`）：真实运行时两名引用同一 dict，hook 写入 conftest.TIER2_RESULTS 对模块可见；守卫测试无真实 hook 运行，替换模块属性即隔离。三阶段状态机不受影响（_TIER2_STAGES 只在 conftest 内读写）。架构上干净。
