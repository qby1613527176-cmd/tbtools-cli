## 发现

### P1-1【P1】金链 pass 短路分支不绑定证据身份——观测与条目错位,写读两端不对称(实机确认)

**位置**: tests/test_conformance_verified.py L416 `_allow_conf = (_gold == "pass") or (_old_conf and _gold != "fail" and _fp_same)`;升级分支 L417-419 只改 level/domain_note,**不动指纹**。

**结构事实**: 十轮修复给**继承支路**加了双侧非空+相等守卫(`_fp_same`),但 `_gold=="pass"` 短路支路**不参与任何 fp 判定**——注释里的同源政策只约束继承,不约束本次观测。于是证据身份不变量出现破口:

- 条目指纹来自 `_exec_entries`:Tier2 pass → 当前 fp(对齐);Tier2 fail/skip/缺失但有旧证据 → **继承旧 fp**(L315-332 规整路径)。
- 金链 pass 是**当前代码+当前环境**下的六步断言观测;把它贴到携带旧 contract_fp/env_fp/旧 last_passed_at 的条目上, ="用今天的观测给昨天的身份发证"。

**可达性评估(为何不是纯理论)**: Tier2(TestTier2ExecutionVerified)与金链(TestExecutableConformance)是同工具的两套独立测试类,结果经 `_record_stage` 各自累积——部分重跑(`-k` 过滤)、语料/fixture 差异、或写入器被单独调用(评审 #110 已承认该场景)都会产生"金链 pass × Tier2 非 pass"格子。探针 #1 证明该格子落出错位条目。

**三级证据链数据流影响**:
1. **CONF 层**: 错位条目写入 committed 报告的 `conformance_verified` 名单;
2. **加载端**: contract_fp 失配 → 双端 discard(探针 #2)——CONF 标签死于抵达,runtime 实际降级但**报告文件不显红**(只读漂移校验只比名单不比 fp);
3. **EXEC/semantic 层**: 同一 `_exec_entries` 继承源在 EXEC 层是对的(继承="曾跑过",不要求本次观测),错的是 CONF 层把"本次金链观测"叠到继承条目上——**EXEC 继承语义与 CONF 观测语义共用一个容器,身份要求不同却未分流**,这是破口根因。

**架构级方案(推荐 A,B 为保守备选)**:
- **方案 A(金链 pass 重绑当前身份)**: `_gold=="pass"` 时金链本身即完整执行观测(含 execute 步),升级分支应**重算并覆盖**条目身份——contract_fp=当前 `_fpfn(SPECS[_t])`、env_fp=当前(无 JAR 沿用旧值,与 Tier2 pass 路径对称)、last_passed_at=now;verified_at 沿用旧值仅当 contract+env 双同(与 L343 `_keep_va` 同政策)。效果:条目身份=观测身份,加载端 fp 比对自然通过,写读对称闭合。
- **方案 B(金链 pass + Tier2 非 pass → 新建当前身份条目)**: 若坚持"CONF 升级只改 level 不动证据",则错位格子应**新建**一条当前身份的 CONFORMANCE 条目(不动旧继承条目),名单从新条目推导。与加载端 discard 对齐方式同 A。
- **反对的修法**: 给 `_gold=="pass"` 也加 `_fp_same` 要求——那会把"金链明明本次通过了"降级成不升级,方向反了(pass 是最强观测,不该被继承守卫约束)。
- **配套**: TestEvidenceWriteGuard 增一例「金链 pass + Tier2 fail + 旧证据(异 fp) → 升级后条目 fp=当前」固化回归;当前 13/13 守卫全部 fp 对齐或 Tier2 pass,此格子零覆盖。

**定级理由**: 当前报告 56/56 非空且 volcano 双名单在册,现行数据不可触发(#12),不定 P0;但它是"写入器发的标签加载端必然丢弃"的写读不对称,与十轮空指纹洞同族(那个修的是继承支路,这个在 pass 支路),定 P1。

### P2-1【P2】env_fp 非确定性:plugins/lib listdir 未排序,同环境可产出不同环境身份(实机确认)

**位置**: tbtools_cli/identity.py L213-219 `for _jar in _os.listdir(_plugins_dir)`——未 `sorted`;最终哈希对 `_paths` 顺序敏感(逐文件 hex 顺序 update)。

**实机证据**: 本机 11 个插件 jar,仅反转 listdir 返回顺序 fp 即变(探针 #3)。`os.listdir` 顺序 POSIX 层**不保证**(ext4 哈希序、overlayfs/WSL 更不稳),同机重装/文件系统变更/跨机同内容都可能不同序。

**架构评估**: env_fp 的定位是"环境身份"(identity.py docstring:引擎本体变化触发证据失效)——身份的第一属性是**确定性**(同环境恒同 fp)。顺序不稳定直接违背该不变量,且有实害级联(探针 #4):①报告重写时 fp 翻牌 → 加载端全量 discard(onboarding 事故同类,代码注释 L1198-1204 记载过一模一样的事故链);②env_fingerprint 在 surface 哈希内(不被 `_surface_hash` 忽略)→ --check 漂移假阳性。

**方案**: `sorted(_os.listdir(_plugins_dir))` 一行修复 + 注释边界化:**jar 增删仍改 fp(这是有意的——环境变了身份就该变),修复只保证"同集合同内容恒同 fp"**。配套可在 tests 加一例"mock listdir 两种顺序 → fp 相等"。

### P2-2【P2】env_fp 缓存键 (path, mtime_ns, size) 不保"保时间戳替换"场景(实机确认)

**位置**: identity.py L184-188 `_key = (p, _st.st_mtime_ns, _st.st_size)`。

**实机证据**: 同路径替换内容 + 恢复 mtime(`cp -p`/`rsync -a`/保时间戳部署常用)→ 缓存返回旧内容哈希(探针 #5)。

**架构评估**: 缓存键即"文件身份近似"。mtime+size 对常规改写足够(写文件必动 mtime),但对**保时间戳替换**类部署不充分——而 JAR/二进制的更新恰恰常走 rsync/包管理器(部分包管理器保 mtime)。后果:换了引擎本体,env_fp 不变,旧证据不失效——与 env_fp 的存在意义正好相反。

**方案(二选一)**:
- **增强键**: `_key = (p, st_mtime_ns, st_size, st_ctime_ns)`——ctime 用户不可设定,任何数据/元数据写入都刷新,覆盖 cp -p 场景;代价是 chmod 等纯元数据操作引发重哈希(数百 MB JAR 一次,可接受)。
- **或文档化局限**: docstring 明示"保时间戳替换不触发重算,进程重启后新进程的 mtime 未变同样不触发"——但注意模块级缓存是进程级的,**跨进程**时 (path,mtime,size) 键本来就不带旧哈希,此边界仅限**进程内**先旧后新的替换,实害窗口窄;据此也可定 P3。综合进程内窗口确实存在(长驻 pytest 会话中换 JAR 重跑),维持 P2 偏低端,建议直接加 ctime(成本一行)。

### P3-1【P3】金链守卫矩阵缺"pass × Tier2 fail"格——13/13 全绿但破口格零覆盖

见 P1-1 配套。当前守卫:fail 降级 / skip 继承 / fp 变拒继承 / 空指纹拒继承 / pass 升级(Tier2 也 pass)——唯独 P1-1 探针打中的格子无守卫,属"守卫全绿≠矩阵全覆盖"的典型。

### P3-2【P3】只读漂移校验只比名单不比 fp——写读不对称的静默通道

`_build` 只读分支(L460+)比 `execution_verified`/`conformance_verified` **名单集合**,不比条目 fp。P1-1 写出的错位条目名单自洽 → 不红;加载端却 discard → runtime 与报告文件两个世界。若 P1-1 按方案 A 修复此通道自然关闭;若选 B,建议漂移校验顺带比对名单内工具的 fp 一致性(成本:一次 `_fpfn` 每工具)。

### P3-3【P3】`_BINS` 派生已 sorted,手写回退清单未 sorted——回退路径残留同类顺序风险

identity.py L197-201:正常路径 `sorted({…})` 派生二进制名,但 `except Exception` 回退清单是手写**未排序** list——虽然 `shutil.which` 逐名解析结果与名单顺序无关、最终 `_paths` 顺序 = 名单顺序,但回退清单顺序是固定的,不引发非确定性;仅记档:两清单内容漂移风险仍在(arch F4 注释已认),回退清单缺 blastp 等,维持观察不升级。

## 总体结论

**附条件通过(0 P0 / 1 P1 / 2 P2 / 3 P3)**。GPT 增量审查两个架构面全部独立核实成立且均有实机证据:①金链 pass 短路支路不绑定 fp,探针确认可写出"观测在当前身份、条目带旧指纹"的错位金链标签,且加载端必然 discard、只读校验不显红(写读不对称,与十轮空指纹洞同族、位于 pass 支路)——推荐方案 A(金链 pass 重绑当前身份)+ 补破口格守卫;②env_fp 非确定性实机复现(11 jar 反转顺序即变 fp),级联到加载端全量 discard 与 surface 漂移两条实害路径,`sorted` 一行可修;缓存键 cp -p 边界实机确认,建议键加 ctime_ns。常规复核全绿:census 80 三源、details 唯一组合(7/8 键)、守卫 13/13、mypy 27 文件、py_compile、strict 门禁 exit=0、版本三源 v1.4.98、_record_stage 双容器+弹键保持。当前报告 56/56 指纹非空,两项缺陷均不可触发,建议十二轮按 P1-1 → P2-1 → P2-2 顺序落地。
