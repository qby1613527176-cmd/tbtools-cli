## 1. 🔴 P0:MCP tool_run UnboundLocalError(GPT 审查二 P1,核实成立且升级)

### 代码事实(mcp_server.py `tool_run`)

十八轮修复(commit `3a506bf`,首发布于 **v1.5.7**,v1.5.8 继承)引入:

```python
if arguments:
    ...
    _unknown_params_warnings = []        # ← 只在 if arguments: 分支内初始化
    for k, v in arguments.get("parameters", {}).items():
        ...
else:
    # args: list/str 兼容入口——不初始化 _unknown_params_warnings
    parts = ...
...
out = _cli("tool-run", *cmd_parts, *parts, "--json", ...)   # ← 底层命令已执行
if _unknown_params_warnings:                                 # ← 无条件访问
    ...
```

`git show 3a506bf~1` 确认:修复前该符号完全不存在,初始化与使用都在同一次提交加入——**这是十八轮修复自身引入的回归,且 v1.5.7 已带菌发布**(GPT 说"十八轮引入"准确;但 GPT 只定性 P1,实证后应升 P0,理由见下)。

### 探针实证(v1.5.8 HEAD,python3 直接调 `tool_run.fn`)

| 入口形式 | 结果 |
|:--|:--|
| `args=['x']`(list,文档支持的新接口) | **UnboundLocalError** |
| `args='x'`(string,旧兼容接口) | **UnboundLocalError** |
| `args=''`(全默认) | **UnboundLocalError** |
| `arguments={}`(空 dict,falsy) | **UnboundLocalError** |
| `arguments={'inputs':['x']}`(唯一幸存路径) | OK(正常 JSON) |

**四种非 arguments 入口全军覆没**——GPT 推断的 `args: list[str]` / `args: string` 两条文档声明的接口 100% 触发,连 `arguments={}` 空 dict(falsy,走 else 分支)也触发。唯一不炸的路径是「非空 arguments dict」。

### 为什么升 P0(比 GPT 的 P1 更重)

1. **底层命令已执行,异常在事后抛**:控制流是 `_cli(...)` 返回 → 才访问 `_unknown_params_warnings`。探针中 `command='search'` 的 CLI 子进程真实跑完(stdout 已在手),MCP 层才炸。对产生文件的引擎(blast/volcano/plot 类),**文件已落盘,Agent 收到的却是 Python 异常**——GPT 担心的「误以为失败重试 → 重复计算/覆盖输出」机制成立。
2. **杀伤面是全部兼容入口**:文档 docstring 明写 `args: list[str] | str` 是合法参数,`arguments` 是可选(None 默认)。任何按文档旧接口调用的 Agent/客户端必炸。这不是边缘 case,是**半数公开接口报废**。
3. **测试零覆盖**:`tests/` 下无 test_mcp 文件;`grep tool_run tests/` 唯一命中是 `test_cli.py::test_tool_run_no_jar_reports_tb005`(CLI 层,不经 MCP 函数)。MCP 层 `tool_run` 函数体**没有任何直接单元测试**——这解释了为何 v1.5.7/v1.5.8 两个发布都漏检。

### 修复方案

```
最小修复(一行): 把 `_unknown_params_warnings = []` 提到 `if arguments:` 分支之前
                 (函数体开头,与 _cli_map/_spec_map 初始化同层)。
```

GPT 建议的「区分没传 vs 传空」在修完初始化后**不需要额外分支**:`arguments={}` 走 else 是合理行为(空 dict 语义=无结构化参数,回退 args),只需初始化提前即两全。

**回归测试(必须随修复同提交)**——四入口矩阵直接调 `tool_run.fn`:

1. `args=['--x','1']` list 形式 → 不抛异常,返回 JSON
2. `args='--x 1'` string 形式 → 不抛异常(+ DeprecationWarning)
3. `arguments=None, args=''` → 不抛异常
4. `arguments={}` → 不抛异常
5. (补) `arguments={'inputs':[...], 'parameters':{已知参数}}` → 正常 + 无 warnings
6. (补) 无契约工具 + 未知参数 → warnings 注入响应(十八轮原意图的保全测试)

建议新建 `tests/test_mcp_server.py`,以上 6 例为首批内容——MCP 层测试空白本身是本次事故的结构性根因。

## 2. 🟠 P2:MCP arguments 结构未校验(GPT 审查一 P2-4,核实成立)

### 探针实证

| 输入 | 实际行为 |
|:--|:--|
| `arguments={'inputs': 'input.fa'}`(字符串) | `list('input.fa')` → `['i','n','p','u','t','.','f','a']` **逐字符展开为 8 个输入**,静默拼入 argv,CLI 层 exit_code=2 报错——错误在下游才暴露,且报错信息(文件不存在)与真实原因(类型错误)完全脱节 |
| `arguments={'parameters': ['x']}`(列表) | **`AttributeError: 'list' object has no attribute 'items'`**——裸 Python 异常,违反 agent-protocol 统一错误信封(非结构化、无 code/retryable) |

两条子路径均如 GPT 所述。`inputs` 字符串逐字符展开那条尤其阴险:不炸,而是带着 8 个垃圾路径调下游,Agent 看到的失败原因完全误导。

### 修复方案(展开前结构校验 + 统一信封)

在 `if arguments:` 块开头加:

```python
for _key, _expect in (("inputs", list), ("outputs", list), ("parameters", dict)):
    _val = arguments.get(_key)
    if _val is not None and not isinstance(_val, _expect):
        return json.dumps({"schema_version": "1.0", "status": "failed",
                           "error": {"code": "INVALID_ARGUMENTS_STRUCTURE",
                                     "field": _key, "expected": _expect.__name__,
                                     "received": type(_val).__name__, "retryable": True}},
                          ensure_ascii=False, indent=1)
```

定级维持 P2:有实际误导性,但触发前提是 Agent 传错类型(契约遵守方不撞)。与 P0 同函数,建议同 PR 修。

## 3. 🟠 架构评估:MCP/workflow 参数编译统一(GPT 审查二架构建议 1)

### 两实现当前分叉点(逐条核对)

| 关注点 | MCP `tool_run` 手写段 | `InvocationSpec.build_argv()` |
|:--|:--|:--|
| 未知参数(有契约) | 返回 UNKNOWN_PARAMETER JSON 信封 | `raise ValueError("UNKNOWN_PARAMETER: ...")` |
| 未知参数(无契约) | **kebab-case 直透 + warnings**(逃生舱,MCP 独有) | 不支持(无契约即无 InvocationSpec) |
| `_cli_map` 宽限 | **KNOWN_PARAMS 旁路兜底**(MCP 独有) | 无 |
| bool 值域校验 | **检查 true/false/1/0/yes/no**(MCP 独有) | 只判 truthy,不校验值域 |
| int/float 校验 | 有,JSON 信封 | 有,ValueError |
| 必填参数检查 | **无** | **MISSING_REQUIRED_PARAMETER**(build_argv 独有) |
| 必填输入计数 | **无** | **MISSING_REQUIRED_INPUT**(build_argv 独有) |
| 输出布局 | inputs+outputs 顺序拼接( positional) | grammar named_flags / token layout / positional 三模式 |

**双向分叉**(不止 GPT 指的方向):MCP 有 build_argv 没有的(`_cli_map` 宽限、bool 值域、无契约逃生舱),build_argv 有 MCP 没有的(必填检查、layout 编译)。两边都不是对方的超集。

### 统一的真实成本与风险

整体让 MCP 调 `build_argv` **不可行**:
1. MCP 的下游是 CLI `tool-run` 子命令(自带一轮 binding/compile),MCP 这层只负责「arguments dict → argv 翻译」,不负责布局——布局在 CLI 侧完成。让 MCP 走 build_argv 会把布局职责上移,与 CLI 路径重复。
2. MCP 有 JSON 协议特有需求:错误必须是结构化信封(不能 raise),无契约工具必须保留逃生舱(CLI 有裸 argv 逃生舱,MCP 对等物就是 kebab-case 直透)。

### 决策建议:最小统一 + 防漂移,不整体合并

**提取共享纯函数**(放 command_spec.py):

```python
def validate_parameter_value(pspec, value) -> str | None:
    """返回 None=通过;否则错误码。MCP 与 build_argv 共同调用。"""
```

统一 int/float/bool 三类的值域判定(消除 bool 校验分叉);未知参数判定逻辑各自保留信封/异常外壳,但「是否在契约内」的判定共用 `_spec_map` 构建函数。

**维持现状的部分**:布局编译(build_argv 独有职责)、逃生舱(MCP 独有职责)、必填检查(MCP 依赖 CLI 下游报错,信封已由 `_cli` 的非 0 包装保证——可接受)。

**防漂移守卫**:加 1 个测试,对同一 (spec, parameters) 分别走 MCP 翻译与 build_argv,断言 flag token 集合一致(对无 layout 工具)。成本 < 50 行,锁住「翻译规则单源」这条不变量。

定级 P3(架构债,非运行时错误)。

## 4. 🟠 P2:测试/生产格式族双源漂移(GPT 审查一 P2-3,核实成立且漂移已发生)

### 事实

- 生产:`workflow.py:344` `_FORMAT_FAMILIES` 在 `plan_from_goal` **闭包内**定义,8 族,`sequence={fasta,fa,fastq,faa,fna,pep}` 与 `alignment={aln,alignment,...,afa}` **分立两族**
- 测试:`test_semantic_unification.py:54` 内联 `_FAMILIES` 5 组,其中 `{"aln","fasta","fa","faa","fna"}` **把 sequence 与 alignment 并成一组**;且 sequence 组缺 `fastq`/`pep`

注释自承「⚠️ _FORMAT_FAMILIES 是闭包内部量,不能 import——测试内联等价映射(独立维护)」。

### 漂移不是未来风险,是当下事实

对 muscle 案例(`output_slots[0].format='aln'` vs `outputs[0]='fasta'`):
- **测试语义**:aln 与 fasta 同组 → `_same=True` → 断言通过
- **生产语义**:`_fmt_level('aln','fasta')` → 不同族、子串规则也不命中 → **incompatible**

即测试放行的配对,生产 planner 判为不兼容。两边语义**今天就不一致**——测试断言的「不漂移」保证在生产侧并不存在。这正是双源维护论点的现实证据,比 GPT 的「未来可能一边允许一边拒绝」更进一步:**已经是了**。

### `_FORMAT_FAMILIES` 在闭包内的原因

纯历史结构:`plan_from_goal` 把 `_accepts`/`_fmt_level`/`_fmt_match`/`_edge`/`_content_compat` 全部实现为闭包(共享 `specs` 等局部量),格式族作为这些闭包的共享常量就近定义在函数体内。**无技术必要性**——它是纯常量,不依赖任何局部状态,提到模块级零成本。

### 最小方案

1. `_FORMAT_FAMILIES` 提为 `workflow.py` 模块级常量 `FORMAT_FAMILIES`(公开名,函数体内留 `_FORMAT_FAMILIES = FORMAT_FAMILIES` 别名一行,零行为变更);
2. 测试删内联 `_FAMILIES`,`from tbtools_cli.workflow import FORMAT_FAMILIES`,断言改为「同族或字面一致」按生产族判定;
3. 附带效果:muscle 的 aln↔fasta 配对在生产语义下不兼容——测试需改写为**期望漂移暴露**(即该测试从「断言一致」改为「断言 planner 语义下的真实级别」,或修正 muscle 契约使 output_slots.format 与 outputs 同族)。**这一步会暴露一个真实契约问题,是修复的正当副产品,不应回避。**

备选(放 command_spec.py 或独立 formats.py):格式族同时被 workflow planning 与契约层消费的话放 command_spec 更合理;当前只有 workflow 用,放 workflow 模块级即可,formats.py 过度工程。

定级 P2(测试保证失效,但无运行时错误)。

## 5. 附加观察(本轮新发现,非 GPT 条目)
