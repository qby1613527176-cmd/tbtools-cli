## 2. 🟠 GPT 潜在风险 1：未知参数 MCP 边界不拒绝 —— **属实，P2**

### 代码路径精读（mcp_server.py `tool_run` L118-181）

`arguments` dict 路径的参数处理优先级：

1. 从 `build_command_specs()` 取该命令 `_spec_map`（有契约工具的 ParamSpec）
2. 每个 `parameters` key：若在 `_spec_map` 中 → 类型校验（int/float/bool，错误 → INVALID_PARAMETER_TYPE，且十七轮已补 schema_version/status ✅）
3. **若不在 `_spec_map`**：`_t=None`，跳过类型校验，flag 取 `_ps.cli_name`（无）→ `_cli_map`（KNOWN_PARAMS，无）→ **兜底 `"--" + k.replace("_","-")` 静默拼接**，`parts += [flag, str(v)]` 直透 CLI

全程无 UNKNOWN_PARAMETER 拒绝分支。

### 探针实证

```
tool_run(command='syn dualsyn',
         arguments={'inputs':[...3 个假路径...],
                    'parameters':{'evil_param':'xyz','chr1':'1,2'}})
```

插桩 `_cli` 抓到实际拼装：

```
('tool-run', 'syn', 'dualsyn', '/a.gff', '/b.col', '/c.out',
 '--evil-param', 'xyz', '--chr1', '1,2', '--json', '--timeout', '600')
```

**未声明参数 `evil_param` 被静默拼成 `--evil-param xyz` 直透**，最终报错是下游 TB102（输入文件不存在）——错误在错误的位置、以错误的码暴露。对有契约工具（全库仅 8 个：specs 带 parameters = 8，与 FULL_params_verified=8 吻合），Agent 传错参数名时无任何「该参数不属于契约」的提示。

### 字符串 args 拆分

`args: str` 形式 `args.split()` 对含空格路径必拆错——但该路径已有 DeprecationWarning 显式劝退（评审遗留），属已知降级路径，P3。

### 定级与方案

**P2**（不升 P1：仅 Agent dict 路径受影响；8 个有契约工具；旧映射/回退路径对无契约工具是必要的逃生舱，不能一刀切）。但对 Agent 而言这是「契约工具的契约不被强制执行」，与 FULL 契约的对外承诺直接相关，建议在下一轮处理。

**最小方案（推荐默认严格 + 显式逃生）**：

- 工具有声明参数契约（`_sp.parameters` 非空）时：key 不在 `_spec_map` → 返回 `UNKNOWN_PARAMETER` 错误（schema_version/status 齐全，`valid_parameters` 列表，`retryable: true`——Agent 可自纠）
- 工具无契约（`_sp` 无或 parameters 空）时：保留 kebab 兜底 + KNOWN_PARAMS 映射，但响应 JSON 加 `warnings: ["parameter '<k>' not in declared contract (tool has no parameter schema); passed through as --k-kebab"]`，让风险可见而非静默
- 字符串 args 维持 DeprecationWarning，不追加动作

## 3. 🟠 GPT P2：FULL 契约 vs 参数审计的用户预期管理 —— **部分属实，P3**

### 子计数投影面核查（FULL_params_verified=8 / unknown=52 到底暴露在哪）

**结论**：十七轮的 census 子计数**不是只在代码里**（doctor --json + tool-index.jsonl 已投影），但投影不全——Agent 最高频入口 `version --json` 和生成的 readiness 文档头都没有。README「60 FULL contracts」单独出现时，GPT 担忧的误读（FULL = 参数已审计）确实成立。

### GPT 四维矩阵 vs 现有体系

GPT 建议：contract_complete / parameter_schema_verified / execution_verified / semantic_checked 四维。

现有体系实际已有三根**正交轴**：

- readiness（FULL/PARTIAL/LEGACY）≈ contract_complete
- params_status（complete/unknown，per-tool 已投影）≈ parameter_schema_verified
- verification_level（DECLARED/COMPILEABLE/EXECUTION_VERIFIED/CONFORMANCE_VERIFIED 四级）⊇ execution_verified
- validate_artifact（executor.py L440，FASTA/GFF/Newick/TSV/SVG 解析级校验）≈ semantic_checked——但它是**运行时产物校验**，不是 spec 静态维度

GPT 的四维 ≈ 现有三轴的重新打包，信息量不增。再加 `parse_validated` 静态维度会与 validate_artifact 运行时校验概念重叠（一个说「产物格式我们认识且会校验」，一个说「这次产物校验过了」），对 Agent 反而多一个易混字段。**不值得新增维度**。

### 定级与最小方案

**P3**。真正的缺口不是维度数量，是**既有子计数的投影覆盖不全 + 文档边界缺一句声明**。

最小方案（文档边界声明优先，不动分级）：

1. README L24 嵌套关系句后补一句：「60 FULL 中 params_status=complete 的 8 个（余 52 为 unknown，参数契约未逐一审计——见 `doctor --json` agent.tools 子计数）」
2. `version --json` 增 readiness census 块（直接复用 readiness_census()，与 doctor 同源，零分叉风险）
3. tool-readiness.md 生成器头部补 census 行（含 8/52）
4. 不新增第四维度；agent-protocol.md 加一句「readiness × params_status × verification_level 三轴正交，勿单读 FULL」
