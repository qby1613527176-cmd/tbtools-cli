## 1. 🔴 GPT 审查二 P1（大文件输入保护）——**核实成立，定级 P1**

### 代码事实（java.py L183-242）
- `snapshot_inputs()`：size > `_MAX_SNAPSHOT_COPY`（50MiB）时走「大文件分支」：
  - Linux `cp --reflink=always` / macOS `cp -c`；**两者失败且平台是 linux/darwin 时，直接 `_backed=False`**，不回退 `shutil.copy2`（copy2 仅用于 Windows/其他平台分支）。
  - 失败时 `snaps.append([_a, None, size, mtime])` —— backup=None。
  - ⚠️ 附加不一致：L207 注释写「COW 不可用→ **hash+警告**」，但实现**并未存 hash**，只有 size+mtime。注释与实现漂移。
- `verify_and_restore()`：backup 存在才比对 sha1；backup=None 只比 `(size, mtime)`。

### 实证探针（本机 /tmp 不支持 reflink，真实复现失败路径）
```
snaps backup?: [('big.fa', False, 52429827)]          # reflink rc=1 → backup=None
场景A(内容变, size+mtime 不变): []                     # ← 完全检测不到（静默破坏）
场景B(size/mtime 变): [(..., 'modified-no-backup')]    # ← 检得出但无法还原
```
即 GPT 两个子断言均实证成立：
1. **同尺寸同 mtime 的内容改写 = 零检测**（引擎如原位 rewrite，破坏静默漏网）；
2. **可检测场景 = 有警无救**（`modified-no-backup` 只报告不恢复）。

### 评估 GPT 建议
- **「reflink 失败退回普通备份」**：方向正确。对 >50MiB 文件做一次全量 `shutil.copy2` 的成本是一次顺序读+写，对数百 MiB 在现代 NVMe 上是秒级——相比「输入被引擎写穿且无法恢复」的数据完整性损失，代价可接受。原设计不 fallback 的动机（避免 GiB 级文件双倍 IO）合理但取舍错误：保护语义不该因性能静默降级。**折中**：reflink 失败→尝试 copy2；copy2 也失败（磁盘满）→退化为现状 None。
- **「无备份时保存内容摘要」**：强烈支持。当前连检测都不完备（场景 A 漏网）。最小成本方案：无备份时存 `sha1`（流式读一遍，数百 MiB 秒级），verify 阶段比 hash；hash 变→报告 `modified-no-backup(unrecoverable)` 并在 stderr 明确「检测到破坏但无法恢复，请从数据源重新获取」。这把场景 A 从「静默」变「显式告警」，是检测完备性的根治。
- 两者**不互斥，应同时做**：fallback copy2 解决「可恢复性」，hash 摘要兜底解决 copy2 也失败时「检测完备性」。

### 定级与最小方案
**P1（数据完整性，发版可带但须列入 known-issue + 下一版必修）**——触发需同时满足「输入 >50MiB 且文件系统不支持 COW」，生信场景（数百 MiB 基因组输入 + ext4/NTFS/网络盘）属常见而非极端。

最小方案（三处改动，均在 java.py）：
1. L207-210 reflink/clonefile 失败后**回退 `shutil.copy2`**（去掉 linux/darwin 的排除条件）；
2. backup=None 时 snaps 第五元素存 `_sha1_file(path)`，`verify_and_restore` 对该分支比 hash 而非 size+mtime；
3. 修正 L207 注释（hash 真做了之后注释即属实）。

## 2. 🔴 GPT 审查二 P1/P2（清理误删预存在副作用文件）——**核实成立，定级 P2**

### 代码事实
- `run()` L485-489：`_pre_listing = frozenset(os.listdir(os.getcwd()))` —— **只快照 CWD**。
- `cleanup_side_effect()` L246-280：扫 `CWD ∪ extra_dirs`（extra_dirs = 所有输入文件所在目录，L514-516）。
- 判定逻辑 L272-278：CWD 内文件用 preexisting 豁免；**非 CWD 目录只退回 `mtime < t0 - 2` 判定**——只要 mtime 够新就删。

### 实证探针
```
输入目录预存在 in.fa.TBtools.fai，本次运行被 touch/重写（mtime 更新）:
  删除数: 1 | victim 还在? False      ← 误删成立
CWD 内同情形（有 preexisting 保护）:
  CWD 删除数: 0 | victim2 还在? True  ← 保护不对称实证
```

### 触发条件真实性评估
- 条件链：① 输入文件不在 CWD（常见：`tbtools run --inData /data/x.fa`，cwd 是家目录）② 输入目录**预存在**符合 `_SIDE_EFFECT_RE` 的文件（TBtools 索引残留 `.TBtools.fai`/`.TBtoolsDB.*` —— 用 TBtools GUI 或此前跑过就会留）③ 本次运行引擎更新了它的 mtime（TBtools 建库/重建索引时会原地重写）。
- ①②单独都常见；③ 是关键——TBtools 对已有索引**通常复用而非重写**（这正是索引存在的意义），所以③不是必然。但 BLAST 建库类工具在参数变化时会重建 `.TBtoolsDB.*`。综合：**有条件触发，非必然，但触发即删用户文件**。
- 缓冲因素：被删的是「可再生的索引文件」而非原始数据，用户损失是重跑一次建库的时间，非不可逆数据丢失。

### 方案评估（GPT 建议 vs 现状）
GPT 建议两点均合理，最小实现：
1. **每个输入目录各存一份 preexisting 快照**：`preexisting` 从 `frozenset[str]`（CWD 文件名）升级为 `dict[dir, frozenset]` 或 `frozenset[abspath]`（扫一次所有 `dirs`，L485 处把 extra_dirs 提前算出再统一快照）。代码量 ~10 行，**根治**。
2. **「无法确定归属宁可保留+警告」**作为纵深防御：对 mtime 落在 `[t0-2, 删除时刻]` 区间但**无法证实本次新建**的文件，打印 `⚠️ 保留疑似预存在副作用文件: <path>` 而非删。若方案 1 落地，此条自动满足（preexisting 命中的就是确定预存在的）。

### 定级
**P2**（误删对象是可再生索引、触发需三条件叠加、有明确修复路径；不升 P1 因为不动用户原始数据）。注意与 §1 的 P1 组合时风险放大：大输入 + 输入目录索引残留是同一用户画像。

## 5. 🆕 本轮 gate 新发现（非 GPT 提出）

### P1: 并发 workflow 状态落盘竞态丢步（executor.py L44）
- **现象**：全量套件 `test_concurrent_merges_no_lost` FAILED；隔离复跑 ~1/15 ~ 1/20 概率失败（并发 flake）。
- **根因**：`_save_state` 的临时文件名是 `p + f".tmp.{os.getpid()}"`——**同进程所有线程共享同一 tmp 路径**。线程 A 写完 tmp 未 rename 时，线程 B 覆盖写同一 tmp 并先 rename → A 的 `os.replace` 抛 ENOENT → 该步**静默丢失**（仅 stderr `PERSISTENCE_WARNING`）。失败现场实证：6 步落盘失败、最终 state 为空 dict。
- **影响**：并发/并行 workflow 执行时步骤状态可丢，断点续跑会重跑已成功的步骤（幂等工具无害，非幂等工具可能重复产出）。测试断言本身写「原子写下可能少量覆盖——但绝不能 JSON 损坏」，说明设计者已知竞态但低估了「整步丢失」的严重度。
- **最小修复**：tmp 名加 uuid 短缀（`f".tmp.{os.getpid()}.{uuid4().hex[:8]}"`）或进程内 `threading.Lock` 包住 read-merge-write 临界区。后者还能消掉「最后写赢」的覆盖丢步，推荐。
- **定级 P1**：数据/状态完整性 + 已有告警通道（PERSISTENCE_WARNING）证明作者知道会失败但没修根因。
