## P1 — 压缩文件扩展名误分类(artifact.py L19-32, L52-55)

### 探针实证(classify 直调)

```
sample.fa.gz          -> ('archive', 'gzip')   ❌ 应为 sequence/fasta
annotation.gff3.gz    -> ('archive', 'gzip')   ❌ 应为 annotation/gff3
reads.fastq.gz        -> ('archive', 'gzip')   ❌
out.collinearity.gz   -> ('archive', 'gzip')   ❌
proteins.faa          -> ('file', 'faa')       ❌ validate_artifact 认 .faa,TYPE_BY_EXT 不认(两处扩展名表已漂移)
genes.fna             -> ('file', 'fna')       ❌ 同上
iqtree.treefile       -> ('file', 'treefile')  ❌ workflow._FORMAT_FAMILIES tree 族认 treefile/contree,TYPE_BY_EXT 不认
iqtree.contree        -> ('file', 'contree')   ❌ 同上
```

### ⚠️ GPT 漏报的更重后果:压缩产物**完全绕过格式校验**

`validate_artifact`(executor.py L440-479)同样用 `splitext` 单扩展名分发,`.gz` 落进兜底分支 `return True, f"exists({ext}, no parser)"`。/tmp 探针实证:

```
bad.fa.gz(内容 "GARBAGE-NOT-FASTA") -> (True,  'exists(.gz, no parser)')   ← 放行
bad.fa  (同内容)                     -> (False, 'fasta header missing')    ← 正确拒收
```

即:**同一垃圾内容,不压缩被最后防线拒收、压缩后直通**。考虑十八轮 verified 视角已证实 validate_artifact 各格式检查本就浅层,压缩旁路使这道防线对生信最常见的产物形态(.fa.gz/.gff3.gz)整体失效。这是 P1 定级的决定性证据——不是元数据不好看,是校验语义空洞。

### 消费方影响面(grep 全量)

| 消费方 | 位置 | 影响 |
|:--|:--|:--|
| validate_artifact 分发 | executor.py L449 | **压缩产物跳过一切 parse 校验**(上实证) |
| artifact inspect 契约列名验证门 | cli_top.py L1657 `art.format in ("tsv","csv","txt")` | `.tsv.gz` 表格永远拿不到 columns 契约验证 |
| artifact 索引登记 | artifact.py register | 索引存 `type=archive/format=gzip`,Agent 读索引得到错误语义(agent-protocol §5 Artifact 模型违约) |
| workflow 契约边格式 | command_spec.py(独立体系) | **不受影响**——规划用 CommandSpec 声明格式,不消费 classify |
| executor 产物登记 | executor.py L217 | type/format 进结果 JSON,语义错但不阻断执行 |

另注意**三处扩展名知识已漂移**:TYPE_BY_EXT(artifact.py)、validate_artifact 的 ext 集合(executor.py)、_FORMAT_FAMILIES(workflow.py)各自维护,`.faa/.fna/.treefile/.contree` 在后两处部分存在、在 TYPE_BY_EXT 全缺。单源化应随本修复一并做。

### 架构方案评估(最小改动路径)

GPT 方向(复合扩展名 + 物理封装/逻辑格式分离)正确,但**不建议给 Artifact dataclass 加字段**(schema_version=1.0 模型被 agent-protocol §5 固定,加 compression 字段是协议变更)。最小兼容路径:

1. **classify() 复合扩展名剥离**:ext ∈ {".gz",".zip",".bz2",".xz"} 时剥一层再查表;`type/format` 返回**逻辑数据格式**(fasta/gff3/...),压缩记入 `metadata["compression"]="gzip"`(metadata 是自由 dict,非协议字段,零兼容成本)。
   - 兼容性:grep 证实**无任何消费方依赖 `type=="archive"`**;cli_top L1657 的 `format in ("tsv","csv","txt")` 门对 `.tsv.gz` 从"误判跳过"变"正确命中"= 行为修复而非破坏。
2. **validate_artifact 同步**:ext 剥离后命中 FASTA/GFF 分支时,用 `gzip.open(path,'rt')` 读前 8192 解压字节做同一套 head 检查(不能拿压缩字节当头)。
3. **扩展名表单源化**:把 `.faa/.fna/.treefile/.contree/.pep/.tre` 补进 TYPE_BY_EXT,并以注释/测试钉住与 _FORMAT_FAMILIES 的对应关系(防再次漂移)。

**定级:P1 成立**(静默校验旁路 + 协议语义错误,非纯美观问题)。

## P2 — fmts.index(f) 架构修复设计(workflow.py L626-630)

### 现状与缺陷

```python
fuzzy = sum(1 for f in fmts if f and f != "relation" and f not in
            [i.format.lower() for i in (specs[chain[fmts.index(f) + 1]].inputs or [])])
score -= 0.05 * fuzzy
```

缺陷①(GPT 指控,属实):`list.index` 按**值**查首次位置——fmts 中重复格式时,第 k 条边的 fuzzy 判定错查 `chain[首现位置+1]` 的 inputs。表达式级复刻:`fmts=["fasta","fasta"]` 时第二边应查 chain[2] 实查 chain[1]。影响有界:每重复边 ±0.05 虚增/虚减。

缺陷②(**本次新发现,GPT 漏报**):fuzzy 判定**未排除 `recipe_*` 字符串标记**。实测 `plan_from_goal("rna-seq", input_format="count_table")` 命中配方链 tpmCalc→pca→heatmap→volcano,fmts=`["tsv","recipe_unvalidated","recipe_unvalidated"]`,最终 confidence=**-0.25**——其中每条 recipe_* 边吃 -0.05 fuzzy 罚(`"recipe_unvalidated"` 恒不在目标 inputs 格式列表)。十七轮修 contract_edges 时排除了 recipe_*(L618-622),fuzzy 处漏修,同一修复原则未贯穿。且因缺陷①,两条 "recipe_unvalidated" 的 index() 都指向 chain[1]——双缺陷在配方链上叠加。

### 架构评估:enumerate 修复是否破坏评分语义

**不破坏。** 两条 fmts 构造路径均保证 `len(fmts) == len(chain) - 1` 且位置语义为"第 i 条边 = chain[i]→chain[i+1]":
- DFS 路径(L540):`_dfs(chain + [cand], fmts + [ef])` —— 每加一节点加一边;
- 配方种子路径(L506-513):`for _i in range(len(_chain)-1): _edge_fmts.append(...)` —— 逐邻接对追加。

enumerate 修复只是把"值查找"换成"本就正确的位置绑定",检查集合与罚分权重不变,仅纠正目标工具索引。与十七轮 recipe_* 字符串标记的交互:修复时应**一并将 recipe_* 排除出 fuzzy**(与 contract_edges 排除原则同源——配方标记不是对目标 inputs 的格式声明,用它算 fuzzy 是范畴错误),否则配方链继续背着 -0.05/边 的隐性罚分。

### 修复方案

```python
fuzzy = 0
for _ei, f in enumerate(fmts):
    if not f or f == "relation" or (isinstance(f, str) and f.startswith("recipe_")):
        continue
    _tgt_inputs = [i.format.lower() for i in (specs[chain[_ei + 1]].inputs or [])]
    if f not in _tgt_inputs:
        fuzzy += 1
```

### 回归测试设计(tests/test_planner_quality.py 增补)

1. **重复格式·虚增向**:构造链 A→B→C,两边格式均为 "fasta",fasta ∈ B.inputs 但 ∉ C.inputs → 修复前 fuzzy=0(虚增),修复后 fuzzy=1。
2. **重复格式·虚减向**:fasta ∉ B.inputs 但 ∈ C.inputs → 修复前 fuzzy=2(双罚),修复后 fuzzy=1。
3. **recipe_* 豁免**:rna-seq 配方链,断言 confidence 不因 recipe 标记吃 fuzzy 罚(修复后应显著高于 -0.25;同时钉住 recipe_unvalidated 不加 contract_edges 的十七轮语义)。
4. **relation 边照旧豁免**、**无边链**(len(chain)==1, fmts=[])不炸、**单边**正常——防回归。
5. 测试内直接调 `plan_from_goal`,对 plan/confidence 断言(现有 test_planner_quality.py 同风格)。

**定级:P2 成立**(评分失真幅度有界 ±0.05/边,不影响正确性,但配方链实测 -0.25 说明叠加后已能翻转候选排序)。

## P2 — MCP workflow_plan 响应包装(mcp_server.py L190-197)

### 实证

```python
return _json.dumps(plan_from_goal(...), ...)   # 裸规划对象直出
```

探针输出顶层:`schema_version("1.1")/goal/input_format/output_format/plan/workflow/confidence/alternatives`——有 schema_version,**无 status/data/error**。对照 agent-protocol.md §3 统一结构 `{schema_version, status, data, error}` 与 §1 铁律 7(schema_version 必带——workflow_plan 满足),违的是 §3 的统一包装。同文件内 tool_run 的 4 处错误分支(L56/70/74/90/166)十七轮已补齐 status 包装,成功路径与 workflow_plan 仍是裸结构——**包装纪律在本文件内都不一致**。

### 架构评估:统一包装 vs 显式例外

对 298 工具规模的项目,我的结论是:**不做全量包装迁移,走"增量 status + 协议显式声明"的混合方案**。理由:

1. **向后兼容成本不对称**。protocol 变更策略自述"1.x 向后兼容(只增不删/不改语义)"。现有 Agent 客户端若已按裸结构解析 `plan`/`workflow` 顶层字段,全量包装是破坏性变更,需 2.x deprecation 周期;而收益仅是"通用解析器少一个适配分支"——成本收益不成立。
2. **plan 是领域文档,不是操作结果**。workflow_plan 无失败路径(DFS 无候选时返回空 plan + direct fallback,L558-561 兜底),status 恒为 "success" 时是纯仪式字段。operation 类工具(tool_run/job_submit)才有真实 status 语义。
3. **但完全裸奔也不对**:协议 §3 未声明例外,文档与实现脱节本身就是协议缺陷(新接入 Agent 按 §3 写解析器会在 plan 上踩空)。

### 决策建议(按优先级)

1. **首选(1.x 兼容)**:workflow_plan 输出**增量加 `"status": "success"` 顶层字段**,保留全部现有字段;agent-protocol.md §3 增补一条:"plan/workflow 模板类响应为领域文档,领域字段置顶层,status/data/error 包装仅用于 operation 类结果"。文档与实现对齐,客户端零迁移。
2. **若坚持全包装**:走双发布——v1.x 输出同时含裸字段(标 deprecated)与 `data.{...}` 包装,v2.0 删裸字段。不推荐现阶段做:项目无 SDK 版本协商机制,无法探知客户端是否已迁移。
3. **必须同时做**:同文件 4 个裸成功路径(tool_run 成功、job_status/job_result 透传 CLI JSON)应与 §3 声明的"operation 类包装"对齐或一并在协议中声明透传语义——否则修 workflow_plan 一处反而加剧文件内不一致。

**定级:P2 成立**(协议-实现脱节,但无功能损坏;客户端适配成本真实存在)。

## 潜在风险 4 — Linux headless 绘图降级(core.py L192-210)

### 现状

```python
if use_xvfb and shutil.which("xvfb-run"):
    full_args = ["xvfb-run", "-a"] + java_args
else:
    full_args = java_args          # xvfb-run 缺失 → 静默降级普通 java
```

GPT 指控属实:xvfb-run 不存在时不警告、不拒绝,直接跑裸 java。headless Linux(无 DISPLAY)上 AWT/Swing 初始化抛 HeadlessException,失败延后到 Java 阶段且以 Java 栈 trace 形态出现,不可操作。

### 降级评估(GPT 未提到的三点)

1. **失败不是静默的,是不透明的**。java 进程会非零退出并报错,executor 层能捕获 exit_code——与"静默吞失败"有本质区别,定级应低于 P2。
2. **就绪诊断已有覆盖**:cli_top.py L188 `doctor --json` 在 Linux 无 xvfb-run 时 `ready=false`(xvfb 被列为 Linux 必需依赖,L223)。Agent 走标准 readiness 检查即可提前发现——缺的是**执行点的就近提示**,不是能力空洞。
3. **不能硬拒绝**:macOS/Windows 本就不需要 xvfb(裸 java 正确),run_plot 目前无 OS 分支;一律拒绝会误杀非 Linux 平台。正确条件是 `os.name=="posix" and not darwin and not os.environ.get("DISPLAY") and not xvfb-run`。

### 修复方向(最小)

run_plot 在 else 分支前加平台条件:Linux + 无 DISPLAY + 无 xvfb-run → stderr 打印可操作警告("headless Linux 无 xvfb-run,绘图引擎将以 HeadlessException 失败;sudo apt install xvfb 或检查 doctor --json")后继续执行(不硬拒,保留 xvfb 检测漏网的逃生空间)。或更激进:给 java_args 注 `-Djava.awt.headless=true` 让失败提前到 JVM 初始化且错误信息明确——需先验证 TBtools 绘图插件在 headless=true 下的失败形态是否可读。

**定级:P3**(诊断链路存在、失败可观测,属 DX/可用性问题而非正确性缺陷)。
