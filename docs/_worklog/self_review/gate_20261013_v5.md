## 发现

### P2-1 get_jar() 通配符候选未展开(GPT 证实,独立复核成立)

- **位置**: `tbtools_cli/runtime/env.py` L58-59,候选列表含 `/mnt/c/Users/*/Downloads/TBtools_JRE1.6.jar`、`/mnt/c/Users/*/Desktop/TBtools_JRE1.6.jar`;候选循环(L63 起)只调 `os.path.isfile(cand)`。
- **独立核实**: 探针①证明 `isfile` 对含 `*` 路径按字面匹配,恒 False;这两条候选是死代码,WSL 普通用户(`C:\Users\<name>\Downloads`)的 JAR 永远命中不了。
- **影响面(降级评估,维持 P2 不升)**: ① `TBTOOLS_JAR` 环境变量、config.toml 路径仍可命中;② 同列表已有 `/mnt/c/TBtools/`、`/mnt/c/Program Files/` 等机器级候选;③ `find_jar_deep()`(L72-)用 `glob.glob(recursive=True)` 正确展开通配,doctor/setup --auto 显式调用可补。受害面=「WSL 用户 JAR 只在 Downloads/Desktop、未设 env/config、且不跑 doctor」的冷启动自动发现。
- **同文件不一致证据**: `get_java()`(L127-137)对通配候选**已正确** `glob.glob(cand)` 再 isfile——get_jar 是孤例。
- **方案**: 候选循环内对含 `*` 的 cand 先 `glob.glob` 展开取首个 isfile 命中(仅 2 条通配、非递归、无匹配时 `glob` 返回空列表零降级,冷启动开销可忽略);或删这两条死候选、统一由 find_jar_deep 承担。推荐前者——与 get_java 对齐,行为一致。

### P2-2 环境指纹缓存非进程级(GPT 证实,独立复核成立)

- **位置**: `tbtools_cli/identity.py` L169,`_fp_cache: dict[tuple, str] = {}` 定义在 `engine_env_fingerprint()` 函数体内;docstring 与注释(L168)声称「(path, mtime, size) 身份缓存——同机多次调用只全量 hash 一次」。
- **独立核实**: 探针②确认模块级无缓存属性;每次调用函数,dict 重建,缓存命中率恒 0。注释承诺与实际行为不符。
- **真危害评估(维持 P2)**: 调用点为 `command_spec.py` L1173 验证报告消费路径,且已做惰性化(`_env_now = None`,仅报告条目带 env 字段才算一次)——不是每条目/每命令一次,频次约「每次验证报告加载 ≤1 次」。但 JAR 53MB + plugins/lib 全部 jar + 外部二进制逐个全量 sha256,单次即数百 MB 读盘;报告生成、身份探针、`cli_top.py` L728 等多入口各自触发,同进程重复调用时纯浪费。属「承诺了缓存却没有」的正确性-性能混合缺陷。
- **方案**: 模块级 `_ENV_FP_CACHE: dict[tuple, str] = {}` + `threading.Lock` 保护读写;key 保持 `(path, mtime_ns, size)`(文件变→key 变→自动失效,测试隔离天然成立,无需清缓存钩子);`_hash_file` 提为模块级私有函数。

### P2-3 (本轮自审新发现) test_doctor_guidance_when_no_jar 在本机失败——九轮机器特例候选破坏测试密闭性

- **实跑**: `pytest tests/test_cli.py::TestAgentOnboarding::test_doctor_guidance_when_no_jar -q` → **FAILED**。断言 `assert "setup --auto" in out`,实际输出 `✅ JAR: /mnt/d/shengwu/TBtools/TBtools_JRE1.6.jar (53MB)`。
- **因果**: 九轮 verified P3-1 往 get_jar 候选加了**本机特例绝对路径** `/mnt/d/shengwu/TBtools/TBtools_JRE1.6.jar`(env.py L56-57,注释自述「本机实际 JAR 位置」)。测试伪造干净 HOME + pop TBTOOLS_JAR,但绝对路径候选绕开 HOME 隔离——在本机(该路径真实存在)doctor 永远找到 JAR,指引分支永不触发。
- **性质**: CI(无 /mnt/d)绿、本机红的**环境分叉门禁信号**;且「把开发机绝对路径写进发布代码候选」本身是九轮修复的副作用,与 P2-1 同源(候选列表卫生问题)。
- **方案**: 测试侧——用 monkeypatch/环境变量把 get_jar 候选收敛(如子进程 env 注入 `TBTOOLS_JAR` 指向不存在路径仍不够,需 patch 候选列表或将机器特例改为读 config);代码侧——机器特例路径更应进**用户级 config.toml**(fetch-jar 已写),而非硬编码进发行版候选。

### P3-1 测试计数记录漂移(GPT「README 不一致」表述不精确,实际漂移在 worklog)

- **核实**: README.md 全仓 grep 无「N 个测试/tests」式计数声明(pyproject description 明确「exact counts via `tbtools version`」,刻意不落数)——GPT 所称「与 README 不一致」**无的放矢,README 没有可不一致的计数**。
- **属实部分**: `pytest --collect-only` @HEAD = **718 tests**;10/12-13 各视角 worklog 记录 652/650/644 passed。数字差异主因是套件随提交增长,worklog 记录的是当时 commit 的数,但**均未标注对应 commit/collect 基线**,横向引用时易误判为漂移。
- **方案**: worklog 记测试数时强制带 `HEAD 短sha + collected N`;README 维持现状(不落数)即可,无需改。

## 总体结论

GPT 增量审查两条 P2 **均独立复核成立**(探针直证,非照抄):get_jar 通配候选死代码(P2-1)、_fp_cache 函数级伪进程缓存(P2-2)。两条均有明确低危降级路径,定级 P2 合适,不升不降。
GPT 整体评价的「测试计数与 README 不一致」**表述失准**——README 无计数;真实问题是 worklog 计数缺 commit 基线(P3-1)。
本轮自审额外发现 P2-3:九轮机器特例候选导致本机 doctor 测试失败,CI/本机门禁信号分叉——这是机器核验(实跑全量套件)才能抓到、GPT 静态审查漏掉的实例,再次验证「静态审查 + 本机实跑」双轨必要。
发布链(release_pypi 门禁预检 + twine check + 冒烟)与 nightly/onboarding 工作流(Render/add-paths ai//pipefail×5/tail -20)机器核验全绿,门禁结构无退化。
