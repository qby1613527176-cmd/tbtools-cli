## 🟠 发现一（GPT 审查一 P2-1 + 审查二 P1/P2）：from_provenance 登记顺序覆盖校验信息 —— **属实，P2**

### 独立核实（不照抄 GPT，自行溯源 + 探针实证）

**代码事实**（artifact.py，当前工作树）：

1. `register()`（L128-188）是**全量覆盖语义**，无合并：
   `idx[art.id] = {"path":..., "metadata": art.metadata}` —— 整个条目（含 metadata dict）被替换。
2. `from_provenance()`（L86-97）流程：`build()` 重建（metadata 只含
   invocation/tbtools_cli/exit_code/timestamp）→ **立即 `register(_art)`**（L96）→ 返回。
   不经过 `validate_artifact()`，也不先读索引旧条目。
3. `resolve_artifact()`（L249-278）：`from_provenance(path) or build(path)` → **之后**才把索引
   条目的 metadata `setdefault` 合并回内存对象（二十一轮 P2-1 修复）。
4. 写入方（executor.py L336-341）：验证通过后才 `_a.metadata["validation"] = ...; register(_a)`
   —— validation 只存在于索引条目中。

**致命时序**：`resolve_artifact` 调 `from_provenance` 时，L96 的 `register()` **先把索引里的
validation 条目全量覆盖成不含 validation 的重建 metadata**；随后 resolve_artifact 的合并循环
读到的已是被覆盖后的索引 —— 二十一轮的「索引 metadata 合并回」修复在**有 .tbtools.json
provenance 边车的场景下被完全架空**（无 provenance 时 build() 不 register，修复仍有效）。

**探针实证**（隔离 HOME，模拟 executor 登记 → resolve_artifact）：

```
index after executor register:   {'validation': 'ok: header+rows'}
index after resolve_artifact:    {'invocation': '...', 'tbtools_cli': '1.5.10', 'exit_code': 0, ...}
returned artifact metadata:      {'invocation': ..., ...}   ← 无 validation
VALIDATION PRESERVED in index:   False
VALIDATION PRESERVED in object:  False
```

validation 在索引与返回对象中**双双蒸发**，且索引被持久污染（后续所有读取方都拿不到）。

**可达路径（blast radius）**：
- `tbtools artifact inspect <path>`（cli_top.py L1652）直接调 `from_provenance(path)` →
  同样触发 register 覆盖。即：**对已验证产物执行一次只读的 inspect 命令，会静默擦掉它在
  全局索引中的校验结论** —— 只读操作产生破坏性写副作用，架构上尤其刺眼。
- `resolve_artifact` 是 Agent 侧「art_id → 完整对象」入口（评审 P1-5 引入），影响所有依赖
  validation 区分合格/未检产物的下游。

**附加架构观察**：`from_provenance` 在「重建内存对象」的纯查询函数里藏了全局索引写副作用
（L96 register），这是问题根源 —— 读路径不该有写副作用；且如 GPT 所述它绕过
validate_artifact 形成「登记先于验证」旁路（虽只覆盖既有条目，不新增未验证 ID，但会
**降级**已有条目的信息完整度）。

### 修复方案（建议，不实施）

推荐 **方案 A（读路径去副作用）+ 方案 B（register 合并语义）双管**：

- **方案 A**：`from_provenance()` 移除 L96 `register(_art)` 调用（或改为可选参数
  `register=False` 默认关闭）。from_provenance 是查询函数，登记职责归写入方
  （executor 已自己做）。**注意兼容**：若有调用方依赖「inspect 顺手补登记」的隐式行为，
  需先 grep 确认（本轮 grep 显示 cli_top 两处调用均不依赖登记副作用，只是读取）。
- **方案 B**（纵深防御）：`register()` 改合并语义 —— 索引已有同 ID 条目时，
  `metadata = {**old_metadata, **art.metadata}`（新键覆盖、旧键保留），而不是整条目替换。
  这样即使未来再有「重建对象登记」路径，validation 等既有结论也不会蒸发。
- 两者独立成立；A 治本（读无副作用），B 防未来同类回归。建议至少做 B（改动小、无行为断点），
  A 做前需确认无隐式依赖。

**回归测试设计**（tests/test_conformance.py 或新 test_artifact_registry.py）：

```python
def test_resolve_artifact_preserves_index_validation(tmp_path, monkeypatch):
    """登记含 validation → 写 provenance 边车 → resolve_artifact →
    索引与返回对象的 validation 都必须存活（二十一轮 P2-1 修复在 provenance 场景不再被架空）"""
    monkeypatch.setenv("HOME", str(tmp_path))
    p = tmp_path / "out.tsv"; p.write_text("a\tb\n1\t2\n")
    (tmp_path / "out.tsv.tbtools.json").write_text(json.dumps(
        {"command": "fasta_formatter", "invocation": "...", "exit_code": 0}))
    a = build(str(p), producer="fasta_formatter")
    a.metadata["validation"] = "ok"
    register(a)
    r = resolve_artifact(a.id)
    idx = json.load(open(_index_path()))
    assert "validation" in idx[a.id]["metadata"]        # 索引不被覆盖
    assert r.metadata.get("validation") == "ok"          # 对象带结论

def test_inspect_is_read_only(tmp_path, monkeypatch):
    """artifact inspect（from_provenance 路径）不得改写索引（方案 A 回归）"""
```
