# tbtools-cli v1.4.91 架构/代码 独立批判性审查

- 日期: 2026-10-07
- 视角: 独立架构/代码审查（只找问题，不称赞）
- 范围: v1.4.91 (HEAD 6a15c1d)。重点核验 v1.4.81→v1.4.91 十版自审战役的 arch 收口质量：
  ①单一真源（CommandSpec vs metadata 投影 vs ai/*，有无作者流回填/双写）
  ②source_scan AST 扫描器（边界 + gen_metadata/command_spec 双侧是否真同源）
  ③meta_guard 投影 staleness 守卫（指纹覆盖面 / mtime 误报容忍）
  ④缓存机制（SpecRegistry/_SPECS_CACHE/失效路径）
  ⑤死代码/废弃路径（引擎注册 vs impl 反射）
  ⑥循环 import 是否根除（import 顺序压力测试）
- 前置: v1.4.81 arch 审查 P0×1/P1×2/P2×6；本轮实测：pytest 547 passed / **1 failed** /
  53 skipped / 2 xfailed（314s）；gen_metadata --check 绿（505 surfaces）；298=298 字段级零差异
- 判定: **不通过（有条件）** — P0 × 0，P1 × 2，P2 × 10。数据完整性无活路径（N1 类破坏
  已闭环），但 CI 主门禁在无 JAR 环境实红、meta_guard 守卫设计自损（对安装用户恒误报），
  两项均属"守卫/门禁声称的状态与实际不符"。

---

## 总体结论

十版战役的**主干成果是实的**：CommandSpec 单一真源方向性成立（runtime 不回填 metadata；
ai/* 唯一写手是 gen_metadata；KNOWN_TOP_MANUAL 已从 command_spec 单源导入，v1.4.81 N4 闭环）；
source_scan AST 化双侧真同源（command_spec.py:867 与 gen_metadata.py:62 调同一函数，
298=298 字段级测试绿）；cli.py 手工命令 output_hint 基本补齐（N1 主路径闭环）；_out_hint
尾部向前修复落地（N9 闭环）；扫描段 except→warn 可见化大面积落地（N6 闭环）。

但发现两处**门禁/守卫层的走形**：① v1.4.90 "安装态 census 55" 改动改变了 env_fp 降级语义
却未同步测试——`test_verification_tiers` 在无 JAR 环境硬挂（CI test.yml 全量 pytest 就是
无 JAR 环境，且行内注释谎称该断言"skip"），HEAD 上 CI 主门禁实红；② meta_guard 的 mtime
指纹 sidecar 同时被 git 跟踪 + 打进 wheel（aaf7513 "fingerprint 进包"）——任何 pip 安装/
新鲜 clone 的 mtime 集与渲染机不同 → `staleness_ok()` 对所有安装用户**恒 False** →
Agent 面永久误报"投影过期"；且 sidecar 自身是 --check 对比面，纯 `touch` 源码即让门禁变红
（本审查实测复现）。守卫在两端都哭狼，N8 的实际保护价值被自损。

## 逐项发现

### M1. 【P1】test_verification_tiers 在无 JAR 环境实红：测试与实现语义分叉，CI 主门禁声称绿实际红

- **位置**: `tests/test_parallel_conformance.py:144-153` vs
  `tbtools_cli/command_spec.py _load_verification_report`（env_fp 比对段，
  "无 JAR 环境无法验证 → 保守信任报告（无 JAR 不刷新不降级）"）；
  `.github/workflows/test.yml:49-53`（全量 pytest 步，无 JAR）
- **发现**: 测试断言 `无 JAR → EXECUTION_VERIFIED == 0`（"防标签指向不存在的引擎"）；
  实现自 v1.4.90（aaf7513 "安装态 census 55"）起明确选择**相反**语义（无 JAR 保守保留证据，
  防 CI --check 漂移）。HEAD 实测（本机无 JAR，与 CI 同形态）：
  `AssertionError: 无 JAR 环境应降级验证证据(env_fp 机制), 实得 55`。
  test.yml:53 注释声称"EXECUTION_VERIFIED 断言在 CI(无 TBTOOLS_JAR)下 skip"——**不 skip，
  是 fail**。改语义时（v1.4.90 PyPI 钳制）没有人跑无 JAR 全量套件，门禁从那天起红到现在。
- **实测证据**: `python3 -m pytest tests/ -x` → `1 failed, 547 passed`（唯一红即本条）。
- **挑战**: 两种语义各自有理（降级=防伪标签；保留=安装态可用性叙事），但必须二选一并
  双侧同步。当前状态比选错更糟：实现走 A、测试守 B、CI 注释谎称 C（skip）——三个口径。
  且这是 F3 修复（env_fp 消费）的回归：修 guard 语义不破测试本应同步改测试。
- **建议**: 确认 v1.4.90 语义为权威（安装态保留）→ 改测试为
  `无 JAR → EXECUTION_VERIFIED == len(report 中有 env_fp 的条目)`（与实现对齐）并修
  test.yml:53 注释；或若坚持降级语义 → 改实现。 whichever，把"CI 无 JAR 全量套件必绿"
  加回发版前检查单。
- **严重度**: **P1**（门禁完整性：主仓库 CI 全量 pytest 在默认环境实红且被注释掩盖）

### M2. 【P1】meta_guard mtime 指纹设计自损：对 100% 安装用户/新鲜 clone 恒误报 + 纯 touch 即破门禁

- **位置**: `tbtools_cli/meta_guard.py sources_mtime_fingerprint`（mtime_ns+size 聚合）+
  `tbtools_cli/command_metadata.fingerprint.json`（**git 跟踪** + wheel 进包，aaf7513）+
  `gen_metadata.py --check`（sidecar 进 `_written` 对比面）+ `cli_top.py _read_command_metadata`
  （warn 出口）
- **发现**: 指纹输入是**渲染机上的 mtime**。sidecar 被 git 提交、被 wheel 携带——
  任何其他机器的 pip 安装（site-packages mtime=安装时刻）或 `git clone`（mtime=clone 时刻）
  都与指纹不符 → `staleness_ok()` 恒 False → 每个安装用户的每次 `tool-describe/search/version`
  都收到 "⚠️ command_metadata.json 投影过期" 误报。守卫对终端用户 100% 哭狼，警告疲劳后
  真正的 stale 也会被无视——N8 的保护目标（开发者改源码未 render）被安装态噪音淹没。
  第二面：sidecar 进了 --check 的内容对比面，而内容是 mtime 指纹——**纯 `touch` 任一
  tbtools_cli/*.py（内容零变化）即让 --check 变红**（本审查实测复现：touch source_scan.py →
  `❌ Generated Surface 漂移: command_metadata.fingerprint.json`）。mtime 语义对
  git 工作流天然不友好（checkout/clone/rebase 全改 mtime）。
- **实测证据**: 上述 touch 复现；本审查为恢复门禁绿不得不重跑 `--render`（见文末"审查副作用"）。
- **建议**: 指纹从 mtime 改为**内容 hash**（sha256 of file bytes；~30 个 .py + 118 个 .java
  全量读约 <50ms，消费端懒加载一次可接受）；或至少：sidecar 不进 git/wheel（只作本地缓存），
  --check 对 sidecar 改用"源码内容指纹重算比对"而非"sidecar 文件内容比对"。
  pip 安装态应直接跳过 staleness 检查（site-packages 场景用户不可能重跑 render）。
- **严重度**: **P1**（守卫设计在其主要部署形态下恒误报 + 门禁对无语义操作过敏）

### M3. 【P2】TTL 告警块缩进错误：--check 每次运行打印 56 行重复"验证超龄(0 个)"告警

- **位置**: `scripts/gen_metadata.py:446-453`（`_msg`/`if _ttl_strict`/`print` 三块
  缩进在 `for _t2, _v2 in _vt.items():` 循环**内部**，与 `if _va:` 同级）
- **发现**: 每次 `--check` 对 verified_tools 每条目打印一遍 TTL 告警，且 0 个超龄也打印。
  实测：`gen_metadata.py --check 2>&1 | grep -c 验证超龄` = **56**。strict 模式下
  `return 1` 在循环内首轮即触发，告警列表只含部分扫描结果（fail-fast 可接受但报告不全）。
  明显是"循环后汇总"写成了"循环内逐条"，走形。
- **建议**: 446-453 整块 dedent 出 for 循环；`_old_days` 为空时不打印。
- **严重度**: P2（门禁噪音；不阻断但稀释告警信道）

### M4. 【P2】循环 import 未根除：java-first 仍 ImportError（F12-3 残留）；cli_load-first 静默降级全注册表 _GROUP=None

- **位置**: `tbtools_cli/runtime/java.py:18` ↔ `tbtools_cli/core.py:279`（core 重导出
  `_n19_move_result`，java 顶层 import core——互引环）；`auto_commands.py _make_impl`
  模块级循环体内 `try: from tbtools_cli.cli_load import _group_of ... except: _GROUP=None`
- **发现**:
  1. import 顺序压力测试（10 模块逐个首导入）：**仅 `import tbtools_cli.runtime.java`
     首导入仍炸** `ImportError: cannot import name '_n19_move_result' from partially
     initialized module`——v1.4.81 F12-3 残留的 java↔core 互引环原样保留（v1.4.89 修的
     是 command_spec↔cli_load 环，已验证该环消失）。
  2. 新增实测：`import tbtools_cli.cli_load` **先**于 auto_commands（任何第三方脚本
     `from tbtools_cli.cli_load import CATEGORY_MAP` 即触发）→ cli_load 顶部 import
     auto_commands（部分初始化）→ 注册循环内 `from tbtools_cli.cli_load import _group_of`

     **import 顺序决定的静默降级**，且 except 不 warn。
- **建议**: ① java-first 环：core.py:279 的重导出改函数级 lazy import（或 java 不顶层
  import core）——若继续接受则在 F12-3 记档处标注"v1.4.91 复测仍在"；② _make_impl 的
  _GROUP 解析延迟到 impl 首次调用（闭包内 lazy），或 except 至少 warn（与 N6 同模式）。
- **严重度**: P2（无数据损害；但"循环 import 修复"声明实际只覆盖 command_spec 侧，
  java 侧原样 + cli_load-first 新降级路径）

### M6. 【P2】输出槽识别白名单泄漏：_OUT_FLAG_RE 不匹配 --outFilePrefix/--outBase/--outDirAndPrefix；one-step 无 output_hint

- **位置**: `runtime/java.py:59-62 _OUT_FLAG_RE`；`cli.py:392`（one-step `run_java` 无
  output_hint）；`cli.py:437`（tool 组泛型分发同样无 output_hint）
- **发现**: 实测正则匹配：`--outTable/--graph/--output/--out` ✓ OUT-FLAG；
  **`--outFilePrefix`（one-step 在用）、`--outDirAndPrefix`（recipBlast 声明的
  named_flags）、`--outBase`（autoMakeBlastDb named_flags）均 no-match**。no-match 时
  flag 值若恰是已存在普通文件 → 被当输入快照 → 引擎重写后被 verify_and_restore 回滚
  （N1 类破坏）。当前无活体触发：三个 flag 的值都是 prefix/base 语义（非已存在文件），
  `os.path.isfile` 兜底救场。但白名单是**按名字猜输出**的启发式——任何工具用
  `--resultFile out.tsv` 类未覆盖 flag 名且重跑到已存在输出，N1 即复活。
  KNOWN_NAMED_FLAGS 已声明了权威 output flag（recipBlast/autoMakeBlastDb 都在），
  快照层却不用它，另起一份正则白名单——双源。
- **建议**: snapshot_inputs 增加第三路输出识别：command_name → build_command_specs()
  → named_flags["output"]/output_slots，权威声明优先于名字启发式；正则白名单降为兜底。
- **严重度**: P2（当前无活体触发，isfile 兜底；但 N1 修复的覆盖面声明与实际启发式
  鲁棒性不符，且存在双源）
