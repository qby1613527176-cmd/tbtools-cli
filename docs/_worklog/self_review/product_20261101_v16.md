## 🟠 GPT 审查一 P2-3：MCP inputs 元素类型未校验 —— **属实，P2**

### 代码事实
`mcp_server.py` tool_run() L131：`parts = list(arguments.get("inputs", []))`。二十一轮已补两处结构校验：
- inputs 整体必须是 list/tuple（否则 INVALID_ARGUMENTS_STRUCTURE）
- outputs 不仅整体是 list，还校验了**元素均为 str**（`all(isinstance(x, str) ...)`，L226-234）

但 inputs 只做到第一层——**元素级校验缺失，与 outputs 不对称**（outputs 有的 inputs 没有）。

### 探针实证
```python
tool_run('volcano', arguments={'inputs': [123, 'file.fa']})
```
实际行为：**裸抛 `TypeError: expected str, bytes or os.PathLike object, not int`**（os.fspath 层，来自 _cli 路径处理）。

三个问题叠加：
1. 不是统一错误信封（无 schema_version/status/error.code），违 MCP 面「永远 JSON 信封」契约；
2. 错误码不可分类（Agent 无法 retryable 判定）；
3. 报错位置远离校验点，消息不含字段名 `inputs`，排查成本高。

### 方案（P2）
与 outputs 段对称，inputs 结构校验后追加：

```python
if not all(isinstance(x, str) for x in arguments.get("inputs", [])):
    return json.dumps({... "code": "INVALID_ARGUMENTS_STRUCTURE",
                       "field": "inputs", "expected": "list[str](元素均为字符串)",
                       "retryable": True}, ...)
```

附带收益：消除下方 P2-4 探针暴露的「业务 TypeError 被测试吞成 skip」的一个具体来源。

## 🟠 GPT 审查一 P2-4 + 审查二 P1：`_run()` 仍吞业务 TypeError/AttributeError —— **属实，P2**

### 代码事实
`tests/test_mcp_server.py` L31-32：

```python
try:
    return fn("volcano", **kwargs)
except (TypeError, AttributeError) as _e:
    pytest.skip(f"tool_run 装饰器包装不可直接调用(框架层, 非业务 bug): {_e}")
```

注释自称「收窄：只有装饰器包装导致的不可调用才 skip」，**但按异常类型无法区分来源**：
- 框架层：fastmcp 把 tool_run 包装成 FunctionTool，直接调用抛 TypeError → 应 skip ✓
- 业务层：tool_run 函数体内的 TypeError（如上面 P2-3 探针实证的 `inputs:[123]`）→ **同样命中 except → skip** ✗

即：如果哪个回归测试传入触发业务 TypeError 的参数，测试会**静默 skip 而非 fail**——钉扎失效，与二十一轮修这个 `except` 的初衷（不吞业务错误）直接矛盾。收窄只是把口子从 Exception 缩到 TypeError/AttributeError，**吞错通道仍在**。

### 可区分性评估（独立结论：可改进）
探针确认当前环境 `type(m.tool_run) == function`，**直接可调用**——skip 分支只在 fastmcp 换包装实现的版本才触发。区分方案按成本排序：

1. **traceback 溯源（推荐，P2）**：捕获后检查 `_e.__traceback__` 最深帧——若 `tb_frame.f_code.co_filename` 以 `mcp_server.py` 结尾（业务代码内抛出），`raise`（fail）；否则 skip。框架包装异常的栈底在 fastmcp/typing 层，业务异常栈底在 mcp_server.py，两者可机器区分，误杀率≈0。
2. inspect.signature 预检：调用前 `inspect.signature(fn).bind("volcano", **kwargs)` 验签——但 fastmcp 包装对象可能伪造签名，可靠性次于方案 1。
3. 消息模式匹配（如 "'FunctionTool' object is not callable"）：脆，fastmcp 版本一变即失效，不推荐。

另注：TestMcpErrorEnvelopes 两个用例的裸 `except Exception: pytest.skip(...)`（L77/93）比 `_run` 更宽——business ValueError/KeyError 也会被吞。同轮可一并收窄。

## 🟠 GPT 审查二设计风险 3：科学语义与执行语义分离 —— **部分已被现状覆盖，P3**

### 现状核查
GPT 建议「保留 execution/artifact 证明作基础，另起一层科学语义验证，别把语义检查硬塞进验证等级」。

实测现有设计**已经是字段级分离**：
- `verification_level()`（command_spec.py L1313）只管执行层：CONFORMANCE_VERIFIED / EXECUTION_VERIFIED / COMPILEABLE / DECLARED，等级本身**不含**语义断言；
- 语义断言（SEMANTIC_CHECKS，test_conformance_verified.py L228：keggEnrich 富集行+kallisto 数值区间+efpHeat ≥100 rect 等内容级断言）以独立字段 `semantic_checked: bool` 挂在证据对象上，与 level 并列；
- 且已有防伪注释：「金链六级断言但 semantic_checked=false——层级≠证据强度超集」。

即「语义不塞进等级」这一点 GPT 的担忧已被现有架构规避。

### 剩余真实缺口（P3）
1. SEMANTIC_CHECKS **住在测试文件里**：科学语义断言是测试的私有常量，不是一等公民数据层——Agent 无法经 CLI/RPC 查询「某工具的语义断言内容是什么」，只有 bool；
2. 无语义层独立版本化：SEMANTIC_CHECKS 集合变更无指纹/无变更日志，证据里的 semantic_checked=true 不指向「按哪版断言验的」；
3. GPT 式「独立可复现科学语义层」值得做的部分 = 把 SEMANTIC_CHECKS 提升为 contracts/ 下的声明式数据（工具→断言描述+断言实现引用+版本戳），报告与 execution 报告分文件落盘。

定级 **P3**：现有分层方向正确，属增强而非纠错。
