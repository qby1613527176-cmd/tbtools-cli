## 发现 1（🔴 P1，属实）commands.md 渲染绕过 `_resolve_group` —— CATEGORY_MAP 单一权威残留

### 独立核实证据

`scripts/gen_metadata.py` `render_commands_md()` L239：

```python
cat = CATEGORY_MAP.get(name, "engine")
```

而同文件 `build()` 产出的 `meta[name]["group"]` 已经由 `specs_from_scans` → `_resolve_group`（KNOWN_GROUPS → CATEGORY_MAP → engine）算出正确分组。**渲染层丢掉了投影层已经算好的答案，重新读了一张更旧的表。**

探针（不复用 GPT 数据，独立跑）：

```
metadata group:  gxffilter→gxf  calcRepeat→asm  admixture→gwas  eggnog→table  filesplit→seq
commands.md 实查: 16/16 个 KNOWN_GROUPS 命令全部落在 "## engine — 通用" 段
mismatch = [(admixture, engine, gwas), (calcRepeat, engine, asm), (gxffilter, engine, gxf),
            (eggnog, engine, table), (filesplit, engine, seq), ... 共 16 条]
```

即 `command_spec.py` 十四轮注释里写明的"消灭 16 个 ENGINE_REGISTRY 命令静默落 engine"在 **runtime/spec/metadata 三层已生效**（`build_command_specs` 与 `command_metadata.json` 均正确），唯独 **用户可见的文档层 commands.md 仍是旧分组**。`gen_metadata.py --check` 不报警——因为检查走临时目录重渲染，同一条 CATEGORY_MAP 路径自我一致，属于"自己对自己"验证盲区。

### 修复方案

1. L239 改为消费投影：`cat = v.get("group") or CATEGORY_MAP.get(name, "engine")`（`v` 即 `meta[name]`，循环里已在手）。一行修复，语义上让渲染层成为纯投影不再读源表。
2. 一致性守卫（新增断言，归入现有 `test_doc_consistency.py`，不新增守卫文件）：解析 commands.md 的 `## <group> —` 段与 `| \`name\` |` 行，断言每个命令所在段 == `command_metadata.json[name]["group"]`。该守卫对 16 条现存错位立即变红，修复后变绿。
3. 顺带：L234 文档头注释"分组归类参考 cli_load.CATEGORY_MAP"改为"分组来源 command_metadata.json group 字段（CommandSpec 投影）"，消除注释与新实现的矛盾。

### 回归风险

极低。分组归属变化只影响 Markdown 渲染布局；counts 统计（L260+ Counter）若按 grouped key 统计需复跑 `--render` 确认数字行不变（实测 grouped key 集合不变，只是 16 个命令换段，各段计数此消彼长，总数不变）。

## 发现 2（🔴 P1，属实且低估）thread_args 三态规则多点实现 —— 且存在真实行为分歧

### 独立核实证据

三态规则（named_flag / positional / unsupported）的当前实现点：

| 实现点 | 位置 | 行为 |
|--------|------|------|
| ① 动态命令 impl 路径 | `cli_load.py` L341-361 | 完整三态分派 + `runner==plot` 动态升级 unsupported |
| ② 动态命令 bash fallback | `cli_load.py` L371-372 | **无条件 `bash_args.extend(["--threads", str(threads)])`** — 不查 thread_style |
| ③ plot 静态命令 | `core.py` `run_plot` L200-202 | 硬编码 warn + ignore（= unsupported 语义） |
| ④ 静态 `tree_onesteptree` | `cli.py` L383-392 | 签名收 `threads`，函数体从不消费、**无警告静默吞参**（注释知道引擎不支持，但用户不知道） |

两处真实分歧（不是纯重复，是 bug）：

- **分歧 A（positional 工具经 bash fallback 错参）**：`mcscanxd` / `parallelMD5Check` / `tfbsShift` / `quickAnno` 四工具契约标注 `thread_style=positional`。impl 路径正确追加位置值；但一旦落到 bash fallback（无 Python impl 或 impl 不可用时），`--threads N` 字面注入——正是十三轮 P1 注释里描述的"落入 Java 位置槽 → 错解/拒跑"事故路径。同一个文件内，impl 与 fallback 不对称。
- **分歧 B（onesteptree 静默吞参）**：用户在 `onesteptree -t 8` 时无任何反馈，引擎按默认线程跑。`run_plot` 有警告但 onesteptree 走 `run_java` 不经 `run_plot`，警告覆盖不到。

### 统一适配器方案

在 `command_spec.py`（或新 `threading.py`，倾向放 `command_spec.py` 与 `_POSITIONAL_THREAD_TOOLS` 同文件就近）加单一函数：

```python
def thread_args(name: str, threads: int | None) -> tuple[list[str], str | None]:
    """线程参数单一适配器: 返回 (追加参数列表, 警告消息|None)。
    三态契约唯一实现点: named_flag → ["--threads", N]; positional → [N];
    unsupported → ([], 警告)。runner==plot 动态升级 unsupported。
    threads is None → ([], None)。"""
```

改造点：

- ① cli_load impl 路径 → `args.extend(t_args); if warn: print(warn)`
- ② cli_load bash fallback → 同一适配器（**消除分歧 A**，positional 工具 fallback 下追加位置值）
- ③ core.run_plot → 保留签名兼容，内部 threads 处理委托适配器（runner=plot 恒 unsupported）
- ④ cli.py onesteptree → 调用适配器拿警告并打印（**消除分歧 B**），或至少复用同一条警告文案常量

### 回归设计

归入 `tests/test_command_spec.py`（不新增测试文件）：

1. 适配器单测：三态 × threads=None/4 共 6 用例 + runner=plot 升级 1 用例。
2. 对称性测试：mock `impl=None`，断言 bash fallback 构造的 `bash_args` 尾部 == `thread_args()` 输出（防分歧 A 回归）。
3. CliRunner 测试 `onesteptree -t 4`，断言 stderr 含"不支持 --threads"（防分歧 B 回归）。
4. 既有 22 个测试全绿为基线（本轮实测 22 passed）。

## 发现 3（🟠 P2，部分属实）CommandSpec 迁移闭环 —— 消费端已闭环，生产端多源仍在，退役无条件

### 独立核实证据

**已闭环的部分（GPT 审查二对此估计不足）**：

- 消费端分组：`spec.group` vs `cli_load._group_of(name)` 探针 298 命令 **0 分歧**。
- `_resolve_group` 已是分组解析单一函数（十四轮收敛三处 CATEGORY_MAP 直读为 854/889/999 一处）。
- `build_command_specs` 与 `specs_from_scans`（gen_metadata 投影）共用 CommandSpec 组装与同源标注逻辑，22 个一致性测试全绿。

**仍开放的部分（GPT 审查二的核心关切成立）**：

1. **多源重复定义仍在**：
   - `ENGINE_REGISTRY`（170 条，auto_commands.py）与 `CLI_TOOLS`（82 条，cli_tools_registry.py）探针发现 **名字交集 `{vcfAddID, mimicVqsr}`**——build_command_specs 里靠 `specs.setdefault`（来源 2，L888）静默去重，registry 优先、tools 条目被丢弃。当前无测试断言"交集应为空"，将来任一侧改 class/xmx 会产生"改了没生效"的隐蔽分歧。注释（gen_metadata L211-213）已认知此归一化，但没有机器守卫。
   - manual 命令真源 = AST 扫描（cli.py 装饰器 + auto_commands impl），与 ENGINE_REGISTRY/CLI_TOOLS 是三类来源，靠 `KNOWN_TOP_MANUAL` + `if _n in specs: continue` 优先级裁定——裁定规则隐式，无文档化真源优先级表。
2. **旧表退役只有方向没有条件**：`CATEGORY_MAP`（188 条）标了 DEPRECATED，注释写"迁表后旧表缩小/逐步清空"，但：
   - `KNOWN_GROUPS` 仅 16 条，**剩余 172 条 CATEGORY_MAP 条目没有迁移计划、没有"何时可删"的判定条件**（如：KNOWN_GROUPS 覆盖率 ≥ X% 且 commands.md 改消费投影后）。
   - 发现 1 证明至少还有 render 层在读旧表——"禁止直接读"目前靠注释自律，非机器强制。
3. `gen_metadata._infer_group`（L105-130）仍自带"CATEGORY_MAP → cli.py 装饰器正则 → engine"三跳逻辑，与 `_resolve_group`（KNOWN_GROUPS → CATEGORY_MAP → engine）是**两套优先级不同的解析器**。当前因 KNOWN_GROUPS 只覆盖 engine-registry 命令而巧合一致；一旦有 manual 命令进 KNOWN_GROUPS，两解析器立即分叉。

### 闭环路线（不增加守卫数量，推进闭环本身）

1. **退役条件显式化**（写进 command_spec.py KNOWN_GROUPS 注释头）："CATEGORY_MAP 条目删除条件 = (a) 该命令在 KNOWN_GROUPS 有映射且两表一致，或 (b) 该命令分组已由装饰器/AST 真源供给。每迁一批删除一批，空表即删 CATEGORY_MAP。"——给"逐步清空"一个可验收的完成定义。
2. **复用既有守卫而非新增**：把"render_commands_md 消费 meta group"（发现 1 修复）视为退役路线的前置步骤——消费端清零后，CATEGORY_MAP 的读者只剩 `_resolve_group` 一处，迁表即删表，不需要新守卫。
3. **交集断言并入现有测试**：`test_command_spec.py` 加 1 条 `assert not (reg_names & set(CLI_TOOLS))`（或显式断言已知 2 条交集的归一化优先级），把隐式裁定变显式契约。成本 1 个用例，消灭多源重复定义的静默漂移面。
4. `_infer_group` 收敛到 `_resolve_group` 单一调用（manual 无装饰器分组时），消灭双解析器分叉隐患。

定级 P2 而非 P1：运行时行为当前正确（0 分歧实测），风险是结构性的（未来漂移），不是现存用户可见错误。
