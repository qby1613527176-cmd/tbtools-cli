## 一、GPT 增量红队 P1：统一边判定入口缺失 —— **属实，P1 成立（且发现 GPT 未指出的实证性评分 bug）**

### 1.1 现状测绘（边判定逻辑实际分布）

v1.5.5 中「A→B 这条边成不成立、算什么性质」被 **4 处各自解释**，无单一入口：

| 位置 | 函数 | 判定维度 | 消费方 |
|:--|:--|:--|:--|
| workflow.py:372 `_edge` | 格式兼容（outputs∩inputs/relations.accepts） | 格式 | DFS 邻居扩展、`_reach_goal_2hop`、分支排序 |
| workflow.py:382 `_content_compat` | content_type 语义（slot 级 protein→dna 等） | 语义 | **仅** `_score` 的 -0.3 罚分（workflow.py:613） |
| workflow.py:435 `_edge_info` | 包装 `_edge` + match 级别 + legacy_relation | 格式+来源 | **仅** 配方种子链校验（:498） |
| workflow.py:553 `_score` / :664 `_reason_for` | 从 fmts 字符串标记反推边性质 | 字符串模式匹配 | 评分、Agent 可见 reason |

观察到的三处不一致（均为实证，非推测）：

**(a) 配方链不查语义冲突。** 配方种子链只调 `_edge_info`（格式层），不调 `_content_compat`。格式兼容但语义冲突（protein→dna，真实存在对：`sixframe→pep2codon`、`sixframe→longestorf`）的配方边会被标 `recipe_validated`，与 DFS 链的判定口径不一致——同一对工具，走配方入口和走契约图入口得到不同的"验证"语义。

**(b) 🔴 新发现 bug（GPT 未指出）：`recipe_unvalidated` 边被计入 contract_edges。** `_score` 中：
```python
contract_edges = sum(1 for f in fmts if f and f != "relation")
```
`"recipe_unvalidated"` 是非空字符串且 ≠ "relation" → 被计为契约边。探针实证（volcano→[未知]→iqtree 配方）：
```
plan: volcano → iqtree  reason: recipe(配方链·边未过契约校验)
confidence_reasons: ['recipe_seed', 'irrelevant_start', 'all_contract_edges', 'content_type_conflict']
```
**`all_contract_edges`（+0.2）与"边未过契约校验"的 reason 同时出现**——这正是 GPT P1 预言的"评分与理由各自判断导致不一致"，且已在 v1.5.5 实际输出中发生。十六轮把哨兵从 tuple 改成字符串修了 reason 泄漏，但没修 `contract_edges`/`fuzzy` 两处对字符串标记的误计（`fuzzy` 中 `fmts.index(f)` 对重复值还会错位）。

**(c) DFS 路径允许语义冲突边入链。** `_edge` 只看格式；content 冲突链只在评分时 -0.3，不淘汰——若它是最高分仍被选中，plan JSON 里 reason 写 `contract graph(fasta)`，Agent 看到的是"契约边成立"，而评分层知道它冲突。理由字符串与评分事实脱节。

### 1.2 架构评估：最小必要统一（不过度设计）

298 工具规模下，**不需要** GPT 暗示的全量 `validate_edge` 对象体系。最小必要方案两步：

1. **修 bug（P1a，必须）**：`contract_edges` 与 `fuzzy` 统计排除 `recipe_*` 字符串标记：
   `contract_edges = sum(1 for f in fmts if f and f != "relation" and not (isinstance(f,str) and f.startswith("recipe_")))`；
   fuzzy 循环改用 enumerate 不用 `fmts.index(f)`。
2. **统一判定函数（P1b，值得做，工作量小）**：加一个备忘录式 `_edge_verdict(a,b) -> (status, format)`，status ∈ {exact, compatible, relation_only, content_conflict, none}——内部就是现有 `_edge_info` + `_content_compat` 的一次合并调用。四处消费方改为只读 verdict：
   - 配方段：`status is none → recipe_unvalidated`，`content_conflict → recipe_semantic_conflict`（新标记，与 validated 区分）；
   - `_score`：contract_edges 只数 status ∈ {exact, compatible}；content_conflict 罚分直接读 verdict 不再重算 `_content_compat`；
   - `_reason_for`：由 verdict 生成，不再从字符串反推；
   - DFS：维持现状（语义冲突边仍允许探索、靠评分降级）——**不建议**在 DFS 层硬排除，会牺牲可达性，298 规模下评分降级已够。

代价：约 40 行净改动 + 每对工具一次 verdict 计算（可 functools.lru_cache，DFS 内重复判定同一对边多次，顺带提速）。收益：消除 (a)(b)(c) 三类不一致，理由/评分/结构同源。

**结论：P1 成立。其中 (b) 是有探针证据的输出级 bug，优先级应排在统一重构之前单独修。**

## 二、GPT 增量红队 P2：未知工具删除后自动重连（拓扑篡改）—— **属实，P2 成立**

### 2.1 代码事实（workflow.py:489-495）

```python
for _t in _raw:
    if _t in specs:
        _chain.append(_t)
    elif _t:
        print(f"⚠️ 配方 ... 引用未知工具 {_t}, 已跳过", file=sys.stderr)
```
v1.5.5 新增的警告**只到 stderr**；未知工具被从链中删除后，前后步骤直接相邻重连，再走 `_edge_info` 校验。

### 2.2 探针实证

探针 1（muscle→NonExistentTool999→trimal，A→C 恰好契约兼容）：
```
STDERR: ⚠️ 配方 probe-topology 引用未知工具 NonExistentTool999, 已跳过
PLAN: muscle → trimal   reason: contract graph(aln)
```
JSON 输出中 muscle→trimal 与"原始配方就是两步"**完全不可区分**（无任何字段记录拓扑被改写过）。警告在 stderr，Agent/程序化消费 JSON 时不可见。

探针 2（volcano→未知→iqtree，A→C 不兼容）：
```
PLAN: volcano → iqtree  reason: recipe(配方链·边未过契约校验)  confidence 0.1
```
仍作为完整候选链进入 plans（还带 recipe_seed +0.4 基础分），只是边标 unvalidated。

**结论：拓扑篡改属实。** A→Unknown→C 静默变成 A→C，若兼容则被当作配方原意。严重程度定 P2 合理：需要配方引用不存在的工具才触发（现实场景=TBtools 版本漂移/工具改名），不污染正常配方；但一旦触发，输出层无痕。

### 2.3 方案（三选一，推荐 ②）

1. 中间未知 → 整条不作完整候选（丢弃）：安全但浪费——头尾片段可能仍有价值；
2. **切分片段（推荐）**：遇未知工具把链切成已知连续段，每段独立作为配方种子（段长 ≥2 才注入，单点无意义），fmts 不变；stderr 警告保留。改动 ~10 行，语义清晰：配方声称的肌肉记忆只保留未被未知打断的部分；
3. 标 `recipe_partial` 标记：比 ② 多一个状态机，收益不明显，298 规模属过度设计。
