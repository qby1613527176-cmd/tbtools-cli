## P1

### P1-1(新) 版本门禁的 tag 腿在 CI 静默失效——守门人在最该开火的环境里半盲
- **发现**: gen_metadata.py --check 的版本门禁用 `git tag` 取最新 tag 与 pyproject 比对(L443-460)。但 test.yml 的 `actions/checkout@v4` 未配 `fetch-depth: 0` / `fetch-tags: true`——默认浅克隆**无 tags**,`_git_tags` 为空 → `_latest=""` → tag↔pyproject 比对整条腿被跳过,只剩 README 腿。本地审查时该门禁正常工作(输出 `✅ 版本一致性 ... (tag v1.4.81)`),**恰好在 CI 这个唯一强制环境里失效**。
- **挑战**: 上轮 P0-3 的修复把版本校验放进了 --check,方向正确;但"门禁存在"≠"门禁能开火"。wheel 携带错误版本号发布的事故路径在 CI 里仍然敞开——如果未来某次发版忘 bump pyproject,本地 --check 会拦,CI 不会,而合并靠的是 CI。
- **建议**: test.yml checkout 步加 `fetch-depth: 0`(或 `fetch-tags: true`);或版本门禁在 `_git_tags` 为空时显式 print "⚠️ 无 tag,tag 腿未检"而非静默通过。
- **严重度**: P1

### P1-2(新) TTL 严格检查整块包在 `except Exception: pass` 内——严格模式存在静默失效路径
- **发现**: TBTOOLS_TTL_STRICT 严格阻断逻辑(L431-438)本身被外层 `try/except Exception: pass`(L439-440)包裹。若 verification_report.json 损坏/字段缺失/日期解析崩坏,异常被吞 → **严格模式静默通过**,与"nightly TTL 严格模式"的设计意图直接矛盾。nightly-e2e.yml 的 TTL gate 步骤因此可能在报告损坏时给出假绿。
- **挑战**: 上轮 P0-2 治理了 15 处静默 except 中杠杆最高的渲染路径,但 TTL 这条新写的防御路径又落回了同一个模式——新增防御代码时未继承"降级必告警"的纪律。
- **建议**: 该 except 至少 print 告警;严格模式下 except 应 return 1(报告不可解析 = 证据不可信 = 红)。
- **严重度**: P1

## P2

### P2-1(残留) 19 处 except Exception 仍有 10 处纯 `pass` 无告警
- **发现**: 渲染关键路径(error-codes/tool-readiness/contracts/版本门禁)已加 print 可见化,但 census、verification census 动态数(`_verif_n="?"`)、relations.json 导出等 10 处仍静默。**存在性**漂移已被 repo→fresh 反向断言覆盖(310 个 git 跟踪 generated surface 全比对),但**内容级**静默降级(如 census 数字算错、verification 数变 "?")无任何信号——--check 会在 `verification=?` 的情况下报"全同步"。
- **建议**: 不强制全部消除,但 `_verif_n` 为 "?" 时 --check 应降级为告警(数字可信度是 EXECUTION_VERIFIED 叙事的一部分);relations/census 类 except 补一行 print,成本极低。
- **严重度**: P2

### P2-2(未闭环) counts.md 的 `rpc_methods: 188` 仍是硬编码字面量
- **发现**: 上轮 P2-2 指出"自称自动生成的权威口径文件里有一个只能手改的数字"。v1.4.81 依然 `"rpc_methods": 188, # RPC 方法(固定)`(L293)。bridges=118 已改为扫文件派生,证明派生化可行,唯独 rpc_methods 未动。
- **建议**: 从 RPC server 方法表/bridges 枚举派生,或在 counts.md 该行旁注明"人工维护";勿让硬编码继续披"自动生成,勿手改"的外衣。
- **严重度**: P2

### P2-3(新) test-windows job 依赖未 pin,与 P1-2 修复口径不一致
- **发现**: 主 test job 与 nightly 已切到 `pip install -r requirements-ci.txt`(click 8.4.2/pytest 9.0.2/ruff 0.16.8/mypy 1.19.1 锁定),但 test-windows 仍 `pip install click pytest ruff pyyaml` 全浮动。windows job 跑 ruff check——ruff 版本滚动可在 windows leg 单独制造红灯,锁定纪律只覆盖了 2/3 的 job。
- **建议**: windows job 同用 requirements-ci.txt。
- **严重度**: P2

### P2-4(新) CI echo 仍含硬编码叙述数字 "54/60=90%"
- **发现**: 上轮 P1-4 修掉了硬编码 "52 skipped",test.yml echo 改为"准确数量见 -rfs 报告"——方向正确;但同一 echo 里仍写死"执行验证 54/60=90%"。execution_verified 变成 55 时该文案即过期,与 P1-4 治理的是同一类漂移点,修了一个留了一个。
- **建议**: echo 删掉具体数字,只保留"口径见 docs/_worklog/PLAN.md"。
- **严重度**: P2

## 最值得改的 3 点

1. **test.yml checkout 加 `fetch-depth: 0`**(P1-1): 一行改动,让版本门禁的 tag 腿在 CI 真正开火——否则"版本漂移轮"在强制环境里是装饰品。
2. **TTL 严格模式的 except 改为告警+严格下 return 1**(P1-2): 严格模式的含义是"证据不可信即红",当前实现允许"证据读不出=绿"。
3. **三处"修尾巴"收尾**(P2-2/P2-3/P2-4 合并): rpc_methods 派生化、windows job 换 requirements-ci.txt、echo 删 54/60——都是 5 分钟级改动,清掉后上轮 11 项 100% 无残留。
