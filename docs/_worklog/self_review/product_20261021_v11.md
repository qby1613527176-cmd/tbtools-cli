## 一、GPT 增量红队 P1：bash fallback 丢弃已处理的 argv —— **代码缺陷属实，但当前零触发面，建议降为 P2**

### GPT 原声称
`cli_load.py` 无 impl 时走 bash fallback，用 `ctx.args` 重建 `bash_args` 而非已处理的 `args`，导致 `--format` 覆盖 / preset 宽高 / threads 分派等前置处理在 fallback 路径全部丢失。

### 独立核实（逐行对读 `_cmd_impl`）

`_cmd_impl` 中对 `args` 做了四项前置加工（cli_load.py 约 340-390 行）：
1. 输入文件校验 + 格式提醒（读 `args[0]`，两分支共享，**不丢**）
2. `--format` 覆盖：倒序扫描 `args` 找 `.svg/.png/.pdf` 后缀改写为 `.{fmt}`（**改的是局部变量 `args`**）
3. preset → width/height 解析，width/height 追加到 `args` 末尾（**改的是 `args`**）
4. threads 经 `thread_args()` 三态分派（named_flag/positional/unsupported）

然后分支：

```python
if impl:
    ec = impl(args, ...)                       # ← 用处理后的 args ✓
else:
    bash_args = [bash_bin, tbplot.sh, name] + list(ctx.args)   # ← 用原始 ctx.args ✗
    if threads is not None:
        bash_args.extend(thread_args(...))     # ← 只有 threads 被单独补上
```

**结论：fmt 扩展名改写、preset 宽高注入、显式 --width/--height 追加，在 fallback 分支全部丢失。** GPT 的代码阅读结论属实。

### 探针实证

构造无 impl 的动态命令 `zzprobe`（`_make_passthrough("zzprobe", g)`），`CliRunner` 调用 + mock `subprocess.run`：

```
入参: zzprobe in.fa out.svg --format png --preset nature --threads 8
impl 路径预期 args: [in.fa, out.png, <preset_w>, <preset_h>, --threads, 8]
fallback 实际 argv: [bash, tbplot.sh, zzprobe, in.fa, out.svg, --threads, 8]
```

**实证确认：out.svg 未改写为 out.png，preset nature 的宽高未追加。** 仅 threads 经十五轮统一适配器存活。

### 但：触发面为零（独立增量发现，GPT 未提）

机器核验全部 140 个 tbplot.sh 命令：13 个无 impl 的命令（dehist/genestructure/hclust/heatmap2/motif/msa/onesteptree/pca/seqlogo/tree/treeRooting/unrooted/volcano）**全部落在 `_load_dynamic_commands` 的 `registered` 排除集内**（都是手工注册命令，不动态转发）。即**运行时实际走 bash fallback 的动态命令数 = 0**。

### 定级与方案

- **定级：P2（潜在缺陷，零存活触发面）**。不是 P1——当前没有任何用户可到达该路径；但代码是不定时炸弹：未来任一 tbplot.sh 新命令若无 auto impl，将静默丢失 fmt/preset/宽高处理。
- **方案（最小）**：fallback 分支改用处理后的 `args` 重建，删掉单独的 threads 补追（threads 已在共享段注入 `args`）：
  ```python
  bash_args = [bash_bin, os.path.join(ROOT, "bin", "tbplot.sh"), name] + args
  ```
  一行修复，消除双轨。附回归测试：mock subprocess.run 断言 fmt 改写存活。

## 二、GPT 全面审查：FULL × execution_verified 交叉表缺失 —— **属实，P2**

### 现状核实

- `version --json` 有 `execution_verified: 56`，但**无任何交叉字段**
- `docs/_generated/tool-readiness.md` 是 metadata coverage 表（5 维元数据），非 readiness×verification 交叉
- `counts.md` 分列 `agent_ready_full: 60` / `execution_verified: 56`，无交叉
- grep 全库无 "交叉/cross" 统计实现

### 独立计算真实交叉数（specs + verification_report.json 双源）

```
FULL = 60   execution_verified = 56
FULL ∩ exec = 56   FULL ¬exec = 4   exec ¬FULL = 0
```

**4 个 FULL 但未执行验证的工具：`gxfIdAppender`、`pafref`、`smart`、`tfbsShift`。**

56 个 exec 工具全部落在 FULL 内（exec ⊂ FULL）——这是好信号：验证投入集中在契约最完整的工具上。但 4 个"契约宣称 FULL 却从未跑过"的工具是 Agent 可见面的潜在承诺缺口（tool-describe 对它们显示 `readiness=FULL` 而无 verification 徽标）。

### 方案（最小）

在 `readiness_census()` 或 `version --json` 增加交叉字段：

```json
"readiness_x_verification": {"full_exec": 56, "full_not_exec": 4, "exec_not_full": 0,
                              "full_not_exec_names": ["gxfIdAppender","pafref","smart","tfbsShift"]}
```

并在 tool-readiness.md 头部加一行交叉摘要。成本 < 20 行，数据源现成。

## 三、GPT 全面审查 P2：基准测试（benchmarks）—— **属实缺失，P3，给最小方案**

### 现状核实

已有机制盘点：
- `scripts/e2e_nightly.sh`：11 条真实引擎 E2E 用例，断言退出码 + 产物非空——**这是冒烟，不是基准**：无固定输入指纹、无任务完成率/首次成功率/错误恢复率指标、无跨版本对比记录
- `examples/workflows/`（deg-pipeline/gxf-ops/phylogeny/synteny 4 个 YAML）+ `examples/fulltest/`：示例数据存在，但无自动评分
- 无任何记录"任务完成率/首次成功率"的脚本或报告（grep 全库零命中）

### 定级：P3

基准测试的价值在跨版本回归（"v1.5.4 比 v1.5.3 首次成功率升了还是降了"），属观测基建而非缺陷。当前 e2e_nightly 已覆盖最关键的 11 条路径，边际收益真实但不紧迫。

### 最小方案（不要铺开）

挑 2 个最高频工作流即可：
1. **volcano（DEG 火山图）**——expr 组最高频，examples/data/deg.txt 现成
2. **onesteptree 或 msy（共线性）**——tree/syn 组代表

固定输入 + 断言产物 + 记录三指标到 `test_reports/benchmark_<version>.json`：
```json
{"version":"1.5.4","cases":[{"id":"volcano_deg","first_try_ok":true,"retries":0,"duration_s":3.2}]}
```
复用 e2e_nightly 的 run_case 骨架 + 一个 JSON 落盘即可，约 50 行。**不做**：全 298 工具覆盖（投入产出比不成立）。
