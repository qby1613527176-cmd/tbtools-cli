## 二、发现

### 🔴 P1-1(GPT P1-A，独立实证确认): 继承路径 semantic_checked 被当前静态集合错误升级

**代码事实**(tests/test_conformance_verified.py):
- L308-327 继承分支(`_res != "pass"` 且有旧证据): `_exec_entries[_t]` 只写 6 字段，**不携带旧证据的 semantic_checked**(52f8b78 有意规整 details schema，合理)。
- L360-369 verified_tools 构建循环: 对 `_exec_entries` 全部条目(本次 pass **和继承**)统一 `"semantic_checked": _t in SEMANTIC_CHECKS`——用**当前**静态集合给继承证据贴标签。

**探针实证**(/tmp 隔离，monkeypatch 指纹/ROOT/结果，用后无仓库污染):
```
EXEC∩SEMANTIC = 11 工具(取 barplotter)
旧证据 semantic_checked=False + 本次 fail(继承) + 当前 SEMANTIC_CHECKS 含 barplotter
→ 最终报告 verified_tools.barplotter.semantic_checked = True  ❌ 错误升级确认
```

**危害路径**: 工具 X 在语义断言加入 SEMANTIC_CHECKS **之前**pass 过(证据语义=只验跑过+sha256)；之后 X 被加入 SEMANTIC_CHECKS；再之后某次运行 X fail → 继承旧证据 → 报告标 semantic_checked=true，但**该证据生命周期内内容级断言从未通过过一次**。与 F2「标签诚实性」设计意图直接冲突——机器可读层对 Agent 撒谎。爆炸半径窄(仅限"加入集合前生成的证据 + 后续 fail 继承"窗口)，但属证据完整性正确性 bug，定 P1。

**修复建议**(最小侵入):
1. `_exec_entries` 继承分支补一字段:`"semantic_checked": bool(_o.get("semantic_checked", False))`(details schema 规整可保留——此字段进 verified_tools 层用，details 里可带可不带，建议带以保持 map 字段集统一时同步修 guard 断言)；
2. verified_tools 循环改 `"semantic_checked": _exec_entries[_t].get("semantic_checked", _t in SEMANTIC_CHECKS)`——pass 路径条目无此键(由 pass 分支不写入，回退当前集合)或显式在 pass 分支写 `True if _t in SEMANTIC_CHECKS else False`。
3. **回归测试**(TestEvidenceWriteGuard 第 6 守卫): `test_old_evidence_fail_inherits_semantic_label`——旧证据 semantic_checked=false + 当前 SEMANTIC_CHECKS 含该工具(不得 patch 为空，改 patch 为含该工具的集合)+ 本次 fail → 断言最终 `verified_tools[_t]["semantic_checked"] is False`；对照组 pass → True。注意现有 `_build_with_results` 恒 patch `SEMANTIC_CHECKS=set()`(L709)，正好掩盖此 bug——新守卫需参数化该 patch。

### 🔴 P1-2(GPT P1-B，独立实证确认): CONFORMANCE_VERIFIED 由静态名单决定，无本次金链结果来源

**代码事实**:
- L250 `CONFORMANCE_VERIFIED = {"volcano"}` 静态集合；L371-393 升级判据仅要求 `_t in _verified_tools`(即 Tier2 pass 或继承)，**全程无金链(TestExecutableConformance.test_volcano_golden_chain, tests/test_conformance.py:48)结果引用**。
- tests/conftest.py hook 只收集 `TestTier2ExecutionVerified` 的 `tool` 参数化项；**不存在与 TIER2_RESULTS 同构的金链结果容器**(grep `TestExecutableConformance` 于 conftest/test_conformance_verified = 0 命中)。
- `_build_report_and_persist` 源码内 TIER2 引用仅 1 处(`_res = _TIER2_RESULTS.get(_t)`)，无 golden/Executable 引用。

**探针实证**: 隔离环境只注入 Tier2 `volcano: "pass"`(金链从未运行)→ 报告 `level=CONFORMANCE_VERIFIED`、`conformance_verified=["volcano"]` 照常写入。❌ 确认。

**实际影响路径**(与 GPT 判断一致，比我预判轻):
- **nightly writeback(生产回写路径)**: nightly-e2e.yml 先跑 `pytest tests/ -q` 全量(含金链，真实 JAR)+ pipefail——金链红则 job 死在 writeback 之前。**有前置保护，但仍是 incidental ordering**(同 job 早步)，与被修的 N7 时序问题同构：writeback 步本身 `pytest tests/test_conformance_verified.py` 单独运行时对金链零观测。
- **单独调用**(本机 `TBTOOLS_WRITE_REPORT=1 pytest tests/test_conformance_verified.py`): 无任何保护，volcano Tier2 pass(或**继承旧证据**)即写金链级——即使此时金链六步断言(sha256 比对/provenance/artifact_id)已坏。
- 继承路径叠加: volcano fail 继承旧证据时同样保 CONFORMANCE_VERIFIED 级，与 P1-1 同根。

**修复成本评估**(与 Tier2 同构):
1. conftest.py 增 `_CONF_CHAIN_RESULTS: dict` + hook 识别 `TestExecutableConformance::test_volcano_golden_chain` nodeid(非参数化，单 item)，三阶段终判复用现有逻辑 → ~20 行；

   总成本 ≈ 40 行 + 2 测试。**注意策略抉择**: 单独调用时金链结果恒缺失 → volcano 恒降级，报告会与现状漂移(只读校验 `_cur_conf == CONFORMANCE_VERIFIED` 会红)——需把只读校验名单比对同步改为「金链结果缺失时容忍静态名单」或要求 writeback 必须跑金链。建议后者(nightly writeback 命令加 `tests/test_conformance.py::TestExecutableConformance`)。

### P2-1: 守卫 `_build_with_results` 恒 patch `SEMANTIC_CHECKS=set()`，语义标签路径零覆盖

TestEvidenceWriteGuard 全部 5 测试在空 SEMANTIC_CHECKS 下跑(L709)——semantic_checked 恒 False，P1-1 这类标签升级 bug 结构上不可能被现有守卫捕获。修复 P1-1 时按上述方案参数化即可闭环，不单列修复项。

### P3-1: hook 三阶段边角——同一 tool 多 item 时按 tool 覆盖

`_TIER2_STAGES` 键是 nodeid，但 `TIER2_RESULTS[_tool]` 键是 tool 名；若未来同一 tool 出现第二个参数化 item(如多语料)，后 teardown 的 item 覆盖前者，「一过一败」可能记 pass。当前每 tool 恰好 1 item(parametrize 于 EXEC_VERIFIED 键)，无现实危害；建议在 hook 加 `_tool in TIER2_RESULTS and 新值为 fail → 不覆盖` 的保守合并，或注释明示假设。
