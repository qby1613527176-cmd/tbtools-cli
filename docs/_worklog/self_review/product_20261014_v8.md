## 二、GPT 发现独立核实

### 核实 1:工具可信度决策机制(GPT P0/P1)——**成立,定 P1**

GPT 称「证据体系只是统计表不参与决策」。独立核实三层:

1. **证据生产层(完好)**:tool-describe 的 verification_details 六字段齐全;README 第 26-27 行有四维显式映射(readiness/verification/semantic_checked/env_fingerprint 各司其职);agent-protocol 6.1 用 40+ 行讲透 env_fingerprint 爆破半径、verified_at vs last_passed_at 时间语义、CONFORMANCE 继承/降级规则。**证据本身是诚实、可读、带反观测语义的。**
2. **发现层(断裂)**:search hits 字典仅 `{name, group, kind, description}`(cli_top.py:1872 源码+实测双重确认);`_ranked` 评分 = 语义命中 60/全名 50/弱名 20/alias -30/kind-manual +10——**无 verification/readiness 权重项**(源码通读确认)。Agent 在 search 阶段看不到任何验证信号,排序也不偏向已验证工具。
3. **规划层(断裂)**:workflow.py `plan_from_goal` 的评分/置信因子(input_format_exact/capability_match 等)全文无 verification 因子;MCP `search`/`workflow_plan` 是 CLI 的薄代理,同源断裂。

结论:Agent 按文档管线 search→describe→validate→run 走时,只有**主动对每个候选调 describe** 才能拿到验证证据;多候选场景(如「画热图」命中 heatmap/efpHeat/layoutheatmap/multiEfp)无任何机制引导 Agent 选 EXECUTION_VERIFIED 的那个。证据体系确实是「统计表+单点查询」,未进决策回路。

**不定 P0 的理由**:不构成错误结果——DECLARED 工具本身可用,协议也未承诺「按验证强度推荐」;证据在 describe 层完整可查,属决策支持缺口而非正确性缺陷。

**最小方案(两选一并,成本均低)**:
- a. search hits 增加 `"verification"` 与 `"readiness"` 两字段(meta 数据源已在 `_ranked` 里加载,字典加两键即可)+ `_ranked` 对 CONFORMANCE/EXECUTION_VERIFIED 加小权重(如 +15/+10,不压倒语义 60 分);
- b. agent-protocol §6.1 末尾补一段「候选选择决策矩阵」:多候选时先 `tool-describe` 比 verification,同等级取 semantic_checked=true,env_fingerprint 失配时证据不可迁移。

### 核实 2:--threads 的 Agent 面影响(GPT P1)——**成立,实测复现,定 P1**

- **named-flag 工具(受益面,十二轮修复有效)**:muscle/kallisto/iqtree/findhomolog/findBestHomologyBatch/recipBlast——click 消费 `--threads` 后 cli_load.py:336 重新以 `--threads N` 追加,各 impl 自解析,链路通。bestid 另有缺省注入 4 的兜底(auto_commands.py:594)。
- **位置线程工具(受害面,实测)**:`parallelMD5Check <list> [threads]` 传 `--threads 2` → 追加的 `"--threads"` 落在 args[1] → 守卫响失败 `threads 须为数字: --threads` EC=2(**响失败不静默,是不幸中的万幸**);位置式 `… txt 2` 正常。
- **未实测但同构风险**:tfbsShift/mcscanxd/quickAnno 均为位置 `[threads]`,且**无数字守卫**——`--threads 8` 追加后字面落入 Java 位置槽(如 quickAnno 位置 4 = "--threads"),引擎侧行为未验证(大概率 NumberFormatException 或静默错解)。这三个是比 parallelMD5Check 更危险的一档:失败可能不响。
- **Agent 视角要害**:agent-protocol 与 MCP 都教 Agent 用公共 `--threads`(cli.py:61 还有 `--runtime-threads` 显式命名空间),但**没有任何文档区分 named/位置两种线程形态**——Agent 无法先知哪类工具该用哪种传法。

**修复后验收判据**(建议):
1. `parallelMD5Check list.txt --threads 8` 与 `parallelMD5Check list.txt 8` 行为全等;
2. quickAnno/mcscanxd/tfbsShift 传 `--threads 8` 时 8 落到正确位置槽(透传层按工具的线程形态白名单转换:位置形态 → 追加裸数字到线程槽位,而非 `--threads N`);
3. muscle `--threads 8` 引擎收到 `-threads 8`(十二轮修复不回归);
4. 位置式与 flag 式同传时显式报错或文档化优先级;
5. agent-protocol 补一句线程形态说明(或 tool-describe parameters 区标注 threads 形态)。

- 「README 入口」不成立——锚点块已是精简终态,保持。

下一轮建议优先级:P1-2 threads 位置形态白名单(有静默错解风险,先修)→ P1-1 search 决策字段(成本低收益大,随修)。
