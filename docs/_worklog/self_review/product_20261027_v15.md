## 🔴 审查一（GPT 审查二 P1）：Agent 模式反射限制 fail-open —— **属实，定级 P1**

### 代码实证（`tbtools_cli/runtime/java.py:381-408`）

`_security_check_generic()` 的安全意图（docstring 自陈）：`config.toml [security] allow_engine_reflection=false` 拒绝裸反射命令（generic 任意引擎类），且 Agent/MCP 模式（`TBTOOLS_AGENT_MODE=1`）**默认关闭**。

实际异常分支（java.py:403-404）：

```python
    except Exception:
        allow = True
```

### 异常路径分析（全部 fail-open）

| 异常场景 | 走向 | 与安全意图 |
|:--|:--|:--|
| `load_config()` 本身抛异常（TOML 解析失败、IO 错误、config 模块 import 失败） | `allow = True` → **放行** | ❌ 相反 |
| 配置存在但 `[security]` 段类型损坏（如 `sec.get` 抛 AttributeError） | `allow = True` → **放行** | ❌ 相反 |
| `agent.policy` 段读取异常 | 同上 | ❌ 相反 |
| 配置不存在 | 不抛异常，走默认 `allow_engine_reflection, True` → 放行（但 Agent 模式分支 `TBTOOLS_AGENT_MODE=1` 且 sec 无键 → `allow = False`，此路径正确） | ✅ 仅此一条正确 |

**结论**：只要 `load_config()` 或配置结构访问抛出**任何**异常，Agent 模式「默认关闭」的安全门即被绕过，退化为允许任意类反射。与安全意图（Agent 模式默认拒绝）完全相反，且无任何诊断输出告知"安全检查因故障被跳过"。

### 定级：P1（安全设计风险）

无人值守/MCP 场景正是配置损坏概率高（并发写、部署模板差异）且后果重（任意类执行）的场景。fail-open 使该安全门在最需要它的时刻失效。

### 修复方案

1. **Agent 模式 fail-closed**：`except Exception as e:` 分支中，若 `TBTOOLS_AGENT_MODE == "1"` → `allow = False`；否则（human CLI）保持 `allow = True` 兼容现状。
2. **结构化诊断**：fail 时向 stderr 输出 `⚠️ security config 读取异常(<type>: <msg>)，Agent 模式 fail-closed 拒绝`；`--json` 模式下应入结构化错误的 `details`。
3. 拒绝消息与现有 `🚫 engine reflection 被 config.toml ...` 区分来源（policy 拒绝 vs 故障拒绝），便于 Agent 归因。

### 回归测试设计

- `load_config` 抛异常（monkeypatch）+ `TBTOOLS_AGENT_MODE=1` → 必须拒绝（exit 5）
- 配置 `[security]` 段类型损坏 + Agent 模式 → 必须拒绝
- 显式 `allow_engine_reflection = false` → 拒绝（现有行为保）
- 显式 `allow_engine_reflection = true` + Agent 模式 → 放行（显式覆盖默认关）
- 无 `TBTOOLS_AGENT_MODE` + load_config 异常 → 放行（human CLI 兼容）+ stderr 有诊断

## 🟠 审查二（GPT 审查二 P2）：TB007 错误码落入通用 TB000 —— **属实，且 GPT 漏报一个同类，定级 P2**

### 代码实证

`errors.py:15-21` `ERROR_CODES` 注册了 `TB006_POLICY_DENIED` 与 `TB007_BRIDGE_COMPILE_FAILED`；
`errors.py:46-57` `ERROR_TIERS` 中**两者均无映射**；
`errors.py:62` `error_tier()` 缺映射 → `return ERROR_TIERS.get(code, ("TB000", "core"))`。

### 机器核验（探针输出）

```
TB007_BRIDGE_COMPILE_FAILED -> ('TB000', 'core')
TB006_POLICY_DENIED -> ('TB000', 'core')
ERROR_CODES 无分层映射: ['TB006_POLICY_DENIED', 'TB007_BRIDGE_COMPILE_FAILED']
ERROR_TIERS 多余键: []
```

### 影响

- `cli_top.py:1206-1207` 经 `error_tier(error["code"])` 转换后，**桥编译失败（exit 6）与 policy 拒绝（exit 5）在 Agent 结构化输出中 code 均为 TB000**，协议 exit code 6/5 语义丢失，Agent 无法编程区分「编译环境坏」与「安全策略拒绝」。
- **GPT 只报了 TB007_BRIDGE_COMPILE_FAILED，漏了 TB006_POLICY_DENIED**——而 TB006 恰是审查一 P1 的拒绝路径要用的码，两问题叠加：fail-open 修复后 Agent 收到 policy 拒绝仍拿到 TB000，归因链断裂。

### 定级：P2（不崩功能，但 Agent 错误契约语义失真）

### 修复方案

- `ERROR_TIERS` 补：`"TB007_BRIDGE_COMPILE_FAILED": ("TB202", "dependency")`（JDK/javac/JAR 缺失属依赖层）、`"TB006_POLICY_DENIED": ("TB401", "agent")`（policy 属 agent 分层，TB400-499 段当前为空，正好启用）。
- **一致性测试**：参数化遍历 `ERROR_CODES` 全键，断言每键在 `ERROR_TIERS` 有映射且分层号段与类别语义一致（exit 5→agent / exit 6→dependency），防再漏。

## 🟠 审查三（GPT 审查二架构建议 3）：测试数字诚实性 —— **属实，且比 GPT 说的更陈旧，定级 P3**

### 实证（tests/test_agent_contract.py）

- 模块 docstring（:3）：「对 **8 个 FULL 工具**逐一验证」。
- 实际：`FULL_TOOLS` 已改为**动态取**（:27，注释自陈「FULL 判定修正后 8→59」），当前 `version --json` 显示 `agent_ready_full: 60`——discover/describe/validate 参数化（:55/:66/:82）跑的是 60 个。
- 但真实 JAR 集成执行（:102）`@pytest.mark.parametrize("tool", ["volcano", "dehist", "hclust", "dualsyn"])` 只覆盖 **4 个**；`RUN_CASES`（:30-43）虽有 8 键（含 mcscanx/iqtree/genestructure/heatmap），其中 4 个从未被参数化使用（死键）。

即：docstring 说 8、动态集是 60、集成跑 4、RUN_CASES 备了 8 只用 4——三个数字互不一致。GPT 的指控成立且实际情况更乱。

### 定级：P3（不影响测试正确性，但误导维护者以为 8 个 FULL 已全链路机器验证）

### 修正文案方案

docstring 改为如实描述分层验证：「discover/describe/validate 对**动态 FULL 集**（当前 60）参数化；真实 JAR 集成 run/artifact/provenance 仅覆盖 4 个代表工具（volcano/dehist/hclust/dualsyn，跨 expr/syn 两组）」；`RUN_CASES` 删除未被参数化的 4 个死键，或为后续扩展加注释说明用途。
