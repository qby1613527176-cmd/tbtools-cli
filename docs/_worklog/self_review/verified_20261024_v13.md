## P1 — validate_artifact() 检查强度不足（executor.py L440-479）

### 逐格式对照表

| 格式 | 当前检查 | GPT 指控 | 探针实证 |
|:--|:--|:--|:--|
| FASTA (.fa/.fasta/.aln/.faa/.fna) | 开头 `>` 且计数 ≥1 | 只查开头 `>` | `>seq1\n\x00\x01\x02garbage-not-ACGT!@#\n>seq2\n` → **(True, 'fasta seqs=2')** ❌ |
| GFF (.gff/.gff3/.gtf) | head 含 `##gff-version` 或 `\tgene\t`/`\tmRNA\t`/`\tCDS\t` | 只查关键词 | `junk\tgene\tjunk\n`（1 行 3 列，非法 GFF）→ **(True, 'gff features present')** ❌ |
| Newick (.nwk/.tree) | 含 `(` 和 `)` 且 strip 后以 `;` 结尾 | 只查括号+`;` | `((A,B);\n`（括号 2 开 1 闭，不平衡）→ **(True, 'newick parseable')** ❌ |
| TSV/CSV/TXT | ≥1 个非空行 | 只查非空行 | `zzz-no-columns\n` → **(True, 'rows=1')** ❌ |
| SVG | head 含 `<svg` 或 `<?xml` | 只查 `<svg`/`<?xml` | `<?xml version='1.0'?><svg><rect\n`（XML 截断）→ **(True, 'svg xml valid')** ❌ |

GPT 指控逐条属实。另注意：消息文本有夸大误导——SVG 分支说 "svg xml valid"、Newick 说 "parseable"，实际都没 parse。但指控本身正确。

### 验证结果对工作流的影响（executor.py L229-235）

```python
if step_ok and out and os.path.isfile(out):
    _vok, _vmsg = validate_artifact(out)
    if not _vok:
        _vwarn = f"output validation failed: {_vmsg}"
        step_ok = False
```

验证失败 → `step_ok=False` → 步骤 status="failed" → 工作流 fail-fast 阻断下游。即验证是**有实权的最后防线**，但其浅层检查使该防线对「结构损坏但头部正常」的产物形同虚设。⚠️ 反向风险同样存在：若贸然加深检查，假阴性会误杀正常步骤阻断整条工作流——分层方案必须注意此点。

### 修复方案（三级验证分层，最小实现路径）

明确层级边界（采纳 GPT 自己的告诫「格式解析通过 ≠ 生物学正确」）：

```
L0 exists      : 文件存在 + 非空（现状对无 parser 扩展名的行为）
L1 parse_valid : 结构可解析（当前浅层检查的强化版）
L2 semantic_valid: 生物学语义合理（序列字符集/坐标范围/树 taxa 数等）——本轮不做
```

最小实现（只动 validate_artifact 函数体，签名不变，约 +40 行）：

- **FASTA (L1)**：逐 record 迭代——`>` 头后必须跟 ≥1 条非空序列行；序列行字符集 ⊆ IUPAC + 空白 + `-`（比对）。拒：头后无序列、序列行含控制字符。~12 行。
- **Newick (L1)**：括号配平计数（遇 `(` +1、`)` -1，过程中不为负、终值为 0）+ 以 `;` 结尾。拒：不平衡。~6 行。完整递归下降 parse 属 L1.5，可选。
- **GFF (L1)**：非注释非空行必须 ≥9 列（tab 分隔）或匹配 GTF 属性结构；`##gff-version` 行若存在须为首个非空行。拒：`junk\tgene\tjunk`（3 列）。~8 行。
- **TSV (L1)**：≥2 个非空行 且 首两行列数一致（表结构最低要求）。当前 `rows>=1` 过松。~4 行。
- **SVG (L1)**：`xml.etree.ElementTree.parse` 整个文件（不止 head）——拒截断 XML。~3 行（try/except）。
- **head 读取量**：FASTA/Newick 用 head 足够（结构错误通常前 8KB 可见），GFF/TSV 同样；SVG 必须全文 parse（截断在尾部）。
- **L2 边界声明**：序列是否真是该物种、树分支长度是否合理、GFF 坐标是否在染色体范围内——属 semantic_valid，本函数**不做**，由下游工具/用户判断。文档字符串中写明。

回归测试：上述 5 个探针文件转 tests/ fixtures + 5 个正例，断言损坏全拒、正常全过。

## P2 — fmts.index(f) 重复格式索引风险（workflow.py L628-629）

```python
fuzzy = sum(1 for f in fmts if f and f != "relation" and f not in
            [i.format.lower() for i in (specs[chain[fmts.index(f) + 1]].inputs or [])])
```

### 探针实证（复刻表达式，双向错位均复现）

| 场景 | chain / fmts | 契约事实 | 当前实现 | 正确值 |
|:--|:--|:--|:--|:--|
| 漏罚 | [A,B,C] / ["fasta","fasta"] | B 收 fasta，C 只收 nwk（第 2 条边实为模糊） | fuzzy=0（两次都查 B） | fuzzy=1 |
| 重罚 | [A,B,C] / ["fasta","fasta"] | B 只收 nwk，C 收 fasta | fuzzy=2（B 被计 2 次，C 0 次） | fuzzy=1 |

`fmts.index(f)` 对重复格式恒返回首次出现位置，后边兼容性永远拿 `chain[first+1]` 的输入契约做比较——漏罚与重复罚双向都可能。重复格式边在真实契约图中完全可能（fasta→fasta 透传链、多步 fasta 处理）。

**与 recipe_* 的交互**：十七轮后 fmts 可含 `"recipe_validated"` / `"recipe_unvalidated"` 字符串——它们 truthy、`!= "relation"`、且不在任何工具 input format 列表中 → **每条 recipe 边被额外计 1 次 fuzzy 罚（-0.05）**。这可能是未预期副作用（recipe 种子奖励与 fuzzy 罚同时出现），属次级观察，建议同一修复中把 `f.startswith("recipe_")` 也排除出 fuzzy 统计。

### 修复方案

```python
fuzzy = sum(1 for _i, f in enumerate(fmts)
            if f and f != "relation"
            and not (isinstance(f, str) and f.startswith("recipe_"))
            and f not in [i.format.lower() for i in (specs[chain[_i + 1]].inputs or [])])
```

回归测试设计：
1. 构造 mock specs：A→B→C 链，两条边同格式 "fasta"，C 不接受 fasta → 断言 fuzzy=1、score 含 -0.05（修前 fuzzy=0）。
2. 反向：B 不接受、C 接受 → 断言 fuzzy=1（修前 fuzzy=2）。
3. recipe 链：fmts=["recipe_validated","fasta"] → 断言 recipe 边不计 fuzzy。
4. 边界：单步链（fmts=[]）不报错；f=None 边被跳过（现有 `f and` 守卫保留）。
