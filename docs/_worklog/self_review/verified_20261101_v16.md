## 发现

### 🔴 P1-1: 大文件摘要「算了没比」——GPT 两文共同 P1,**属实**

**代码证据**(runtime/java.py):
- L219-230 快照阶段:COW+copy2 均失败时计算 `sha1(头4KB+尾4KB)` 存入第五字段 `_digest`,注释明确承诺「verify_and_restore 无备份时比对摘要检测改写」。
- L243-268 `verify_and_restore()`:无备份分支(backup=None)只比较 `(getsize, getmtime)` 元组——`_digest` 被解包(L250)后**再未被引用**。注释承诺与实现再次漂移(与二十轮修的「注释声称 hash 但没存」是同族问题的下半段:存了但不比)。

**探针实证**(/tmp/probe_sr22/probe1_digest.py):
构造 20MB 文件 → 快照 `[path, None, size, mtime, digest]` → 改写头 4KB 内容(同尺寸)+ `os.utime` 恢复 mtime → `verify_and_restore` 返回 `[]`。**改写完全漏检**。

**影响**: 磁盘满/权限导致 COW+copy2 双失败的场景下,引擎对大输入的同尺寸改写(如注释漂移类原地编辑)静默不可见,且无法恢复——快照机制在该分支形同虚设。

**方案**:
1. 头尾采样摘要提取为公共函数 `_sample_digest(path, size)`(快照/验证共用,防两处采样逻辑漂移);
2. 无备份分支:size/mtime 变了 → `modified-no-backup`;size/mtime 未变但 `_digest` 非空且重算不等 → 同样报 `modified-no-backup`(无法恢复,只报告);
3. 测试:构造「内容变但 size+mtime 不变」场景(utime 恢复),断言 problems 含 modified-no-backup。

### 🟠 P2-2: 状态文件锁 fail-open + 终态不走锁——GPT 两文共同 P2,**属实**

**代码证据**(executor.py):
- `_merge_state_step()` L84-94:`flock`/`locking` 获取抛异常 → `except Exception: pass` → **继续无锁执行读-改-写**,无任何告警/返回值变化(锁失败与锁成功从外部不可区分)。
- `run()` 终态写入(L499/L503):`_save_state(workdir, {...status: failed/succeeded...})` **直接调用,不经过 `_merge_state_step` 的锁**——跨进程共享 workdir 时,终态写可覆盖另一进程刚 merge 的步骤列表。
- 附带确认:tests/test_parallel_conformance.py L268 `assert len(state["steps"]) > 0`——二十一轮注释自称修复并发丢步骤,但测试仍只断言非空,丢步骤可通过(GPT 所指测试弱化属实)。

**探针实证**(/tmp/probe_sr22/probe3_lock.py):
- 3a:patch `fcntl.flock` 抛 OSError → `_merge_state_step` 返回 `None`(无警告)且状态**正常写入**——fail-open 静默实证。
- 3b:子进程持排他锁期间,`_save_state` 0.00s 立即完成——终态写完全绕过锁,不对称实证。

**风险评估**: flock 获取失败在常规本地 fs 上概率极低(LOCK_EX 缺省阻塞而非失败,失败需 NFS/只读 fs 等异常),故 3a 实际触发率低但一旦发生即静默丢保护;3b 是**结构性**缺口(不是概率问题)——跨进程终态覆盖必然无保护,只是同 workdir 多进程并发场景本身少见,维持 P2 定级合理。

**方案**:
1. 锁获取失败 → 返回结构化 `PERSISTENCE_WARNING: lock unavailable`(与现有落盘失败告警同通道),至少 stderr 可见;
2. 终态 `_save_state` 走同一把锁(提取 `_with_state_lock(workdir, fn)` 公共上下文,merge/终态共用);
3. 并发测试强化:`test_concurrent_merges_no_lost` 断言 `len(steps)==20`(全部保留),不只非空。
