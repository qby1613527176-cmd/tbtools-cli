## 二、GPT P2 核实：恒真断言 + 不触达生产代码的测试 —— **属实，维持 P2**

### 2.1 证据（逐条定位）

**① `or True` 恒真断言 —— tests/test_semantic_unification.py L46-49**

```python
def test_output_formats_unified(self):
    ...
    if sp.output_slots and sp.outputs:
        assert sp.output_slots[0].format == sp.outputs[0] or True  # slot 优先
```

`X or True` 恒为 True，该断言对任何输入都通过——**数学上不可能失败**。注释「slot 优先」表明作者本意是表达「不一致时以 slot 为准」的语义说明，但写成了断言，等于在测试报告里虚增一个永远绿的检查点。

**② 只构造对象不调生产代码 —— 同文件 L53-56**

```python
def test_overlay_outputs_syncs_slots(self):
    from tbtools_cli.command_spec import OutputSpec
    slots = [OutputSpec(name="svg", format="svg")]
    assert slots[0].format == "svg"
```

构造一个 dataclass 实例然后读回刚写入的字段——断言的是 Python 对象语义本身，**与 tbtools-cli 任何一行生产代码无关**。生产代码全删，此测试照绿。注释声称验证「overlay 重建 output_slots（评审 #94 P0-1）」，但实际没有调用 overlay 路径。

**③ 扩展扫描发现的同类模式（GPT 未点名，本轮补充）**

- **tests/test_semantic_unification.py TestF `test_yaml_output_slots_preserved`（L110-123）**：在测试体内**手工重写一遍** overlay 分支逻辑（`if "output_slots" in c: ... else: ...`），再断言自己刚写的结果。断言为真只证明「我抄的逻辑能跑」，不证明 `tbtools_cli/command_spec.py` 里的真实 overlay 代码如此行为——生产代码改了分支条件，此测试无感知。与 ② 同病：仿真代替触达。
- **tests/rpc_regression_linux/run_p14.py L257**：`sum(1 for r in results if r[1]=='基线通过' or True)` —— 统计行里的 `or True`，使「基线命令可跑通」计数恒等于总数。不是 assert，但同样是恒真条件污染报告口径。P3。

**全 tests/ 目录扫描**（`grep -rn "or True\|assert True\|and False"`）：除上述两处外**无其他命中**。`assert True` 零命中。问题面收敛，不是系统性陋习。

### 2.2 负例验证（本轮实跑证明测试失灵）

```python
# 人为破坏：slot.format="BROKEN" vs outputs=["fasta"]（不一致）
sp.output_slots = [FakeSlot(format="BROKEN")]; sp.outputs = ["fasta"]
assert sp.output_slots[0].format == sp.outputs[0] or True   # 原断言 → 依然 PASS（失灵证实）
assert sp.output_slots[0].format == sp.outputs[0]           # 修复版 → AssertionError ✓（能抓到）
```

实跑输出：原断言在数据已破坏时 PASS，修复版正确 AssertionError。**GPT 判断成立**。

### 2.3 影响评估

- 危险不在这两行本身，而在**测试报告的膨胀信号**：20/20 绿的语义统一测试里有 2-3 个是永绿或空转，审阅者（包括 GPT 评审和自己）会把「测试全绿」误读为「语义一致性被验证过」。
- 当前真实保护来自同文件的 TestF `test_production_slots_semantic_intact` / `test_outputs_projected_from_slots`（这两个**确实**调 `build_command_specs()` 并对 4 个真实命令断言）——即生产面未裸奔，但报告口径失真。

### 2.4 修复方案（v1.5.8 候选，P2）

1. L49：去掉 `or True`，改为语义正确的真实断言——「slot 优先」的真实不变量是 **`sp.output_formats == [o.format for o in sp.output_slots]`**（即 TestF 已有投影断言的通用化），或显式 `if sp.output_slots: assert sp.outputs == [o.format for o in sp.output_slots]`。
2. `test_overlay_outputs_syncs_slots`：改为调用真实 overlay 路径——构造一个带 `output_slots` 的最小 YAML 字典走 `build_command_specs` 的 overlay 合并入口（或抽出该函数单测），断言 overlay 后 slot 语义存活；若 overlay 逻辑不可独立调用，则**删除此测试**（空转测试 < 无测试，前者误导）。
3. `test_yaml_output_slots_preserved`：同样改为触达生产 overlay 代码；测试体内不得复制生产分支逻辑（复制即漂移源）。
4. run_p14.py L257：`or True` 删除，计数改 `sum(1 for r in results if r[1]=='基线通过')`。
5. 负例测试设计（防回归）：新增一个 mutation 风格测试，**故意**在 monkeypatch 后制造 slots/outputs 不一致，断言修复后的检查抛 AssertionError——即对测试本身做负例，本轮 §2.2 的脚本可直接固化为 `test_slot_projection_assertion_is_live`。

## 三、GPT 增量建议核实：validate_artifact 测试矩阵 —— **缺口属实且比 GPT 说的更大**

### 3.1 现状核实

- 生产代码：`tbtools_cli/executor.py` L440 `validate_artifact(path)`，支持格式分发：fasta 系 / gff 系 / nwk·tree / tsv·csv·txt / svg / 压缩层剥离（.gz/.bgz/.bz2，v1.5.7 十八轮修复点）/ 兜底 `exists(ext, no parser)` → **默认 (True, ...)**。
- **测试覆盖：`grep -rn "validate_artifact" tests/` 零命中**。全 tests/ 无任何直接单测。唯一沾边的是 `tests/test_dx_quality.py` L67 的 `tool-validate volcano /nonexistent.tsv --json` CLI 冒烟——只验证「不崩」，断言语义为 `rc==0 or "valid" in stdout`（又是一个 `or` 宽容断言，对不存在文件两种结果都接受）。
- 即：**十八轮 P1 的核心修复（解析级校验 + 压缩层剥离）是零测试保护的**。v1.5.7 的生产代码变更没有任何回归测试锁定，下一轮重构可以静默退化回「exists 即通过」。

### 3.2 「不支持格式应报未校验」行为变更评估

当前签名 `-> tuple[bool, str]` 是二态：有效/无效 + 消息。`exists(ext, no parser)` 返回 `(True, ...)` 把「没校验」谎报为「校验通过」——这是**语义错误**，GPT 建议正确。但改为三态是破坏性变更：

- 影响面：`executor.py` L231 调用点（`ec==0 后产物校验`，三态中「未校验」应→警告而非失败）；`cli_top.py` L1657 `tool-validate`（输出 JSON 需新增 `status: "unchecked"` 字段，消费方是 Agent——协议变更要同步 ai/ manifest 与文档）；`workflow.py` L43 re-export。
- 建议形状：`tuple[Literal["valid","invalid","unchecked"], str]` 或 `(bool|None, str)`。**P2**——不改变默认行为前，至少先把消息从 `exists(...)` 改为 `unchecked(...)` 并在 tool-validate JSON 中透出，让下游能区分。

### 3.3 测试矩阵设计（最小可行集，v1.5.8）

格式 × 样本形态，每格一个用例（tmp_path 构造，无需 JAR，纯单测）：

| 格式 | 有效 | 截断/损坏 | 空文件 | 错误内容 | .gz | .bgz | .bz2 |
|:--|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| fasta (.fa) | ✓ | 半行 header | ✓ | 纯数字 | ✓ | ✓ | ✓ |
| gff (.gff3) | ✓ | 无 `##gff-version` 且无 feature | ✓ | fasta 内容冒充 | ✓ | — | ✓ |
| newick (.nwk) | ✓ | 缺尾 `;` / 括号不配对 | ✓ | 纯文本 | ✓ | — | — |
| tsv (.tsv) | ✓ | — | ✓（应 invalid: table empty） | — | ✓ | — | — |
| svg (.svg) | ✓ | 无 `<svg`/`<?xml` | ✓ | html 冒充 | — | — | — |
| 未知 (.xyz) | 应 **unchecked**（三态后）/ 当前记录默认 True 的行为钉扎 | — | — | — | .xyz.gz | — | — |
| 不存在路径 | invalid (file missing) | — | — | — | — | — | — |

关键交叉用例（十八轮修复的回归钉扎，**最高优先级**）：`bad.fa.gz`（gzip 包裹的坏 fasta → 必须 invalid）、`good.fa.bz2`、截断 gzip（`gzip.open` 抛异常 → 走 `parse error` 分支 → invalid）。最小可行集 ≈ 20 用例，一个参数化测试函数即可装下。

## 四、GPT P2 建议核实：CI 报告分层 —— **部分已做，缺口在「显式分层计数」，定 P3 合理**

### 4.1 现状（精读 test.yml / nightly-e2e.yml / onboarding-e2e.yml）

已有分层事实：
- test.yml 注释层面分了 **L1（静态/lint，无 JAR）/ L1.5（无 JAR CLI 冒烟）**，且 `Run full pytest suite` 步已用 `-rfs` 报告 skip 原因，并显式 echo 说明「EXECUTION_VERIFIED 在无 JAR 下 skip，口径见 counts.md」——这是上一轮自审（评审 #115 E4 + gate P1-4）的成果，**GPT 建议的一半已经落地**。
- nightly-e2e.yml 物理分层：`Nightly E2E`（真实 JAR 出图）/ `pytest (wrapper layer)` / `Execution verification refresh`（conformance_verified + writeback）/ TTL gate / render——「真实 JAR 集成」与「生物学语义验证」已是独立 step，各自失败各自红。
- onboarding-e2e.yml 为独立工作流（Agent 接入路径），分层职责清晰。

### 4.2 缺口

- 没有**一处汇总**给出三层各自的「实际运行数 / 跳过数 / 失败数」。`-rfs` 只列 skip 原因明细，pytest 尾行汇总被 `tail -40`/`tail -1` 截断后，三层各自的数字要靠人眼从日志拼。CI 无 JUnit XML 上传 / 无 GitHub Step Summary（`$GITHUB_STEP_SUMMARY`）分层表。
- 无 JAR 单元 vs 真实 JAR 集成的**计数分离**依赖 marker（`@pytest.mark.integration`）隐式约定，CI 命令行没有 `-m "not integration"` / `-m integration` 的显式分流——nightly 里 `pytest tests/ -q`（wrapper 层）其实仍会把 integration 用例再跑一遍（有 JAR 时不再 skip），与 conformance_verified 步存在口径重叠。

### 4.3 建议（P3）

1. test.yml 全量 pytest 步改两层显式跑：`pytest -m "not integration" -q --junitxml=...` 与（有 JAR 时）`pytest -m integration -q`，各写一行 `echo "## 层X: ran/skip/fail" >> $GITHUB_STEP_SUMMARY`。
2. nightly 的 wrapper pytest 加 `-m "not integration"`，消除与 verification refresh 的重叠口径。
3. 成本极低（纯 YAML），收益是审阅者一眼看到三层各自的真实数字。**定级 P3 同意**。
