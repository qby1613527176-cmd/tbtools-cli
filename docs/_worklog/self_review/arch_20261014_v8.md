## 二、探针实录(独立核实,非照抄)

### 探针①: env 空条目加载端五场景(mock json.load 注入合成报告,volcano 用真实 contract_fp)

| 场景 | 证据条目 | 当前环境 | 加载结果 |
|:--|:--|:--|:--|
| A | `env_fingerprint=""`(写入端"置空"产物) | 无 JAR | **保留 EXEC**(跳过 env 比对) |
| B | env 字段缺失 | 无 JAR | **保留 EXEC** |
| C | contract_fingerprint 缺失 | — | **discard**(对照组,缺 fp 即 discard 生效) |
| D' | `env_fingerprint="deadbeef_stale"`(非空但不匹配) | TBTOOLS_JAR=存在 jar | **discard**(env 比对机制本身工作正常) |
| E | `env_fingerprint=""` + `prev_env_fingerprint="deadbeef"` | TBTOOLS_JAR=存在 jar | **保留 EXEC** ← 漂移点:写入端已声明"身份不可确认",加载端在 env 可观测时仍放行 |

结论: command_spec.py L1194 `if _old_env:` 对空串 falsy 短路 → env 侧**没有**与 contract 侧 `elif not _old_fp: discard` 对称的"缺 fp 即 discard"不变量。D' 证明比对机制健全,缺陷纯粹是空值支路语义。

### 探针②: 位置线程工具 + 十二轮透传修复

cli_load.py L336-337 无条件 `args.extend(["--threads", str(threads)])`(bash 兜底 L347-348 同)。对 parallelMD5Check(`<md5_list.txt> [threads]`,args[1] 必须是数字):透传后 `args[1]="--threads"` → isdigit  False → ec=2 **确定性破坏**。同形态受害面:tfbsShift(`[threads]` 位置 3)、mcscanxd(`[threads]` 位置 6,且后续 [blastHits] [evalue] 整体错位)、quickAnno(`[threads]` 位置 4)——三者无 isdigit 守卫,字面量 "--threads" 将进 Java 桥 argv 错位槽,大概率 NumberFormatException 或静默参数漂移。另:静态 cli.py 80 命令函数体 threads 消费行数仍为 **0**(与 v7 探针同法复测),v1.5.0 只修了动态通道;且 cli.py L387 注释明示 oneStepTree 引擎"没有 --threads"——**无条件透传对"不支持线程"的工具同样是错的方向**(引擎收到未知 flag)。

### 探针③: 契约表达缺口

CommandSpec 字段(name/group/kind/class_name/runner/xmx/doc/status/aliases/alias_of/inputs/outputs/capabilities/dependencies/relations/parameters/output_slots)中唯一候选 `parameters`(ParamSpec)对上述六工具全为空;InvocationSpec.layout grammar 有 flag/literal/input/output 四类 token,可表达位置形态但**无一处为线程参数实例化**。透传层(cli_load)无任何 per-tool 形态知识,纯一刀切。

## 三、发现

### P1-1 🔴 env 写入端置空 vs 加载端空跳过——两端语义不对称(GPT 评价**属实**,且发现一处注释与代码漂移)

- **写入端**(test_conformance_verified.py L431-447): 金链 pass 但 env 不可确认(无 JAR)→ `env_fingerprint=""` + `prev_env_fingerprint` 留档。语义 = "本次观测不绑定任何 env 身份"。
- **加载端**(command_spec.py L1194): `if _old_env:` 空串跳过 → 证据继续携带 EXECUTION/CONFORMANCE 标签,**即使当前环境已有 JAR、env 完全可观测**(探针 E)。
- **架构面判定**: 证据身份不变量"空 env = 身份不可确认"只在写入端成立;加载端把它解释为"无需检查"。contract 侧两端对齐(缺即 discard),env 侧两端漂移——**保守置空(写) vs 宽松跳过(读)**。
- **加重项(GPT 未指出)**: 写入端 L431-433 注释自称"置空后 _fp_same 四字段非空要求自动保守降级(**与加载端'缺 fp 即 discard'不变量对齐**)"——该括号断言为假:加载端的 discard 不变量只覆盖 contract_fingerprint,不覆盖 env_fingerprint。注释把未实现的对齐当作已对齐,会误导下一轮审计。
- **方案**: 加载端改为"身份可证时必证"——`if _old_env:` 支路前加:当前 env 可观测(TBTOOLS_JAR 置位且文件存在)且 `_old_env` 为空 → discard(证据无 env 身份,无法证明同源);当前 env 不可观测 → 保留(与写入端"无 JAR 不刷新"对称,CI 无引擎环境不漂移)。此方案下写入端无需改动,prev_env_fingerprint 继续承担审计留档;备选更严方案"空 env 一律 discard"会杀死 CI 写入的全部证据,不可取。次选:prev_env_fingerprint 作为 last-known-good 与当前 env 比对,不匹配降级为软警告——但弱于主方案,仅建议在需要保留"换机后历史标签可读"场景时叠加。
- **与十二轮 prev_env_fingerprint 衔接**: prev_ 字段当前只写不读(与十一轮 env_fp 曾"只写不查"同构)——主方案落地后 prev_ 仍为纯审计;建议同时补一条守卫:env="" 条目必须携带 prev_(除非首写即无 JAR),防置空路径丢审计链。

### P1-2 🔴 threads 参数形态未契约化,一刀切透传双向破坏(GPT 评价**属实**,破坏面比 GPT 描述更宽)

- **现状**: 十二轮修复(cli_load L336-337/L347-348)把"吞没"改成"无条件 `--threads N` 透传"——对 named-flag 工具(muscle/kallisto/findhomolog)正确;对位置线程工具(parallelMD5Check/tfbsShift/mcscanxd/quickAnno)**确定性破坏**(探针②,ec=2 或 argv 错位);对不支持线程的引擎(静态侧 oneStepTree 类)方向性错误。
- **架构面判定**: 线程参数形态(named_flag / positional / unsupported)是引擎 argv 布局契约的一部分,与 InvocationSpec.named_flags/layout 同层,理应在 CommandSpec 表达;现在它只散落在 auto_commands docstring 自然语言里(`[threads]` vs `[--threads N]`),机器不可读 → 透传层无法分派。这是 v7 已提的 runtime_params 长期分离项,十二轮止血(impl+bash 双路径)把"静默吞没"换成了"部分场景确定性报错",**位置工具从"降级默认"变成"直接坏掉"——对该子集是回退而非修复**。
- **方案**:
  1. CommandSpec 增契约字段(建议挂在 ParamSpec 或 CommandSpec 顶层):`thread_form: "named_flag" | "positional" | "unsupported"`,positional 时附 `thread_position: int`(相对已声明位置参数序)。四位置工具 + named 工具在 auto_commands/command_spec 注册处显式声明,缺省 = `unsupported`(保守:宁可显式拒绝不可静默错传)。
  2. cli_load 透传分派:`named_flag` → `["--threads", N]`(kallisto 类 `-t` 方言由 impl 内部翻译,维持现状);`positional` → 在声明槽位插入 `str(N)`(槽位后还有可选参数时仅当用户显式给线程才插入,其后槽位保持缺省);`unsupported` → 显式报错 exit 2("该工具引擎不支持线程参数"),取代静默丢弃。
  3. bash tbplot.sh 兜底路径同一分派函数,禁止双份逻辑再漂移。
- **回归测试设计**(表驱动,新 TestThreadsFormDispatch):
  ① parallelMD5Check `--threads 8` → mock run_java 捕获 jargs,断言引擎 argv = `[lst, "8"]` 且无 "--threads" 字面量;
  ② muscle `--threads 8` → 断言 extra 含 `-threads 8`;
  ③ unsupported 工具 `--threads 8` → ec=2 且 stderr 含"不支持线程";
  ④ 不传 threads → 四工具 argv 与 v1.4.x 基线逐 token 相等(防分派函数污染默认路径);
  ⑤ bash 兜底路径用 mock shutil.which/subprocess.run 断言对称分派。

## 四、总体结论

**有条件通过(0 P0 / 2 P1 / 1 P2 / 3 P3)。** GPT 两份评价的三个架构面全部独立核实属实,且两处比 GPT 描述更重:① env 不对称不仅是"两端语义漂移",还伴随写入端注释把未实现的加载端对齐**声称为已对齐**(假不变量断言,审计误导级);② threads 一刀切透传对位置线程四工具是**从降级到破坏的回退**(parallelMD5Check 实测 ec=2),且对不支持线程的引擎方向性错误——十二轮止血只覆盖了 named-flag 形态。常规复核全绿(census 80 三源 / details 字段组合唯一 / 守卫 15/15 / mypy 27 文件 / compileall / _record_stage 双容器 / sorted listdir / ctime 缓存键)。两个 P1 均有不改证据合法性边界的落地方案(加载端"可证必证"+ 契约字段+透传分派),建议作为十四轮必修项;P2-1 的 CATEGORY_MAP 六处直读清理可同轮顺带完成。
