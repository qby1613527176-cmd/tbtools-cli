## 🔴 核实一：GPT 审查二 P1「三类门禁（A/B/C）必须固定 + 发布报告明示」

**结论：部分属实 → 判 P2（不是 P1）。**

### 现状核实
- **A 类（无 JAR 基础自动化）已实质存在**：test.yml = ruff / shellcheck / bash -n / mypy / coverage(fail_under=35) / pytest 全量 / 无 jar CLI 冒烟 / `gen_metadata.py --check` 元数据一致性；windows 腿跨平台冒烟。
- **B 类（真实引擎集成）已实质存在**：nightly-e2e（每日 01:00 UTC，fetch-jar → e2e_nightly.sh → conformance 执行验证全量 → writeback PR + TTL 严格门禁）；onboarding-e2e（每周一，fetch-jar → doctor 全绿 → 8 图 + 代表命令真实出图断言 ≥5 非零产物）。
- **C 类（语义验证）已实质存在但薄**：counts 显示 `semantic_checked: 11`、`conformance_verified: 1` —— 语义层覆盖仅 11 命令，是三分类中最弱的一档。
- **发布报告未区分三类**：`release_pypi.py` 门禁预检只跑 A 类子集（`gen_metadata --check` + ruff + mypy）+ wheel 冒烟 + PyPI 拉取验证；**没有任何"四态表/三分类执行情况"输出**，发布时 B/C 类状态完全依赖"nightly 最近绿没绿"的人为记忆。全仓 grep「发布报告/release report」无命中。

### 判定理由
三类门禁**已隐式分层且各自有硬失败通道**，缺的只是：① 三分类没有命名/文档化（A/B/C 边界靠读 YAML 推断）；② 发布脚本不汇总 B/C 最近状态（nightly writeback PR merge 与否、semantic_checked 计数）。这是"可见性/纪律"缺口而非"门禁缺失"，故 P2。

### 方案（若采纳）
1. 在 `docs/`（或 CI 注释块）固定三分类定义：A=test.yml（无 JAR）/ B=nightly+onboarding（真实 JAR）/ C=conformance 语义层。
2. `release_pypi.py` 预检末尾打印四态表（PASS/SKIP/FAIL/STALE）：A 行取本次实跑；B 行取 `gh run list nightly-e2e` 最近结论或 verification_report `verified_at` 保鲜度；C 行取 counts `semantic_checked/conformance_verified` 计数 + TTL。STALE 不阻断但显式告警。
3. 仅"文档化 + 发布输出"即可闭环，不需要新 CI 腿。

## 🔴 核实二：GPT 审查一 P1「Bash fallback 绕过 thread_style 三态分派」

**结论：代码级违规属实，但当前不可达 → 降判 P2。**

### 代码事实（cli_load.py L334-376）
impl 路径有完整三态分派（unsupported 警告不注入 / positional 追加位置值 / named_flag 注 `--threads N`，含 plot-runner 降级 unsupported）；**bash fallback 分支（impl=None 时）无条件 `bash_args.extend(["--threads", str(threads)])`**，三态规则被整体绕过。代码对照属实。

### 可达性探针（本轮关键增量，GPT 未做）
1. `build_command_specs()` 中非 named_flag 的 spec 仅 4 个（parallelMD5Check/tfbsShift/mcscanxd/quickAnno，全 positional）——全部有手写 impl（`hasattr(ac, '_xxx_impl')=True`），**不走 fallback**。
2. tbplot.sh 解析出 127 个动态命令，逐一查 impl：**0 个 impl=None** → fallback 分支当前无任何命令可达。
3. metadata 中 97 个"无 impl"命令（volcano/msa/rpkmCal 等）实查均不经 `_make_passthrough`：volcano 等走 cli.py 手工装饰器分组、rpkmCal 等走 ToolGroup（ArgsParser 层，实跑 stub bash 探针确认未到 fallback 就被参数契约拦截）。
4. 回归测试（test_cli.py L799-853）只复制 impl 路径分派逻辑，**fallback 分支无覆盖**。

### 判定理由
违反三态规则的代码确实躺在那里，但现存命令拓扑下是**休眠代码**：无命令、无 spec 组合能触发它。一旦未来新增"无 impl 的动态命令"或 4 个 positional 工具的 impl 被移除，错误会静默复活（且测试不报警）。属"定时炸弹/防漂移"性质，P2。

### 方案（若采纳）
抽统一 `thread_args(name, threads) -> (argv_tail, warning)` 适配器，impl 路径与 fallback 共用同一出口；补 2 条回归：① fallback 路径 thread_style=unsupported 不注入；② fallback 路径 positional 追加位置值（用 stub bash 捕获 argv，本轮探针已验证手法可行）。

## 🟠 核实三：GPT 审查一 P1「commands.md 绕过 _resolve_group，与 CommandSpec group 分裂」

**结论：属实，且比 GPT 描述的更广 → 判 P1（文档面与运行时/元数据双重矛盾）。**

### 代码事实
- 运行时权威：cli_load `_group_of()`（L45-49）CommandSpec 模型优先、CATEGORY_MAP 兜底；CATEGORY_MAP 已标 `DEPRECATED(Phase 2, 评审 #62): 新代码禁止直接读`。
- 但 `gen_metadata.py render_commands_md()` L239 仍 `CATEGORY_MAP.get(name, "engine")` —— **绕过 _group_of，直接消费已废弃映射**。

### 分裂量化探针
- 对 298 条 metadata 命令逐条比对 `CATEGORY_MAP` vs `CommandSpec.group`：**107 条分裂**（admixture→gwas、gxffilter/gxfsort/mggxf→gxf、calcRepeat/regiondepth/sambamcov→asm、eggnog/qpcrproc→table、DecodeIlluminaFqPool 等→tool……）。
- `command_metadata.json` 的 `group` 字段 = spec.group（gxffilter→gxf），即 **commands.md 与本仓库唯一数据源自相矛盾**。
- 运行时实证：`tbtools gxf gxffilter --help` 正常；`tbtools engine gxffilter` 报「not a command in group 'engine'」；`engine --help` 0 条 gxffilter。即 **commands.md 把 gxffilter 列在「## engine — 通用（112 个）」下，而用户按文档敲 `tbtools engine gxffilter` 必失败**。

### `--check` 为何抓不住
`gen_metadata.py --check` 是"重新渲染 → 逐字节比对 surface"：同一错误逻辑确定性地产出同一错误内容，比对永远绿。515 个 surface 同步 ≠ 内容正确。本轮实跑 --check 全绿，分裂依旧。

### 方案（若采纳）
1. render 改消费 `meta[name]["group"]`（唯一数据源投影，与 _group_of 同源），删 CATEGORY_MAP 直读。
2. 补生成物一致性守卫（pytest）：断言 commands.md 中每条命令所属小节 == command_metadata.json 的 group 字段 —— 内容级校验，堵住"确定性错误重渲染"盲区。
3. 顺带核对「## engine — 通用（112 个）」计数在修正后的漂移（会缩到 ~80 量级），确认 counts.md 口径同步。
