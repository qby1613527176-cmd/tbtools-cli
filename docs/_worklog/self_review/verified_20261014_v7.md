## 发现

### P1-① 金链 pass 重绑是「半身份」: env 不可用时旧 env_fp 被宣为当前观测身份(属实)
- **实证**: 核验 #4。组合(旧证据 env=X + Tier2 fail 继承 + 金链 pass + `_JAR` 不可达)下, 报告条目变为 `(contract=当前, env=旧X)`——contract 与 env 分属两次不同观测, 违反「一条证据 = 一次完整观测身份」的证据链不变量。十一轮修复只重绑了 contract, env 走了回退。
- **生产触发面(如实评估)**: 窄。金链 pass 需真实执行引擎 ⇒ 跑金链时 JAR 存在; 同进程 `_env_fp` 判定同源(runtime/env.py 同一 env 源), 故单进程 pytest 流程几乎不可达。但写入器是可独立调用的公开函数(monkeypatch/外部注入 CONFORMANCE_RESULTS 即达, 守卫测试自己就在走这条路), 且 `core.JAR` 是 import 期常量——JAR 在跑金链后被移除/重挂载的边界也存在。**逻辑缺陷成立, 定 P1 但注明低生产触发面**。
- **修复方案**: 金链 pass 重绑分支中 `_env_fp is None` 时**不得**把旧 env 宣为当前身份。建议:
  ```python
  if _env_fp is not None:
      _env_now = _env_fp
  else:
      # env 不可确认: 本次金链观测不绑定 env 身份——置空(宁可无身份, 不可假身份),
      # 旧值留档独立字段, 供历史追溯但不参与同源判定
      _verified_tools[_t]["prev_env_fingerprint"] = _verified_tools[_t].get("env_fingerprint", "")
      _env_now = ""
  ```
  置空后果是保守安全的: `_fp_same` 要求四字段非空 ⇒ 后续 skip 不继承(降级), 与加载端「缺 fp 即 discard」不变量对齐; 不会出现「半个当前身份」的中间态。或等价方案: 加 `"env_unverified": true` 标记 + env_fingerprint 置空。
- **回归守卫**: 新增场景测试「金链 pass + Tier2 继承 + JAR 缺席 + 旧 env=X」→ 断言最终 `env_fingerprint != "env_old_X"`(且 `prev_env_fingerprint == "env_old_X"` 留档)。

### P2-① 身份重绑守卫测试宿主依赖: 有 JAR 机过、无 JAR 机红(属实)
- **实证**: 核验 #5/#6。`_build_with_results` 未控制 `os.path.isfile(_JAR)`, 使 `_env_fp` 在有/无 JAR 宿主取不同值, `test_conformance_pass_rebinds_current_fp` 走两条不同代码路径(fake env 分支 vs 旧值回退分支)。本机(有 JAR)14/14 绿; patch JAR 缺席即红。**十一轮给 P1 配的回归守卫本身在 JAR-less 环境(如 CI)不成立**——这也是 P1-① 必须修的另一层理由: 修好 P1 后该测试在两类宿主上的预期才能统一。
- **修复方案**: helper 增加 `jar_available: bool = True` 参数, 显式 `monkeypatch.setattr("tbtools_cli.core.JAR", "/nonexistent.jar" if not jar_available else <真实或伪造存在路径>)`(注意 `_JAR` 是函数内 `from tbtools_cli.core import JAR` 运行时取值, patch 模块属性即生效; 伪造存在路径需同时 patch `os.path.isfile` 或指向 tmp_path 真实文件)。三场景覆盖:
  1. `jar_available=True`: 重绑绑定 fake env(现有断言);
  2. `jar_available=False` + 旧 env=X: 按 P1-① 修复后的新语义断言(旧 env 不得宣为当前);
  3. `jar_available=False` + 无旧 env: 不崩溃、env 字段为空/标记一致。

### P3-① helper 注入 fake fp 与 `_NO_DATA_WHITELIST`/名单校验的间接耦合(提示)
`_build_with_results` 把 `EXEC_VERIFIED` 整体 patch 成单工具, 绕过了 TestConformanceReport 的数据文件校验——无碍, 但 `test_passed_tool_still_writes_evidence` 用 `next(iter(EXEC_VERIFIED))` 取「首工具」, 依赖 dict 序(volcano 当前居首); 若未来首工具变更测试仍过(只用真实工具名), 无行动必要, 仅记录。

## 总体结论

GPT 增量审查两项发现均**独立实证属实**: P1-①(半身份重绑)与 P2-①(守卫测试宿主依赖)互为表里——P2 让 P1 在 CI/无 JAR 环境失去回归保护。生产触发面窄(单进程同源 JAR 判定), 但证据链「一次观测一个完整身份」的不变量被破, 且修复+三场景守卫成本低。建议下一版本: ①按上文方案修金链 env 回退(置空+prev 留档或 env_unverified 标记); ②helper 加 `jar_available` 参数并补三场景。其余面(守卫 14/14、继承/同源/空 fp 矩阵、conftest 结果收集、只读校验)本轮核验全部健康, 无新 P0。
