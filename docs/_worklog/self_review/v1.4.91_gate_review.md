## P0

### P0-1(新, 最高优先) test.yml 缺 `name:`/`on:` 头部——主 CI 自 09-24 起 100% 失效, 全程无人察觉
- **位置**: `.github/workflows/test.yml` 第 1 行即 `jobs:`
- **发现**: 文件没有 `name:`/`on:` 块。GitHub 对无 `on:` 的 workflow 判 invalid → 每次 push 产生一条 0s failure("workflow file issue", 无日志)。`git log -S "on: [push, pull_request]"` 定位: **47336c0(09-24, "第七份评审 P0——CI YAML 结构重组")重组时误删头部**, 之后 6 次触及该文件的 commit(含 v1.4.87 依赖锁定、v1.4.81 后 fetch-depth 修复)全部在修一个**永远不会运行的文件**。13 天 / 10 个发布版 / PyPI 两次上传, 主 CI 零覆盖。
- **连带**: 上轮 P1-1(fetch-depth: 0)与 P2-3(windows 换 requirements-ci.txt)的"闭环"只是文本闭环——它们至今未在 CI 执行过一次, 闭环证据无效。
- **建议**: ①补回 `name:` + `on: [push, pull_request]`; ②在 repo 内加一个**workflow 语法静态自检**(本地 pytest 里 yaml.safe_load 全部 .github/workflows/*.yml 并断言每文件含 `on` 键——注意 YAML 1.1 里 `on` 会被解析成 True, 断言需兼容); ③RELEASING.md 发版 checklist 增加"push 后确认 CI run 绿"一步(当前 SOP 全为本地门禁, 这是 P0-1 十三天无人发现的结构性原因)。
- **严重度**: P0(门禁的强制环境整体不存在)

### P0-2(新) meta_guard sidecar 用 mtime 指纹且纳入 --check 对比——中央门禁在任何 fresh checkout 上确定性红
- **位置**: `tbtools_cli/meta_guard.py` `sources_mtime_fingerprint()`(mtime_ns+size 聚合); `scripts/gen_metadata.py` --check 将 `tbtools_cli/command_metadata.fingerprint.json` 纳入 505 surface 双向对比(arch N8)
- **发现**: sidecar 是**提交进 git 的 mtime 派生指纹**。git clone/checkout 不保留 mtime → 任何新检出环境算出的指纹 ≠ 已提交指纹 → --check 必红。实测: `git clone` 到 /tmp 后跑 --check → `❌ Generated Surface 漂移: tbtools_cli/command_metadata.fingerprint.json`, exit 1(505 中其余 504 全同步)。**P0-1 修复后 CI 第一步就会撞上这堵墙**——本轮 P0-1 被 P0-2 接力, --check 在 CI 依然不可能绿。
- **本机工作树证据(并发干扰实锤)**: 审查会话开始(17:24)时 --check 全绿; 17:47 前后全量 pytest 内嵌的 `test_gen_metadata_check_passes` **失败**(fingerprint 漂移); 17:50:42 工作树 sidecar 被某并发过程重 render(git diff 仅 sidecar 一行变化, 纯 mtime churn, 无内容变化)。即在本机单仓库内, 该机制也会被任何 touch mtime 的操作(git checkout/并发 render)随机打红——**gate 的触发与"源码是否真改"脱钩**。
- **建议**: 指纹改为**内容哈希**(sha256 of file bytes, 不含 mtime)——检出环境可复现, 且仍满足"改源码未 render → 指纹变"的守卫语义; 或将 sidecar 移出 --check 对比集+移出 git(只做本地消费端 warn)。当前"提交 mtime 指纹 + 跨机对比"的组合在任何拓扑下都不成立。
- **严重度**: P0(--check 在强制环境确定性失效)

### P1-1(残留恶化) TTL 严格门在 verified_tools 非空时**无条件红**——且非严格模式刷 56 行假告警
- **位置**: `scripts/gen_metadata.py` TTL 检查块(~L441-460)
- **发现**: `_msg` 构造 + strict 阻断 + 软告警 print 三者**缩进在 `for _t2, _v2 in _vt.items()` 循环内、且无 `if _old_days:` 守卫**。后果实测:
  - `TBTOOLS_TTL_STRICT=1 python3 scripts/gen_metadata.py --check` → 第一条工具迭代即 `return 1`, 输出"❌ 验证超龄 **0** 个(>90 天, TTL 严格模式阻断)"——**0 个超龄也红**, nightly 的 TTL gate 步一旦被执行到就永远绿不了(当前被 nightly 更上游的 E2E 失败掩盖, 见 P1-4);

### P1-2(新) coverage 硬门槛在 CI 管道里被 tail 吞掉退出码——fail_under 永远不会开火

- **严重度**: P1

## 最值得改的 3 点

1. **补 test.yml 的 `name:`/`on:` 头部 + workflow 语法静态自检 + RELEASING 加"确认 CI 绿"**(P0-1): 一分钟改动 + 一个测试 + 一行 SOP, 恢复整个强制环境; 不加自检则同类事故必然三度复发。
