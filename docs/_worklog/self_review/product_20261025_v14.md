## 二、GPT P2-1：未知参数拒绝的边界完整性 —— 基本成立，1 处 P3 不一致 + 2 处观察项

### 核验路径（mcp_server.py `tool_run`，十八轮修复后）

逐条核实 GPT 的 6 个验证点：

1. **有契约工具传未知参数时不启动外部进程（执行前拦截）** —— ✅ 实证成立。
   探针：`tool_run('expr volcano', arguments={inputs:[...], parameters:{'evil_param':'x'}})`
   返回 `UNKNOWN_PARAMETER`，stderr 无 Java 输出（对比探针 2 合法参数有 `java.lang.reflect.InvocationTargetException`  stderr）——拒绝发生在 `_cli()` 调用之前（`mcp_server.py` 参数循环内 `return`），外部进程未启动。

2. **cli_name 别名参数不误拒** —— ✅ 实证成立。
   探针：`pval_cutoff='0.01'`（契约名，cli_name=`--pval-cutoff`）正确识别、翻译并进入执行（仅因输入文件不存在而 TB102，属预期）。KNOWN_PARAMS↔spec 分歧全量扫描：对所有有 spec 的工具比对 `KNOWN_PARAMS` 多出项，**0 例分歧**（即 `k not in _cli_map` 的宽限分支当前无实际触发场景，属防御性冗余，无害）。

3. **布尔/数值参数不因类型转换绕过检查** —— ✅ 实证成立。
   探针 3：bool 工具 heatmap 注入 `evil_bool='true'` → UNKNOWN_PARAMETER 拒绝（未知检查在类型检查**之前**，bool 宽松值域不能绕过）。
   探针 4：`w='abc'`（int 参数传非数值）→ `INVALID_PARAMETER_TYPE`，expected/received 明确。

4. **错误响应 valid_parameters 与实际契约一致** —— ✅ 成立。
   返回 `sorted(_spec_map.keys())`，与 `build_command_specs()` 实测参数集逐一相符（volcano: fc_cutoff/h/pval_cutoff/w；heatmap: h/log2/row_scale/w）。

5. **无契约工具的 warnings 不被误认为经过完整校验** —— ✅ 实证成立。
   探针 5b：`tool mcscanxd` + `evil_param` → 走逃生舱，引擎自行报 TB101，响应带 `warnings:["参数 evil_param 不在已知契约中, 按 kebab-case 直透(--evil-param), 引擎将自行判定"]`。warning 措辞明确说"引擎将自行判定"，语义上不可能被读成"已通过校验"。✅

6. **retryable 不机械为 true** —— ⚠️ **发现不一致（P3）**。
   `UNKNOWN_PARAMETER` 标 `retryable: true`，而同为"用户须修正输入"的 `INVALID_PARAMETER_TYPE` 标 `retryable: false`（两分支相隔 ~20 行）。两者都是修正参数后重试即可成功的同类错误，retryable 语义相反。无论采哪种语义（"可修正后重试" vs "原样重试无意义"），当前是不一致的。GPT 要求的"需要用户修正输入时不应提示可重试"若严格执行，UNKNOWN_PARAMETER 的 `retryable:true` 应改 false；但更合理的解读是二者统一为 true（修正输入后重试本来就是 Agent 的正常循环）。**定级 P3**（协议语义一致性，不影响安全/正确性）。

### 观察项（不定级，记录备查）

- **O1：`build_command_specs()` 异常静默降级**。`_spec_map` 构建在 try/except pass 中，若 spec 构建抛异常，**所有工具（包括有契约的）退化为逃生舱**——严格拒绝静默失效。建议 except 分支记 stderr warning（当前完全静默）。
- **O2：`job_submit` 无 arguments-dict 入口**（仅 args list），未知参数直透引擎。与 CLI 语义一致（见下节），但与 tool_run 的 arguments 路径不对称。属设计分层而非缺陷——异步入口是 CLI 透传语义的延伸。

**结论：GPT 该 P2 的核心修复（执行前拦截/别名识别/类型不绕过/valid_parameters 一致/warnings 语义）全部独立核实成立。遗留 1×P3（retryable 语义不统一）+ 2 观察项。**

## 三、GPT P2-2：三入口同一参数校验 —— 属实分叉，GPT 判断成立，定级 P2（偏 P3）

### 现状核实（三入口各自实现）

| 入口 | 校验位置 | 未知参数行为 | 类型检查 |
|:--|:--|:--|:--|
| **CLI**（`tbtools tool-run` / `tbtools tool <name>`，cli_top.py:935 / cli.py ToolGroup） | `context_settings={"ignore_unknown_options": True}` —— **无契约校验**，原样透传引擎 | 引擎自行报错（TB101） | 引擎自行判定 |
| **MCP**（mcp_server.tool_run arguments 路径） | **自实现的一份校验**（spec_map 查名 + int/float/bool 类型 + bool flag 化） | UNKNOWN_PARAMETER（有契约）/ warnings 逃生舱（无契约） | int/float/bool |
| **Workflow**（compiler.py → InvocationSpec.build_argv，command_spec.py:67） | **CommandSpec 为唯一源的编译期校验**（`raise ValueError("UNKNOWN_PARAMETER: ...")`） | 拒绝（实测：`UNKNOWN_PARAMETER: evil`） | int/float（**无 bool 检查**，bool 由 flag 语义处理） |

### 分歧点（实测确认）

1. **MCP 与 workflow 是两份手写实现，不是共享调用**。MCP 的翻译/校验逻辑（mcp_server.py 参数循环 ~40 行）与 `InvocationSpec.build_argv`（command_spec.py:67-100）功能高度重叠但各自演化：
   - MCP 多一层 `_cli_map`（KNOWN_PARAMS）宽限；build_argv 严格只认 spec.parameters。
   - MCP 校验 bool 值域；build_argv 不校验 bool（直接 flag 语义）。
   - MCP 输出结构化 JSON 错误；build_argv 抛 ValueError（由 compiler 捕获包装）。
   - 实测：同一组合法参数二者产出一致 argv（`--pval-cutoff 0.01 --w 800`），行为当前等价，但**漂移风险实在**（两份代码已各有对方没有的分支）。
2. **CLI 完全不校验**是显式设计（引擎即真相，`--key=value 会被 ArgsParser 拒绝` 的引擎契约），但意味着"CommandSpec 为唯一校验来源"对 CLI 入口不成立——GPT 建议的三入口同一套测试目前**不存在**。

### 定级与最小统一方案

**定级：P2（架构债，非正确性缺陷）**。当前三入口在"有契约工具 + 正常参数"路径行为一致（探针实证 MCP 与 build_argv argv 等价），分歧只在边界分支与错误形态。不阻塞发布，但属于每轮自审反复消费的同源债。

**最小统一方案**：
1. MCP `tool_run` 的 arguments 翻译**改调 `InvocationSpec.build_argv`**（有契约时），删除 mcp_server.py 内手写的 40 行平行实现；无契约工具保留逃生舱。ValueError→结构化 JSON 的映射表（UNKNOWN_PARAMETER/INVALID_PARAMETER_TYPE/MISSING_REQUIRED_*）单点维护。
2. CLI 入口不动（透传是引擎契约设计），但在 `tool-run --dry-run` 里对**有契约工具**复用同一 build_argv 做预检（dry-run 本就是规划期校验位），三入口共享只发生在"契约存在"时。
3. 测试侧：以 CommandSpec 为源生成参数化测试（每工具：合法集/未知键/错类型三用例），同时打 MCP tool_run 与 compiler.compile_step 两入口——CLI 透传入口断言"未知参数达引擎报 TB101"即可。
