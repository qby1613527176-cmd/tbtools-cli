## 二、发现

### P1-1 🟠 GPT P1/P2 属实: TTL 循环对「两个时间戳都缺失/为空」的记录静默放行(strict 亦不拦)

**代码实证**(scripts/gen_metadata.py L448):
```python
_va = _v2.get("last_passed_at") or _v2.get("verified_at", "")
...
if _va:            # ← _va 为 ""/None 时整个解析分支不进入
```
`_bad_ts` 只在 `if _va:` 分支内的 except 里 append。双字段空串/双 null/字段缺失(`get` 默认 `""`)三条路径全部使 `_va` 为 falsy → 该工具既不判龄也不记 bad → strict 模式 exit 0 且**零告警**(探针 A/B 实测, 核验表 #3/#4)。

**影响**: nightly 保鲜链若某工具 writeback 时漏打/打空时间戳(报告回写回归、手工编辑报告、schema 漂移), 严格 TTL 门禁永久无感——这正是 147845e 想堵的"畸形时间戳静默"同类漏洞, 只堵了"畸形非空", 漏了"空"。

**GPT 附带指控的勘误**: GPT 称"只读校验 fromisoformat 只捕 ValueError, None 等类型错误外层捕到只 warning 不 fail"——**不准确**。TTL 内层是 `except Exception`(broad), 非只捕 ValueError; 外层大 try 的 except 在 strict 下是 `return 1`(L476-479), 不是 warning。None 值的真实问题不是"类型错误只 warning", 而是 `or` 短路导致根本不进解析分支(同上 P1-1)。

**修复建议**:
```python
_va = _v2.get("last_passed_at") or _v2.get("verified_at") or ""
if not _va:
    _bad_ts.append((_t2, "<missing/empty>", "last_passed_at+verified_at"))
```
即双缺失一律记 bad(strict fail / 普通 warning 均带工具名, 现有 `_bm` 格式化已支持)。另建议只读校验把 verified_tools 条目做最小 schema 断言(必须含非空 last_passed_at 或 verified_at 之一), 缺失即 schema 失败。

### P2-1 aware datetime 被误报为「时间戳解析失败」

探针 C(核验表 #5): 合法的 ISO 8601 带偏移时间戳 `2026-10-12T10:00:00+08:00`,`fromisoformat` 解析**成功**(Python 3.11+ 全程支持; 3.7+ 对 `+08:00` 形式也支持), 但 `(_now2 - aware_dt)` 抛 TypeError, 被 broad except 吞后报成"解析失败", strict 下直接 fail。

**影响**: 当前 writeback 打点用 naive 本地时间, 不会触发; 但一旦上游(或手工/其他工具)写入 RFC3339 带 `Z`/`+hh:mm` 的合规时间戳, nightly TTL gate 会误红, 且报错文案误导排查方向。

**修复建议**: 解析后统一归一化再相减:
```python
_ts = _dt2.datetime.fromisoformat(_va)
if _ts.tzinfo is not None:
    _ts = _ts.astimezone().replace(tzinfo=None)
_age = (_now2 - _ts).days
```
(或 `_now2 = datetime.now(timezone.utc)` + 全部 aware 化。)GPT 此项"TypeError 是否被当解析异常处理"——答案: 是, 被当解析异常处理, 能拦但归类错误。

### P3-1 探针注入会引起 fingerprint 漂移 → `--check` 先于 TTL 红

观测: 修改 verification_report.json 后未 render, `--check` 先在 Generated Surface 漂移处 exit 1(`tbtools_cli/command_metadata.fingerprint.json`), TTL 块根本执行不到。这本身是正确设计(报告是 surface 输入), 但意味着 **P1-1 的静默放行有一个前置遮蔽**: 真实场景里"报告被改坏但没 render"会先被漂移门禁拦下; 只有"坏报告 + 同步 render 并提交"(如 nightly writeback 链本身写坏了再 render)才会走到 TTL 块并静默放行。降低了 P1-1 的实际暴露面, 不消除它(nightly 链正是"改报告+render"的执行者)。
