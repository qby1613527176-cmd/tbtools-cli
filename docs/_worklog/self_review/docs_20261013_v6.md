### P2-1 ✅确认并独立坐实(GPT 增量): v1.4.98 门禁数字三口径互不相干

三个发布面对同一版本给出三个 pytest 数字, 且**任何一个都无法从仓库内复核**:

| 数字 | 出处 | 口径可溯? |
|---|---|---|
| 24 passed | CHANGELOG v1.4.98 门禁行 | ❌ 无命令、无构成 |
| 39 passed | GitHub Release v1.4.98 body | ❌ 无命令、无构成 |
| (115) | README_EN L85 质量门禁行 | ❌ 无快照日期; 实为 09-23 旧值 |

- 复算尝试: 守卫13(TestEvidenceWriteGuard 实测 13 collected) + doc 10 + metadata 15 + TestReadmeCounts(4) = **42**, 既非 24 也非 39——即两组数字的测试子集构成都无法从现有记录重建(GPT 猜的「39=13+10+15+cli1」与实测 TestReadmeCounts=4 不符, 仅是可能性之一)。这正是问题本质: **裸数字不可审计**。
- 对比: v1.4.94/1.4.95 门禁行有构成注记(「34=守卫7+doc10+metadata15+cli2」)——项目自己有更好惯例, v1.4.98 回退了。
- 方案(最小): ① CHANGELOG/Release 门禁行恢复构成式 `N=守卫13+doc10+metadata15+cliK(命令: pytest <paths>)`; ② Release body 与 CHANGELOG 同一行同源(发版脚本从 CHANGELOG 抽取或反之); ③ README_EN 的 `pytest (115)` 改为不写数(对齐中文面策略: README 刻意回避测试计数, 见 gate v5 报告 #4)或注「快照 2026-09-23」。

### P2-2 ✅确认(GPT 增量): README_EN `pytest (115)` 陈旧且无守卫
