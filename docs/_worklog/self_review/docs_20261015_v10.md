## F1 · 🟡 GPT 审查一 P2：schema-capable 定义窄于实际谓词 —— **属实，P2 确认**

**独立核实**（非照抄）：

- README hero（L28）：`Schema-capable 64`(有 inputs 契约) —— 文字定义 = **仅 inputs**。
- 权威谓词（`scripts/gen_metadata.py:293`、`tbtools_cli/cli_top.py:137`）：
  `inputs OR outputs OR output_slots OR parameters` —— **四元析取**。
- 守卫 `test_schema_capable_consistent` 用的却是**第三种**口径：`command_metadata.json` 里 `e.get("inputs")`（inputs-only）。

**实测三个口径当前是否分叉**（本轮新证据，GPT 未做）：

```
metadata.json: inputs-only = 64, OR-predicate = 64, OR-only 工具 = 0
specs(build_command_specs): inputs-only = 64, OR = 64
```

→ **当前数值无漂移**（64 在三个口径下恰好一致），但：

1. **文字定义窄于代码谓词**：读者会把 schema-capable 误读为「有 inputs 契约」，而代码实际承认 outputs-only / parameters-only / slots-only 工具也算 schema-capable。若未来出现一个 outputs-only 工具，README 文字定义将率先失真。
2. **守卫自身口径不统一**：`test_schema_capable_consistent`（inputs-only）与 `test_schema_capable_version_json`（OR 谓词，经 counts.md）两个守卫各用一套谓词，今天重合是巧合而非保证——这是比 README 文字更值得修的隐患。

**结论**：P2 确认。
- **修 README**：hero 行改为「有 schema 契约(inputs/outputs/parameters/slots 任一)」，与代码谓词对齐。
- **修守卫（建议升级 P1.5）**：`test_schema_capable_consistent` 的 command_metadata 口径改为同一 OR 谓词，消除「巧合一致」型守卫。
- 不诱导误读为 fully verified：README L28 已有「FULL 契约 ≠ 已验证执行」显式声明，schema-capable 定义修正后无需再加。
