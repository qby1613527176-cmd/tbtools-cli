## 二、发现 1:工作流示例输入输出关系 —— **P1 属实,且比 GPT 所述更重**

### 2.1 独立核实证据(实测,非复述)

**ai/workflows.json 两条链的数据流断点**(用各工具自身 relations 契约交叉验证):

- `rna-seq`: inputs 声明 `counts + len_info`,steps = tpmCalc→pca→heatmap→volcano。
  实测各工具契约:
  - tpmCalc `produces: [TPM_TABLE]`,pca/heatmap `accepts: [EXPRESSION_MATRIX]`(勉强兼容)
  - **volcano `accepts: [DEG_TABLE]`** —— 链上**没有任何一步产出 DEG_TABLE**。tbtools 没有差异表达计算工具(DEG 表需外部 DESeq2/edgeR 产出),README 任务表"counts + 基因长度 → tpmCalc→pca→heatmap→volcano"行同样断在 volcano。
- `gene-family-analysis`: inputs 只声明 `family_fasta`。
  实测:
  - **genestructure `accepts: [GFF3, GENE_ID_LIST]`,两个输入均 required** —— 工作流未声明
  - **motif `inputs: meme_xml(required) + ids(required)`** —— FASTA 不能直连 motif,中间缺 memerun(任务表另一行 `memerun → memeViz/motif` 反而写对了,与典型工作流 bullet 自相矛盾)

**结构缺陷**: workflows.json 的 step 只有 `{tool, role}`,**无 depends_on / inputs_from / required_inputs 字段**;inputs 是流程级平铺列表,无法表达"哪一步消费什么、缺什么外部输入"。而 docs/workflows.md 声称 "each step = tool id + role; **inputs/outputs chained**" —— 文件里根本没有链式信息,文档陈述与数据不符。

### 2.2 独立评估:是否误导 Agent?

**误导成立,分三层**:

1. **静态文件消费者(读 ai/workflows.json 的外部 Agent)**: 拿到平铺 steps + 不完整 inputs,会按 FASTA-only 规划基因家族流程,在 genestructure/motif/volcano 步必然 tool-validate 失败。这是 GPT 所指的问题,**属实**。
2. **文档消费者(读 README/docs 的人或 Agent)**: README 典型工作流 bullet 虽有 `(DEG)` 括注,但无任何"外部输入"标注;docs/workflows.md 明确声称 "inputs/outputs chained"(不实)。
3. **缓解面(为什么不是 P0)**: 真正的规划路径 `plan_from_goal`(workflow.py L275+)**根本不读 ai/workflows.json**,而是走 relations 契约图(A.outputs ↔ B.inputs 真实配对 + 格式族三级匹配)。实测契约图不会连出 tpmCalc→volcano 假边(TPM_TABLE vs DEG_TABLE 子串/格式族均不命中)。即"规划器是对的,静态示例是错的"——错的是 Agent 的**第一认知入口**。

### 2.3 方案(按性价比排序)

1. **workflows.json schema 升 1.1**(根治): 每 step 加 `depends_on`(DAG) + `inputs_from`(上一步产物 or `external`);流程级显式 `external_inputs`(rna-seq: `deg_table`; gene-family: `gff3, gene_id_list, meme_xml`)。同步修 docs/workflows.md "chained" 的不实陈述。
2. **README 典型工作流 bullets 加外部输入标注**(止血,一行内的事):
   `counts → tpmCalc → pca → heatmap;volcano(需外部 DEG 表,如 DESeq2 产出)`、`FASTA → muscle/trimal → iqtree;motif(需 memerun 产出 MEME XML + ID 列表);genestructure(需基因组 GFF3 + ID 列表)`。
3. **守卫**: gen_metadata --check 增一条"workflow steps 数据流闭合校验"(用 relations accepts/produces 验证每条链,断点必须被 external_inputs 覆盖),防再漂移。

**定级 P1**(GPT 同);不升 P0 的理由: 契约图规划器自身正确,tool-validate 会在执行前拦下错误链,不会静默产出错误结果。

## 三、发现 2:"4 plan-able workflows" 名不副实 —— **P1(本轮升格)**

这是核实发现 1 时暴露的**更深问题**,GPT 未报。

**证据**(`grep -rn "workflows.json" tbtools_cli/*.py` 零命中;实测):

```
$ tbtools workflow-plan "rna-seq" --json        → plan: []  conf: 0.0
$ tbtools workflow-plan "gene family" --json    → plan: [circlegene]  conf: 0.35   # 错配
$ tbtools workflow-plan "phylogeny" --json      → plan: [degramdom]  conf: 0.2     # 错配
$ tbtools workflow-plan "comparative genomics"  → plan: []  conf: 0.0
$ tbtools workflow-plan "基因家族" / "系统发育"   → plan: []  conf: 0.0
```

而对外宣传面: examples/workflows/README.md"更多工作流定义见 ai/workflows.json(**4 个可规划流程**)"、docs/agent.md"ai/workflows.json 4 **plan-able** workflows"。

**判断**: ai/workflows.json 是一份**没有任何代码消费的孤儿文件**——规划器不读它、按名字/id 也查不到它描述的四条流程;宣传面却把它定位为"可规划"。对 Agent 而言这是发布链上的硬矛盾: docs 说"这 4 条能 plan",实际 `workflow-plan` 对同款目标返回空或错配工具(circlegene/degramdom 与目标无关)。

**方案**(二选一):
- a) plan_from_goal 增加 workflow id/title 直查层(命中 workflows.json 直接实例化模板,配合发现 1 的 DAG 字段),让"plan-able"名副其实;
- b) 若定位本就是"静态参考示例",则**删掉 docs/agent.md / examples 里 "plan-able/可规划" 表述**,改述为"参考链(规划请用 workflow-plan 契约推导)"。

**定级 P1**: Agent 可见面的功能宣称与实测行为直接矛盾。

## 四、GPT P2 项核实

### 4.1 CONTRIBUTING 82 vs counts.md 80 —— **P3(口径混淆,定级下调)**

- 实测: `len(CLI_TOOLS)` = **82**;counts.md 权威 `tools: 80`(spec `kind=="tool"` 口径,与 version --json 同源)。
- gen_metadata.py L209-215 注释已自陈根因: 注册表 82 条中 mimicVqsr/vcfAddID 在 CommandSpec 归一化为 **direct**(引擎反射层),故 kind==tool = 80。
- CONTRIBUTING.md L31 原文: "`tbtools_cli/cli_tools_registry.py` | 82 个 CLI 工具共享注册表"。它描述的是**注册表条目数**(82 条属实),但措辞"82 个 **CLI 工具**"与已统一为 80 的 census 口径撞词——这正是注释里点名的"COMMAND_REFERENCE 82 个工具漂移的结构根因"的同类残留。
- **不是真漂移**(两处数字都有据),是**口径混淆**: 定 **P3**。修法一句话: "82 条注册项共享注册表(权威工具口径 kind==tool 为 80;mimicVqsr/vcfAddID 归一化为 direct)"。
- GPT 定 P2 偏高: 该文件是维护者文档,非 Agent 规划面;且注释体系已记录口径差异。

## 五、发现 6(本轮独立新发现): execution_verified 环境漂移 —— **P2**

**实测**(同一 checkout、同机、间隔秒级):

```
$ python3 -m tbtools_cli.cli version --json   → execution_verified: 56
$ ./bin/tbtools version --json                → execution_verified: 53   # 可复现
$ docs/_generated/counts.md                   → execution_verified: 56
$ README L26-27                               → "EXECUTION_VERIFIED 56 ... 数字权威源: version --json / counts.md"
```

**机制**: bin/tbtools `source config/config.sh` → 用户配置 `~/.config/tbtools-cli/config.sh` 注入 `TBTOOLS_JAR=/mnt/d/.../TBtools_JRE1.6.jar` → census 走 contract_fingerprint 绑定(评审 #110),3 个工具的存证指纹在当前 env 下失配降级,EXECUTION_VERIFIED 55→52(+1 conformance)。即**设计内的 env_fingerprint 语义**,本身合理。

**问题在呈现层**: README L27 明确宣称 "数字权威源: `tbtools version --json` / counts.md(**自动生成防漂移**)" 并把 56 写进正文——但在用户真实配置环境(bin/tbtools 路径)下,version --json 输出 53,与 counts.md/README 的 56 **直接互相矛盾**,"防漂移"承诺被击穿。Agent 按 README 指引拿 version --json 对账 counts.md,会判定仓库数字不可信。

**定级 P2**(功能无损,信任面受损)。方案:
1. README L26-27 的 verification 行注明"execution_verified 随 env_fingerprint 变化,counts.md 记录的是金链环境值(56),version --json 为当前环境实测"——把 env 依赖从隐式变显式;
2. version --json 增一字段 `execution_verified_goldenv: 56`(从 verification 存证直读,与 env 无关),让 Agent 一次拿到"环境实测 + 金链基线"两个口径,对账不再靠猜。
