## 🔴 P1-1：Bash fallback 丢弃已处理 argv —— 属实

### 数据流复核（cli_load.py `_make_passthrough._cmd_impl`，L317-393）

```
args = list(ctx.args)                # L318 拷贝
validate_file(args[0])               # 校验（只读 args，不修改）
preset → 可能改写 width/height 局部变量
fmt   → 原地改写 args[i] 输出扩展名  # L352-357 ✅ 写进 args
width/height → args.append(...)      # L360-363 ✅ 写进 args
threads → args.extend(thread_args)   # L376-380 ✅ 写进 args
─────────────────────────────────────
if impl:  impl(args, ...)            # ✅ impl 吃到全部处理后参数
else:     bash_args = [...] + list(ctx.args)   # ❌ 丢弃 fmt/width/height/preset
          + thread_args(...) 单独重算追加        # （threads 是唯一被补回的）
```

### 影响面量化（探针实测）

bash fallback 路径（impl=None）当前覆盖 **13 条命令**：
`dehist genestructure hclust heatmap2 motif msa onesteptree pca seqlogo tree treeRooting unrooted volcano`
——**几乎全是绘图命令**，即 fmt/preset/width/height 语义最重要的那批。Agent 调
`tbtools seq volcano ... -f png -p nature` 走 fallback 时：输出仍是 `.svg`，nature 预设的
宽高静默丢失，无任何警告。这是「Agent-facing 契约被静默降级」，比 impl 路径缺功能更糟——
两条路径行为分叉且不可观测。

### 架构语义判定

GPT 的「前置处理 vs 后置处理职责错位」定性准确。正确的分层：
- **Agent-facing 语义（必须对 fallback 生效）**：fmt（输出扩展名改写）、preset→width/height、
  显式 width/height、threads——这些是 CLI 对 Agent 的承诺，与执行通道无关；
- **通道私有**：verbose/quiet（impl 的 Python 日志开关，bash 通道天然没有，丢弃合理）。

当前代码恰恰把「通道无关承诺」绑死在 impl 通道上。

### 修复方案

fallback 分支改为消费已处理的 `args`（threads 已在 L380 前并入，删除单独重算块）：

```python
bash_args = [bash_bin, os.path.join(ROOT, "bin", "tbplot.sh"), name] + args
```

注意点：① threads 已在 args 里，重算会**双重追加**（现状不重只是因为基于 ctx.args）；
② fmt 改写后的扩展名对 bash 通道同样有效（Java 工具按扩展名定输出格式）——语义一致。

### 回归测试设计

复用 `tests/test_cli.py::test_missing_spec_fallback_named_flag`（L835，monkeypatch 模式已存在）：
1. monkeypatch `_parse_auto_metadata` 返回 impl=None；monkeypatch `shutil.which`→"/bin/bash"；
   monkeypatch `subprocess.run` 捕获 argv；
2. 调 `Runner.invoke(cmd, ["in.txt", "out.svg", "-f", "png", "-W", "800", "-t", "4"])`；
3. 断言 bash argv 含 `out.png`、`800`、`--threads 4`，且 `--threads` 只出现一次；
4. 反向断言：argv 中不出现 `out.svg`。

## 🔴 P1-2：workflow-plan 配方种子绕过校验 —— 属实（三 sub-claim 全中）

### 复核路径（workflow.py plan_from_goal）

**① 种子注入不过契约边校验（L440-451）**：配方链直接 `plans.append((chain, [("recipe", None)]*len(chain)))`，
不经过 `_edge()`/`_content_compat()` 任何一边的格式配对。`_score` 只对 content_type 冲突罚分
（`content_type_conflict` 循环对配方链同样跑），**格式兼容性零校验**。

探针实测（ai/workflows.json 现有 4 条配方）：

```
rna-seq 配方链 tpmCalc→pca→heatmap→volcano：
  pca→heatmap:    prod=[svg, pca_plot]  vs acc=[tsv, expression_matrix]  → 不兼容
  heatmap→volcano: prod=[svg, heatmap]  vs acc=[tsv, deg_table]          → 不兼容
gene-family 配方链：
  trimal→iqtree:  prod=[aln, trimmed_alignment] vs acc=[fasta, alignment] → 兼容(族匹配)
  iqtree→motif:   prod=[nwk,...] vs acc=[xml,txt,fasta,gff3]              → 不兼容
  msa→trimal:     prod=[sequence_artifact] vs acc=[fasta, alignment]      → 不兼容
```

即**现有配方一半以上的相邻边过不了自家契约图**。`plan_from_goal("rna-seq", input_format="txt")`
实测返回 confidence=0.2、reasons 含 `irrelevant_start + passthrough_prefix`——分数被压下来了，
但 plan 照样作为 best 输出，且 `planning_score.evidence` 没有任何「配方边未校验」标注。

**② fmts off-by-one**：边列表应为 `len(chain)-1`，实注入 `len(chain)` 个 `("recipe", None)`。
后果链：
- `_score` 中 `contract_edges == len(chain)-1` 永假 → 配方链永远拿不到 `all_contract_edges` 加分（设计如此还是 bug 不明）；
- `fuzzy` 循环对每个 recipe tuple 罚 -0.05（tuple ∉ 格式字符串列表）——配方链被隐性扣分；
- `_fmts_padded = [None] + fmts` 长度变成 len+1，zip 截断后 step≥2 的 reason 渲染为
  **`contract graph(('recipe', None))`**（实测输出确认）——内部哨兵 tuple 泄漏到 Agent 可见面。

**③ 未知工具静默过滤**：`_chain = [c for c in _chain if c in specs]`——配方写错工具名（typo）
整条链静默缩短，无任何告警；`ai/workflows.json` 无人校验（探针确认 "heatmap" 在 specs 纯属运气）。

### 架构评估：种子的正确位置

GPT 问「高置信先验 vs 绕过校验的边界」——判定：**当前实现是绕过校验**。正确设计是
「种子 = 候选生成器，校验 = 同一套」：

1. 种子链注入后，逐相邻边跑 `_edge()`：兼容 → 边信息替换为真实契约边（同时修掉 off-by-one，
   边数 = len-1）；不兼容 → 不丢链（配方是人工策展的高价值信号），但 reason 标
   `recipe_edge_unvalidated` 并扣分（如 -0.2/边），confidence 透明降级；
2. reason 字符串用显式 `"recipe"` / `"recipe(unverified edge)"`，禁止渲染内部 tuple；
3. 未知工具过滤处 `warnings.warn`（与全仓「失败可见化」纪律一致，参照 cli_load._spec_groups 先例）；
4. 新增守卫测试：`tests/test_workflow.py` 断言 ai/workflows.json 每条配方 ① 工具全在 specs
   ② 相邻边 `_edge` 兼容或显式列入白名单——把配方文件纳入契约维护面，防腐化。

### 缺口 1：ENGINE_REGISTRY ∩ CLI_TOOLS 无交集断言

探针实测交集 = **{mimicVqsr, vcfAddID}**（2 条，auto_commands.py L197 注释为 N13 有意双注册，
build 用 `setdefault` 使 CLI_TOOLS 条目静默被 ENGINE_REGISTRY 覆盖）。问题不在双注册本身，
而在**无任何测试钉住这个交集**——第三个双注册命令出现时，其 CLI_TOOLS 定义（runner=java/xmx=3g
投影）会被静默丢弃，无告警。闭环条件：加断言 `ENGINE_REGISTRY ∩ CLI_TOOLS ⊆ {mimicVqsr, vcfAddID}`
白名单，或消除双注册。

### 缺口 2：`_infer_group`（gen_metadata.py L104）未与 `_resolve_group` 统一

`_infer_group` 是平行遗留实现：直读 CATEGORY_MAP（**不感知 KNOWN_GROUPS**）+ 正则扫装饰器
（command_spec 侧已换 AST source_scan）。`specs_from_scans` 里 reg 命令走 `_resolve_group`（正确），
manual 命令分组兜底走 `infer_group` 或 `_CM.get(name, "engine")`（command_spec.py L1032）——
**投影管线的 manual 分组推断与运行时 AST 推断存在双实现**，正则 vs AST 的解析分歧（多行装饰器、
引号变体）会让 metadata 投影分组与运行时 spec.group 分裂，而现有 census 守卫只比
`spec.group vs _group_of`，不覆盖投影管线。

### 可验收闭环清单（GPT 所问「闭环条件」）

1. CATEGORY_MAP 退役条件可验收化：CATEGORY_MAP 当前仍被 `_resolve_group` 兜底读取，
   **循环依赖**——spec.group 派生自 CATEGORY_MAP，清空它要求分组信息先上移真源
   （ENGINE_REGISTRY 元组加 group 列，或 YAML overlay 声明）。验收：CATEGORY_MAP 键数单调
   递减计数器测试（只允许减不允许增）+ 目标清零里程碑；
2. 交集断言（缺口 1）；
3. `gen_metadata._infer_group` 删除，manual 分组统一走 `source_scan.ast_scan_commands` 的
