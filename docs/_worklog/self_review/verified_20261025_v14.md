## 发现

### 🔴 P1-1 Artifact 登记先于验证——无效产物进入全局索引(GPT 属实,实证复现)

**代码事实**(executor.py L211-234):
```python
if step_ok and out and os.path.isfile(out):
    _a = _ab(out, producer=st["tool"]); _reg_err = _areg(_a)   # L217-219 先登记
    ...
if step_ok and out and os.path.isfile(out):
    _vok, _vmsg = validate_artifact(out)                        # L231 后验证
    if not _vok: step_ok = False
```

**探针实证**(HOME=/tmp 隔离,`_execute_step` 直接调用,tool=`--help` ec=0 + 预置坏 fasta):
- 返回 `status: "failed"` + `validation_warning: "output validation failed: fasta header missing"`
- **同时返回 `artifact_id: art_7e4b43b8...`,且 `~/.config/tbtools-cli/artifacts.json` 已含该条**
- `artifact.resolve(art_id)` → 返回坏文件路径(文件存在+sha 匹配,身份验证通过)

**影响**: 外部调用者/workflow 下游步骤持 artifact_id 可解析到一个**未通过验证的文件**;索引成为"失败产物的持久残留",且无任何字段标记其验证状态。下游若用 `binding.inputs: ["@art_xxx"]` 引用,将消费损坏产物。

**方案(按侵入度排序)**:
1. **先验证后登记**(最小改): 把 L229-234 的 validate 块上移到 register 之前,仅 `_vok` 时才 build+register。副作用:失败产物无索引记录(本就应如此)。
2. 登记后校验失败则撤销(`unregister(art_id)`,需新增 API)——比方案 1 多一个失败窗口。
3. Artifact 生命周期 `created→validated/invalid`(索引条目加 `validation` 字段,resolve 对 invalid 拒绝或警告)——最完整但改动最大。
- 推荐方案 1,一次改动闭环。

### 🟠 P1-2 validate_artifact 严格程度(GPT 增量评估——部分属实,建议降级为标注层级)

**当前实际检查**(L440-499,十八轮后):
| 格式 | 已做 | 未做(GPT 指出,属实) |
|:--|:--|:--|
| FASTA | 首字符 `>` + 计数 | 序列字符合法性(IUPAC)、record 完整性(头/序列配对)、gzip 全量(仅读 8KB 头) |
| GFF | 关键词存在(`##gff-version`/gene/mRNA/CDS) | 9 列结构、坐标 start≤end、数值列解析 |
| Newick | 括号配对存在 + 末尾 `;` | 括号平衡、分支长度数值、拓扑合法性 |
| TSV/CSV | ≥1 非空行 | 列数一致性、表头、数值范围 |
| SVG | `<svg`/`<?xml` 在头部 | XML well-formed 解析、图形完整性 |

**评估**: GPT 的三级分类(existence/structural/semantic)中,L1 parse 我们已到"头部启发式"层级(严格说介于 existence 与 structural 之间);L2 semantic 已在 §6.2 声明不做。GPT 的 incremental 建议**合理部分是:返回值标注检查层级**,让调用方知道"通过"是哪种通过。

**最小方案**: `validate_artifact` 返回 `(bool, msg)` 改为详情串带层级前缀,如 `"syntax_valid: fasta seqs=3"` / `"structure_valid: ..."` / 兜底 `exists(...)` 改标 `"existence_only: ..."`——一行文案改动,无 API 变更,语义透明度闭环。真正的 L2 语义校验维持 §6.2 边界不做。

### 🟠 P2-1 test_semantic_unification.py L49 恒真断言(GPT 属实,且掩盖真实漂移)

L49 原文:`assert sp.output_slots[0].format == sp.outputs[0] or True  # slot 优先`。
**实证漂移**: muscle 的 `output_slots[0].format="fasta"` 而 `outputs[0]="aln"`——移除 `or True` 后该用例立即失败。当前 `output_formats` 属性(slots 优先投影)掩盖了 outputs 字段本身的陈旧。
**修复**: 删除 `or True`,改为断言语义一致性——`sp.output_slots[0].format == sp.output_formats[0]`(slots 为真相的设计),并单独修 muscle 的 `outputs` 字段漂移(或在 spec 构建时统一从 slots 投影 outputs,L1107-1108 已有此逻辑但未覆盖 build_command_specs 全路径)。

### 🟠 P2-2 test_overlay_outputs_syncs_slots 不触达生产代码(GPT 属实)

该测试体仅 3 行:本地构造 `OutputSpec` 列表并断言 `slots[0].format == "svg"`——**纯自证**,不经过 `build_command_specs()`/metadata overlay 加载/KNOWN_OUTPUT_SLOTS 挂接任何一条生产路径。同文件 `test_yaml_output_slots_preserved`(TestF)也是"内联模拟 overlay 逻辑"而非调用生产 overlay 代码(但它至少验证了设计意图;`test_production_slots_semantic_intact` 才真正走 `build_command_specs`,可视为补偿)。
**修复**: 改写为端到端往返——调用 `build_command_specs()`(或 metadata 导出函数)取真实 spec,断言 `output_slots` 与导出 metadata 的 `output_slots` 字段一致;`test_overlay_outputs_syncs_slots` 直接删除或替换为对生产 spec 的断言。
