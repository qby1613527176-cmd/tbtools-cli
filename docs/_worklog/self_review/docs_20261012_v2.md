## 发现

### P1 — agent-protocol.md §6.1「全库 56 条验证证据均 semantic_checked: false」注记与事实直接矛盾

- **位置**: docs/agent-protocol.md:114-117(六轮 product P3 注记, commit 749820f 引入)
- **事实**: `tests/verification_report.json` 59 条 verified_tools 中 **11 条 semantic_checked=true**(barplotter/efpHeat/gsea/kallisto/keggEnrich/microsyn/multiEfp/notung/peakanno/peaktss/plotrna), 与 counts.md `semantic_checked: 11`、代码 `SEMANTIC_CHECKS`(test_conformance_verified.py:213, 11 个内容级断言函数)三源互洽。**全库并非全 false。**
- **注记想解决的问题是真实的**(§6.1 JSON 示例用 volcano 却写 `semantic_checked: true`, 而 volcano 实为 CONFORMANCE 且 semantic=false——示例本身误导), 但修复方式「全库均 false」**矫枉过正成了新的错误事实**: 读 §6.1 的 Agent 会得出「本仓没有任何内容级语义断言」的错误结论, 恰好掩盖了 SEMANTIC_CHECKS 11 工具这一真实分层。
- **建议**: 注记改为「上例以 volcano 为例, 其 CONFORMANCE 条目 semantic_checked=false(金链六步无内容级断言); 全库 11 个 EXECUTION_VERIFIED 工具带内容级断言(semantic_checked=true), 以实际报告/counts.md 为准」; 或把示例工具换成 keggEnrich 等 semantic=true 的真实条目。
- 另注: GPT 提示的「发布记录 34 passed 误读」在本仓未找到对应文本(全仓 grep 无「34 passed」)——实际措辞是「pytest 20 关键 passed」, 见 P2-1。

### P2-1 — CHANGELOG 门禁行「metadata 5」口径不明, 存在误读风险(GPT 关注的门禁数字问题)

- CHANGELOG v1.4.94:「pytest 20 关键 passed(守卫 5+doc 10+metadata 5)」。「关键」二字已表明是**本轮针对性门禁**而非全仓测试数, 方向正确; 但 `tests/test_metadata.py` 实际 collect=**15** 个测试, 「metadata 5」对不上——推测指本轮相关子集(TestAiManifestInheritance 3 + TestVerificationDetailsProjection 1 + test_verified_tools_single_layer 1 = 5), 但文中未注明。
- 对比 v1.4.93 门禁行写「pytest 61 passed(带 JAR)」是可复现全量口径, 本轮 20 的构成不可复现(读者跑 test_metadata.py 得 15, 跑守卫+doc 得 15, 怎么都凑不出 20)。
- **建议**: 补限定语为「本轮针对性门禁: 守卫 5 + doc_consistency 10 + metadata 相关 5 = 20 passed(非全量;全量口径以 CI 为准)」, 与六轮 gate 报告:127 行口径对齐并消除凑数困惑。风险等级 P2(措辞歧义, 非事实错误)。

### P2-2 — GPT 两个 P1(semantic 继承升级 / conformance 静态名单)若属实, 文档层面确实缺警示

- **语义继承升级**: 代码中 `semantic_checked` 由 `_t in SEMANTIC_CHECKS` 每次 render 重算——**继承条目(本次未跑、沿用旧证据)在新加入 SEMANTIC_CHECKS 时会被无证据升级为 true**。这是 verified 视角的实质问题; 文档侧 §6.1 完全没有定义 semantic_checked 的授予语义(「内容级断言跑过」还是「该工具配有断言函数」), 叠加 P1 的「全 false」错注, Agent 无法从文档获得任何正确心智模型。**建议在 P1 注记修正时一并写明授予口径**。
- **conformance 静态名单**: `CONFORMANCE_VERIFIED = {"volcano"}` 为静态集合, 报告顶层 `conformance_verified` 字段**无条件**输出该名单(仅 verified_tools/details 层有 _exec_entries 前置守卫)。文档侧: agent-protocol.md §6.1 完全未提 CONFORMANCE_VERIFIED 层级(全文仅注记里一次「金链」); quickstart.md:52 决策矩阵有「CONFORMANCE_VERIFIED(金链)…volcano 标杆」一格但无「静态名单/试验层 n=1」说明——报告 JSON 内的 `verification_tiers_note` 倒是写明了「试验层(n=1)暂无第二批推广」。**建议 agent-protocol.md §6.1 补一段三层体系说明(EXECUTION/CONFORMANCE 定义、volcano 静态试验层、语义断言授予口径), 在 verified 修复落地前把「层级≠证据强度超集」与「n=1 试验」两个既有 code note 提升到文档层**, 避免 Agent 按层级直觉过度信任。
