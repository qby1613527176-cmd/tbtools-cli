## 二、发现

### P1 — GPT P1「conformance 继承不可达」**CONFIRMED**, 且 CHANGELOG v1.4.95 表述与代码事实不符

**代码实证**(tests/test_conformance_verified.py L392-394):

```python
_gold = _CONFORMANCE_RESULTS.get(_t)          # 金链 skip 时 = "skip"/None
_old_conf = (_t in _verified_tools and _verified_tools[_t].get("level") == "CONFORMANCE_VERIFIED")
_allow_conf = (_gold == "pass") or _old_conf
```

`_verified_tools` 在 L361 起由 `_exec_entries` **全新构建, 所有条目 level 一律先写 EXECUTION_VERIFIED**(L363)——`_old_conf` 查的是新 map, **永远为 False**; 真正该查的旧报告 `_old_verified` 从未被用于等级继承。故「金链 skip + 旧报告已是 CONFORMANCE_VERIFIED → 继承保金链级」路径**不可达**。

**机器证据**: 本机无 JAR → 金链 skip → `_want_conf={}` 与报告 `_cur_conf={'volcano'}` 不一致 → `test_report_counts` 红(但报错只打印 exec 差集 `缺 [] 多 []`, conf 差集不显形, 诊断信息有盲区)。若在无 JAR 环境以 `TBTOOLS_WRITE_REPORT=1` 写盘, volcano 会被**静默降级**出金链名单——CHANGELOG v1.4.95 承诺的「或继承旧金链证据」在写盘路径不成立。

**docs 视角判定**:
- (a) CHANGELOG v1.4.95 第 2 条 bullet「升级须金链 pass 或继承旧金链证据」**与代码行为不符**, 需修正措辞或待代码修复后验证;
- (b) 守卫 9/9 的 `test_conformance_no_upgrade_without_golden_chain` 只盖「无旧证据+无金链观测」方向, **缺「旧金链证据+金链 skip → 继承保持」对照测试**——正是本 bug 的逃逸窗口;
- (c) §6.1(agent-protocol.md)**完全没有描述 CONFORMANCE_VERIFIED 层的继承/skip 语义**——quickstart L52 三等级表列出金链层, 但金链 skip 时等级行为(应保旧级/降级/拒绝写盘)无任何文档说明。代码修复落地后 §6.1 应补一段「金链 skip 时 CONFORMANCE_VERIFIED 继承语义」, 否则 Agent 读方无法预知无 JAR 环境的等级读数。

### P2 — v1.4.95 门禁行缺「本轮针对性子集, 非全量」限定

v1.4.94 段(L27)已有显式限定「(本轮针对性子集, 非全量): pytest 34 passed(守卫7+doc10+metadata15+cli2)」; v1.4.95 段门禁(L14)改为「pytest 守卫 9/9 + doc 10 + metadata 19」——**拆子集罗列、不再出现总计数字 38**, 部分防误读; 但**未保留「非全量」限定词**, 读者自行加总 9+10+19=38 后仍可能误读为全量套件(全量在无 JAR 环境实为 65 passed+1 failed, 带 JAR 更多)。GPT「38 非全量」提示只防住了一半。建议门禁行补「(本轮针对性子集, 非全量)」前缀, 与 v1.4.94 口径一致。

### P3 — test_report_counts 报错信息不打印 conf 差集

只读校验漂移时仅打印 exec 的 `缺/多` 差集; 本次实际漂移在 conf 集(`{}` vs `{'volcano'}`), 报错却显示「缺 [] 多 []」, 排查者需手动重算 `_want_conf` 才能定位。属 verified 域的诊断质量问题, docs 记录在此供对应视角认领。
