## 🔴 结论一：GPT P1「_content_compat protein↔dna 误兼容」——**属实，定级 P1（确认）**

### 1.1 代码事实

`tbtools_cli/workflow.py` L382-433 `_content_compat()` 的 **slot 级配对路径**（L400-414）：

```python
for _os in _a_spec2.output_slots:
    for _is in _b_spec2.inputs:
        if _os.content_type != "generic" and _is.content_type != "generic":
            if _os.content_type == _is.content_type:
                return True
            if "table" in (...):
                return True
            if {_os.content_type, _is.content_type} <= {"alignment", "protein", "dna"}:
                return True          # ← L409：问题行
```

L409 的集合条件 `{a, b} ⊆ {alignment, protein, dna}` 是**对称且无方向**的：它不仅放行 `alignment↔protein` / `alignment↔dna`（设计意图：比对结果可回接序列工具），**也放行 `protein↔dna` 这对生物学上非法的方向**。

**架构层面的关键反差**：同一函数的**工具级兜底路径**（L424-433）写得是对的——

```python
if ca == "alignment" and cb in ("protein", "dna"): return True
if ca in ("dna", "protein") and cb == "alignment": return True
return False                        # protein↔dna 直达 → False
```

即：兜底路径只允许 alignment 作为桥，protein↔dna 显式拒绝。slot 级路径（L409）与兜底路径（L424-433）**同一函数内两套语义互相矛盾**，slot 级路径先命中所以 bug 只在"两侧都有 slot 级标注"的工具对上暴露。这是典型的"后加的快路径绕过了旧路径的不变量"。

### 1.2 实证（真实 specs 数据 + 逐行复制的真实实现）

| A → B | A 输出语义 | B 输入语义 | 实测 | 生物学正确 | 判定 |
|---|---|---|---|---|---|
| sixframe → longestorf | protein | dna | **True** | False | ❌ 误兼容（蛋白序列进 ORF finder） |
| sixframe → blastn | protein | dna（工具级，无 schema） | False | False | ✅（兜底路径拦截，侥幸正确） |
| pep2codon → recipBlast | dna(cds) | protein（slot 标注 query/subject） | **True** | False | ❌ 误兼容（CDS 核酸进蛋白比对） |
| pep2codon → hmmsearch | dna | protein（工具级） | False | False | ✅ |
| pep2codon → blastn | dna | dna | True | True | ✅ 合法不受影响 |
| sixframe → recipBlast | protein | protein | True | True | ✅ 合法不受影响 |
| muscle → trimal / iqtree | alignment | alignment | True | True | ✅ |
| muscle → blastp | alignment | protein | True | 存疑 | ⚠️ 桥语义（见 1.4） |

附带的反向失真（新发现，GPT 未提）：`sixframe → muscle` 实测 **False**——muscle 输入标注 `content_type="sequence"`（评审 #98 为表达"DNA+蛋白双兼容"引入的非枚举值），`{protein, sequence}` 不在三元集合内且两侧都有标注 → 落入 L411-414 "有标注但无兼容对 → False"。**蛋白进 muscle 是合法操作却被判冲突**。即同一行代码同时造成误兼容（protein↔dna）与误拒绝（protein→sequence）。`sequence` 作为"泛序列"语义在兼容矩阵里没有位置，是标注体系的第二处结构性缺口。

### 1.3 与项目自身测试的冲突

`tests/test_semantic_unification.py` L58-84（TestC_BindingResolver）：

- `test_dna_into_protein_rejected`（L70-77）：构造真实 DNA FASTA，要求 `resolve_input_binding(..., content_type="protein")` 返回 `INCOMPATIBLE`——**绑定期必须拒绝 DNA 进蛋白槽**；
- `test_dna_into_dna_exact` / `test_protein_fasta_exact`：同类内容必须 EXACT。

结论：**绑定层（文件内容嗅探）严格执行 protein/dna 不互通，规划层（`_content_compat`）却判定兼容**。同一仓库两个语义层对同一问题给出相反答案——规划器会把 `sixframe→longestorf` 这种链当成"无冲突"（不触发 L643 的 `content_type_conflict` -0.3 罚分），而执行时绑定层又会拒绝或降级。层间不一致 = 规划结果不可信。GPT 指出的冲突成立。

### 1.4 正确的兼容矩阵（架构评估）

设显式转换工具存在（sixframe: dna→protein；pep2codon: protein_alignment+dna→cds 等），则**隐式兼容**应收窄为：

| 输出 \ 输入 | dna | protein | alignment | sequence(泛) |
|---|---|---|---|---|
| **dna** | ✅ | ❌（须显式 sixframe 类转换） | ❌* | ✅ |
| **protein** | ❌ | ✅ | ❌* | ✅ |
| **alignment** | ⚠️ | ⚠️ | ✅ | ✅ |
| **sequence** | ✅ | ✅ | ❌ | ✅ |

- `alignment↔序列` 桥本身也值得收紧：alignment 是**多序列比对**（等长、带 gap），直接当裸序列输入很多工具是错的（iqtree 吃 alignment 是对的，blastp 吃 alignment fasta 只是"碰巧能读"）。GPT 建议保留 alignment 桥，我的架构意见是降级为 **weak/compatible（不罚但也不给满分信号）**，至少 protein→dna / dna→protein 必须硬拒绝。
- `sequence`（泛序列）需要进入矩阵作为**通配兼容**项（与 dna/protein 均兼容），否则 muscle 这类双兼容工具持续误伤。
- 显式转换工具（sixframe/pep2codon）存在的意义就是**把类型变更做成图上的显式节点**；`_content_compat` 越俎代庖做隐式转换，等于让规划器绕过了这些节点的成本与可见性。

### 1.5 修复方案 + 测试设计

**最小修复（workflow.py L409 一处）**：

```python

_pair = {_os.content_type, _is.content_type}
if _pair <= {"alignment", "protein", "dna"}:
    # protein↔dna 非法；仅 alignment 参与桥接
    if _pair == {"protein", "dna"}:
        pass  # 不 return True,留给"无兼容对"判定 → False

        return True
if "sequence" in (_os.content_type, _is.content_type):
    return True  # 泛序列槽双向兼容
```

## 🟠 结论二：GPT 风险 2「规划器启发式搜索边界」——**属实，定级 P2（部分已缓解，残留真实缺口）**

### 2.1 现状核实

正面（本轮实测）：

- 无意义 goal（`"quantum entanglement teleportation"` / `"xyzzy nonsense goal zzz"`）→ **返回空 plan + confidence 0.0**，不会强行拼链。规划器并非"为给答案而拼接"。
- 评分体系已是 reasons-based（L566-646），含 `irrelevant_start` -0.2、`shell_manual` -0.25、`passthrough_*` 罚分、`content_type_conflict` -0.3——软性抑制已有多层。

残留缺口（实证）：

1. **`rejected` 字段是死代码（新发现，GPT 未提）**：返回结构 L730-736 的 rejected 推导式过滤条件为 `_bindability(n) == "UNEXECUTABLE"`，但 L455-463 的 `_bindability` 三态只返回 `EXECUTABLE / PARTIALLY_BINDABLE / MULTI_INPUT`——**"UNEXECUTABLE" 字符串在评审 #82 重构后从返回值中消失，过滤条件永不命中，`rejected` 恒为 `[]`**（实测确认）。也就是说：对 Agent 宣称的"拒绝可见性"实际为零输出。这正好是 GPT 建议的"拒绝原因"机制的预埋位——字段存在、协议存在、生产逻辑死了。
2. **拒绝无显式信号**：空 plan 与"找到但置信 0"不可区分；`confidence=0.0` 没有任何 reason 说明"为什么拒"（goal 无命中工具？输入格式无起点？）。Agent 消费端只能猜。
3. **content_type 冲突仍是软罚分**（L641-646，-0.3 且 `break` 只记一次）：误兼容链（结论一）不触发该罚分；即使触发，-0.3 可被 `all_contract_edges`+契约边加分淹没。对"生物学非法链"而言软罚分不够硬。

### 2.2 最小增量方案（不做大重构，低成本高价值优先）

| # | 改动 | 成本 | 价值 |
|---|---|---|---|
| R2-1 | 修 `rejected` 死代码：条件改为 `_bindability(n)=="MULTI_INPUT" and _bind_slots_local(...) is None`（与评分路径 L653-663 同一判定），恢复拒绝可见性 | 极低（一处） | 高：GPT 要的"拒绝原因"机制 70% 已存在，只差这一行 |
| R2-2 | 空 plan 时填 `confidence_reasons=["no_goal_matching_tool"]` / `["no_start_accepts_input_format"]`（二选一诊断） | 低 | 高：拒绝可解释 |
| R2-3 | `content_type_conflict` 从软罚分升级为**硬过滤**：DFS 扩展后继时（L523-537）对 `_content_compat(cur,cand) is False` 的候选直接不入 `nexts` | 低 | 高：非法链根本不生成，比事后罚分可靠；与结论一修复联动 |
| R2-4 | 类型转换记录：`_reason_for` 对 content_type 变化的边追加 `(type: dna→protein via sixframe)` | 低 | 中：满足 GPT "类型转换记录"诉求，Agent 可见 |

不建议本轮做：硬性前置条件 DSL、不可满足条件形式化——那是大重构，且当前 goal 语义全靠词根匹配，先补拒绝可见性收益更大。

## 🟠 结论三：GPT 风险 3「Artifact 身份/内容/验证状态生命周期」——**属实，定级 P2**

### 3.1 现状核实（artifact.py + executor.py）

`Artifact` dataclass（artifact.py L36-48）字段：`id / type / format / path / uri / size / sha256 / producer / created_at / schema_version / metadata`。

- **内容身份** ✅ 已分离且做得好：`id=art_<sha256[:32]>`（L104，同内容同 ID，支持去重/resume）；`resolve()`（L176-199）做 stale 检测（文件消失或 sha256 漂移 → 拒绝解析）。十八轮已修压缩扩展名分类（classify L57-69）。
- **产生过程** ✅ 分离：provenance 在 `<artifact>.tbtools.json` 侧车文件，`from_provenance()`（L88-101）重建时把 invocation/exit_code 等塞进 metadata。
- **验证结论** ❌ **不在模型里**：`validate_artifact()`（executor.py L440-491，十八轮成果，解析级校验）的结论只以 `validation_warning` 字符串存在于**步骤返回 dict**（executor.py L257），不落 Artifact 对象、不进登记索引（`register()` L131-172 写入的 entry 无 validation 字段）。

**时序问题（关键实证）**：executor.py L216-230 先 `build+register`，L231-237 才 `validate_artifact`——**登记先于验证，且验证失败只翻转 `step_ok=False`，已登记的 artifact 不撤回、不标注**。后果：一个 `validation failed` 的产物在 `~/.config/tbtools-cli/artifacts.json` 里与合格产物**不可区分**，下游 `resolve()` 照样解析成功。这正是 GPT 说的"文件存在/哈希一致被理解为科学上正确"的精确机制：sha256 只保证"内容没变"，不保证"内容是对的"。

### 3.2 成本收益与最小方案

收益明确：验证状态随 artifact 持久化后，规划器/Agent 复用旧产物（resolve 命中缓存）时能区分"验证过"与"从未验证/验证失败"，与 verified 视角「登记先于验证」的修复形成闭环（verified 改时序，arch 这里改持久化——两者正交互补：单改时序不持久化，跨会话复用仍盲区；单持久化不改时序，登记瞬间仍是未验证态）。

最小方案（两处小改）：

1. `Artifact` 增字段 `validation: dict = field(default_factory=dict)`（`{"status": "passed|failed|unchecked", "detail": str, "validated_at": iso}`，缺省 `unchecked`）；`register()` 的 entry 同步带上 `validation.status`。
2. executor.py 执行路径：validate 后**回写**——`_a.validation = {...}` 再 register（或 register 后按 art_id 二次更新索引）。顺序改为 build → validate → register（带结论），消除"未验证态登记"窗口。

成本：dataclass 一个字段 + register/executor 各几行；向后兼容（缺省 unchecked，旧索引条目按 unchecked 处理）。测试：①验证失败的产物登记后索引中 `validation.status=="failed"`；②`resolve()` 命中 failed 产物时返回路径但调用方可见状态（本阶段不改 resolve 拒绝语义，避免破坏 resume——那是下一步决策）。

定级 P2：不阻塞正确性的主路径（执行期 step_ok 已翻转），但跨会话复用链路有实质性误导风险。
