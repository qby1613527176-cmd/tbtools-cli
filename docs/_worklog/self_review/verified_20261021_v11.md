## 发现

### P1（证实 GPT 红队 P1，四项子claim 全部属实）— workflow-plan 配方种子链边零校验

代码位置：`workflow.py` plan_from_goal 种子注入段（`plans.append((_chain, [("recipe", None)] * len(_chain)))`）与 `_score`。

探针实证（注入配方 `volcano → muscle → nonexistent_tool_xyz → iqtree`，goal="probe-evil"）：

- **(a) 相邻工具不验证契约边 — 属实**。volcano 产出 `svg/volcano_plot`，muscle 接受 `fasta`——格式完全不兼容，但链整体被接受进 plans 并作为 best 返回（plan=[volcano,muscle,iqtree]）。种子注入时**不调 `_edge()`/`_edge_info()`**；唯一防线是 _score 里 content_type 冲突罚 -0.3 与 irrelevant_start -0.2（本探针 confidence=-0.1 已很低，但**若配方内工具与 goal 词面命中，recipe_seed +0.4 + name/capability 加分可盖过罚分，不兼容链仍可胜出**）。契约图 DFS 路径每条边都过 `_edge()`，配方种子路径一条不过——双标。
- **(b) `("recipe", None)` 被当真实边评分 — 属实**。`contract_edges = sum(1 for f in fmts if f and f != "relation")`：tuple 恒 truthy 且 ≠ "relation" → 全部计入契约边。4 步链 contract_edges=4 → 深管线加分 +0.20（应 +0）；同时 fuzzy 检查里 tuple 不在 inputs.format 列表 → 每条再罚 -0.05。加罚相抵是**巧合不是设计**，且 `fmts.index(f)` 对重复 tuple 恒返回 0，fuzzy 全部错查 chain[1] 的 inputs（次生 bug）。
- **(c) fmts 长度 off-by-one — 属实**。DFS 链 fmts 长 = len(chain)-1（边数），配方种子为 `[("recipe", None)] * len(_chain)` = len(chain)。下游 `_fmts_padded = [None] + fmts` 后与 chain zip 截断，**展示层无恙**；但 _score 的 `all_contract_edges`（== len(chain)-1）对配方链**永不触发**（len(chain) ≠ len(chain)-1），行为不一致。
- **(d) 未知工具静默过滤 — 属实**。`_chain = [c for c in _chain if c in specs]`：nonexistent_tool_xyz 无任何 warning/报错被丢弃，链静默从 4 步缩到 3 步——配方文件写错工具名零可见性（workflows.json 当前无校验器，load_workflow 的 Layer 2 工具存在性校验不覆盖配方种子路径）。

**修复方案**（供 product 视角评审）：
1. 种子链每相邻对过 `_edge_info(a, b)`：无契约边且无 legacy_relation → 丢弃该链并 `warnings.warn`（或降级 confidence 并在 confidence_reasons 记 `recipe_edge_invalid: a→b`）；
2. fmts 改为 `len(_chain) - 1`；评分循环对 `("recipe", None)` 边显式跳过 contract/fuzzy 计数（用专用标记而非混入 fmts）；
3. 未知工具：`warnings.warn(f"recipe {id} 引用未知工具: {name}")` 而非静默 filter。

### P2（证实 GPT 红队 P2，两项子claim 属实，严重度维持 P2）— positional 无线程槽位声明 + 0/负数无校验

- **positional 槽位 — 属实（设计缺口，非现行 bug）**。`thread_args` positional 分支只 `[str(threads)]` append 到 args 末尾，注释自承「槽位由工具 impl 解析」。契约层（CommandSpec.thread_style）只有三态枚举，**无 thread_slot 位置字段**。实证：当前 4 个 positional 工具（parallelMD5Check/tfbsShift/mcscanxd/quickAnno）的用户面向用法里 threads 恰好都是「必填位置参数之后第一个可选位」，append 语义碰巧全对；但 mcscanxd 有 `[threads] [blastHits] [evalue]` 三可选位——**若 CLI 未来暴露 blastHits/evalue 给用户直填，append 的 threads 会落错槽**，契约无字段可表达该约束。
- **0/负数无校验 — 属实**。click 层 `{"type": int}` 无 IntRange；`thread_args("muscle", 0)` → `["--threads","0"]`、`("muscle", -1)` → `["--threads","-1"]` 直透引擎。缓解：parallelMD5Check impl 层 `isdigit()` 能拦 `-1` 但**拦不住 `0`**（`"0".isdigit()==True` → 透传 java）；named_flag 路径（muscle 等）引擎层裸收 -1。
- **修复方案**：① cli_load click option 加 `type=click.IntRange(1, None)`（一行，统一拦截，含 0）；② CommandSpec 加 `thread_slot: int | None = None` 字段（声明 threads 应插入的位置序号），positional 分支按槽位 insert 而非 append——或最低限度文档化「positional=append 仅在 threads 是第一个可选位时正确」约定并把 4 个工具用法冻结进测试。
