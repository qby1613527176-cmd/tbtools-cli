## 逐项发现（新增 + 未闭环）

### N1. README 权威源行指向不存在字段：`tool-describe --json` 无 `verification_details` —— P1（新增）

**发现**：README L19 权威源行写"execution_verified(54, 其中 semantic_checked 10=内容级断言, **详见 `tool-describe --json` verification_details**)"。实测 `tbtools tool-describe kallisto --json` 输出键列表：
`$schema/availability/capabilities/class/dependencies/group/help/id/inputs/invoke/kind/name/outputs/pitfall/platforms/readiness/relations/schema_version/semantic_fingerprint/uri/verification` —— **无 `verification_details`**。代码确认：tool_describe（cli_top.py L611+）读 command_metadata.json，而 verification_details 只由 gen_metadata 写入 `ai/tools/<group>/<name>.json`，从未进 metadata entry；`tbtools_cli/` 全仓 grep 无第二个 verification_details 投影点。

**挑战**：红队 P1-4 的闭环标准是"读者沿权威源可查证证据分层"。当前 README 把读者引到一条没有证据的通道——Agent/用户跑 tool-describe 拿 `verification: EXECUTION_VERIFIED` 裸标签，env_fp/semantic_checked/domain_note 一概不可见，只能去翻 ai/tools/*.json（而 README 没提这个路径）。标签分层在"静态投影层"成立、在"运行时 CLI 层"断裂。这恰是 v1.4.81 P1-3 想消灭的"双世界"问题，只是换了个界面残留。

**建议**（二选一，不改模型）：① tool_describe 增加 verification_details 投影（从 verification_report.json 直读或渲染时进 metadata entry，与 ai/ 同源）；② README 改指向 `ai/tools/<group>/<tool>.json`。①更符合"CLI 是一等公民"的既有架构取向。

**严重度**：P1（权威源可查证性断裂；非模型缺陷，是通道缺陷）

---

### N2. ai/tools/*.json 存在潜在自相矛盾面：contract/env 漂移后 `verification` 与 `verification_details.level` 会分叉 —— P2（新增）

**发现**：render_ai_manifest 中 verification_details **无条件**从 report 投影（`_verif_details_map.get(name)` 有就挂）；而同文件顶层 `verification` 字段来自 metadata entry 的 verification_level()——加载侧有 contract_fp/env_fp 双比对，失配即降级。后果：契约变更后、重跑验证前的窗口期，同一 JSON 文件会出现 `verification: "COMPILEABLE"` + `verification_details.level: "EXECUTION_VERIFIED"`（旧证据）并存。

**挑战**：当前未触发（54 个 fp 全匹配，实测零差异），但这是 P1-3 投影设计里埋的时序矛盾：verification_details 内部携带的 level 与顶层 verification 语义不同步，下游消费者若读嵌套 level 会拿到过期结论。证据对象里其实已有 contract_fingerprint——消费者**可以**自己比对发现失配，但没有任何注释说明"嵌套 level 是报告时快照，当前判定看顶层"。

**建议**：二选一——① verification_details 去掉冗余的 `level` 字段（证据对象只留指纹/时间/语义标记，level 判定唯一由顶层承担）；② 投影时加 `"level_as_of_report": true` 类标注或注释。倾向①，最符合"单一判定源"。

**严重度**：P2（潜在态，当前数据不触发）

---

### N3. env_fingerprint 全局耦合的爆破半径无用户侧文档 —— P2（新增）

**发现**：engine_env_fingerprint() 是**全局单值**（JAR + plugins/lib 全部 jar + KNOWN_DEPENDENCIES_STRUCT 派生的全部外部二进制），写入每个工具的 evidence；加载侧 `_env_now != _old_env → discard`——**任何一个**外部二进制（如 muscle）升级，54 个工具的验证**全部**降级，包括与该二进制无关的工具。且降级只在"有 JAR 的环境"发生：用户机器装了 JAR 但二进制版本与验证机不同 → `tbtools version --json` 的 execution_verified 几乎必然低于发布的 54。

**挑战**：保守降级本身是诚实设计（"验证证据绑定具体引擎本体"），identity.py docstring 也有说明。但用户侧面（README/counts.md）没有任何一句"verification 标签是环境绑定的，你机器上的计数可能低于发布值"。发布的 54 是验证机环境的属性，README 把它读作产品属性。另外全局单值指纹让"换 muscle 降级 kallisto 证据"成为制度性误伤——per-tool 依赖子集指纹会精确得多，但这属于模型增强，**与冻结决定冲突，仅记录不推荐现在做**。

**建议**：README/文档补一句环境绑定说明即可（文档级修复，不动模型）。

**严重度**：P2

---

### N4. README "semantic_checked 10" 为手写硬编码，无测试守卫 —— P2（新增）

**发现**：README L19 的"10"是静态文本；counts.md（自动防漂移的权威数字文件）**不含** semantic_checked 计数；test_doc_consistency.py 仅 2 个测试（mcp_count / full_count），均不覆盖该数字。SEMANTIC_CHECKS 增删一条，README 静默漂移——而这行恰是 P1-4 要求的"动态口径"落点，实际是静态的。

**建议**：counts.md 增加 `semantic_checked: N`（gen_metadata 从 report 的 verified_tools 动态统计，一行代码），README 引用之；或 doc_consistency 加断言。同属文档级修复。

**严重度**：P2

## 关于 CONFORMANCE_VERIFIED 的一点语义皱褶（记录，不列级）

volcano（唯一 CONFORMANCE_VERIFIED，最高层）的 `semantic_checked: false`——金链断言（artifact 类型/sha256/provenance/artifact_id 六步）不含内容级断言，而 10 个 EXECUTION_VERIFIED 工具有。层级高低 ≠ 证据强度超集，与直觉相反。tiers_note 已限定"勿按三层全满解读"，未声称语义超集，故不构成矛盾；但 Agent 按"高层=更强"直觉读时会误判。若未来金链推广，建议把内容断言纳入升级条件（届时再议，现冻结期内仅记录）。

## 冻结判定支持意见

本轮未发现需要新增层级或改动 evidence 字段集的问题——所有 P1/P2 均在"投影通道/文档/测试下限"层面，模型本身（level × {contract_fp, env_fp, verified_at, corpus, semantic_checked, domain_note}）语义自洽、读写双侧对称（无 JAR 不刷新/不降级的设计闭环实测成立）。**支持红队的冻结建议**。唯一必须在冻结期内修的是 N1（权威源通道断裂），其余可排入常规迭代。
