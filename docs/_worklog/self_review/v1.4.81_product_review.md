## 本轮新增/未闭环发现

### P1-1. README 英雄行 294 与动态权威源 298 直接打架
- **发现**：README L5/L17 写 `294 Agent-facing tools`、`Registered 294(version --json 实时统计)`；实测 `tbtools version --json` → `metadata_commands: 298`，`docs/_generated/counts.md` → 298，`gen_metadata --check` → 298。294 是 v1.4.81 提交（7acc312）把 counts.md 从 294 改为 298 后**未同步的静态残留**；且 298 无法用任何合法口径解释（非别名：别名 8 个，去别名 290）。
- **挑战**：v1.4.81 的主题就是"叙事诚实化"（P1-2/P1-4），而英雄行第一句数字就是错的，且同一行括号里写着"version --json 实时统计"——读者照做立刻看到 298，信任损伤发生在第 30 秒。这正是旧 F4 的同类问题在"已宣称修复"后的复发。
- **建议**：README 的 294 全部改为"见 `tbtools version --json` metadata_commands"或构建期注入；`gen_metadata --check` 已有"README 含版本号"校验，扩展为"README 英雄行数字 ∈ counts.md 数值集"断言。

### P1-2. README 指向 `tool-describe --json verification_details`，但该字段不存在
- **发现**：README L19 写"execution_verified(54, 其中 semantic_checked 10=内容级断言, 详见 `tool-describe --json` verification_details)"。实测 `tbtools tool-describe volcano --json` 输出**无 verification_details 字段**（cli_top.py:640-687 的 desc 字典逐字段构建，从未投影它）；grep 全仓库，verification_details 只存在于 ai/tools/*.json（gen_metadata.py:562）与 README 这一行指针。docs/agent-protocol.md 也未提及该字段。
- **挑战**：P1-3（证据投影）在 schema 层确实闭环了（7 字段齐全：level/contract_fingerprint/env_fingerprint/verified_at/corpus/semantic_checked/domain_note ✓），但 README 把 Agent 引向一条死路——CLI 主入口拿不到证据对象，Agent 只有去读仓库内 ai/tools/*.json 才能区分"跑过"vs"跑过+内容级检查"，而这违反"CLI 即协议"的设计。且 10/54 是手写数字，verification_report.json 更新后 README 即漂移。
- **建议**：tool-describe --json 增加 verification_details 投影（数据源 command_metadata.json 已有 verification 字段，从 tests/verification_report.json 同源注入）；或 README 指针改为 `ai/tools/<group>/<cmd>.json`。semantic_checked 计数进 counts.md/version --json（见 P2-4）。

### P1-3. dry-run 的 estimated_artifacts 仍把输入文件列为产物（F1 未闭环子项）
- **发现**：`tool-run --dry-run --json expr volcano examples/data/deg.txt /tmp/out.svg` → `estimated_artifacts: ["examples/data/deg.txt", "/tmp/out.svg"]`——输入 deg.txt 被估为产物。根因：dry-run 的 `_OUT_EXTS`（cli_top.py:818）**包含 .txt/.tsv/.csv**，而同函数 60 行后的执行预检 `_OUT_EXT_PRE`（cli_top.py:876）**显式排除**它们，注释写明".txt/.tsv/.xls 等既可能是输入也可能是输出， 不预判"——同一文件内两套启发式自相矛盾。
- **挑战**：旧 F1 明确点过"estimated_artifacts 把输入列为产物"，本轮只修了 tool 字段，产物预估子项原样保留。Agent 规划时会等待一个永远不会被"产出"的产物（它是输入），依赖图建错。
- **建议**：dry-run 与执行预检共用同一份输出槽判定（抽取共享常量/函数）；有 inputs 契约的 FULL 工具应按契约 role 判定而非扩展名猜测。

### P1-4. `list tools --json` 静默返回空清单（count: 0, exit 0）
- **发现**：`tbtools list tools --json` → `{"category":"tools","commands":[],"count":0}`，exit 0。根因：--json 输出是**正则刮取人读文本行**（cli_top.py:1763 `^    (\S+)\s{2,}` 要求 4 空格缩进），而 tools 分支用 2 空格缩进（`f"  {cmd:20s} {short}"`）——plots 分支恰好 4 空格所以幸存。rpc 分支同样不匹配。
- **挑战**：F5 修复只验证了 plots 路径。Agent 按文档用 `list tools --json` 发现 CLI 工具，拿到空数组且无错误——比报错更糟，Agent 会得出"没有工具可用"的结论。人读输出同一时刻显示"共 191 个工具"，人机两视图事实相反。
- **建议**：--json 改为从数据源直接构建 records（循环时同步收集 dict），废弃文本刮取；补三个类别的契约测试（count>0）。

### P1-5. 非 --json tool-run 无输入预检：缺失输入 → TB009"engine-level defect" + 错误 exit 1 + help 提示缺 group 前缀
- **发现**：`_pre_probs` 处理仅在 `if _pre_probs and as_json:` 分支（cli_top.py:904）。非 --json 下 `tool-run expr volcano /nonexist.txt /tmp/out.svg` 直接进引擎，输出 `💡 engine-level defect; see PITFALL/docs`（TB009 的 action 文案）、`📖 tbtools volcano --help`（缺 `expr` 前缀，照做撞未知命令——旧 F3 子项未闭环）、exit 1。quickstart 退出码表承诺"2 = 文件缺失"。
- **挑战**：人机协议分裂——同一错误，Agent（--json）拿到 TB002/exit 2/修路径建议，人类拿到 TB009/exit 1/"引擎缺陷，看 PITFALL"。文档承诺的退出码契约只在 --json 下成立。
- **建议**：预检提前到 stdout 重定向与 as_json 分支之前，非 --json 路径输出人读版 TB002 提示（含正确 group 前缀 help 行）并 exit 2。

### P2-7. 退出码/错误码叙事两处混乱
