## 发现

### P0-1(本轮新发现, GPT 未抓到): tool-submit/job 异步链路全断——v1.5.0 已发布(GitHub+PyPI)的功能回归

**现象**: v1.5.0 全量套件 3 failed(全在 test_jobs.py); 任何 `tool-submit` 提交的任务终态恒为 `failed / exit_code -1`, 即使实际命令成功执行(version 输出完整写入 .log)。

**根因**(独立定位, `git diff 635bdb9^ 635bdb9` 确证): 十二轮 product P3「UTC 统一」改了 `cli_top.py` 3 处 + artifact 1 处, 其中一处是 `_JOB_MONITOR` ——这是一段通过 `python -c` 在**独立子进程**执行的字符串模板, 模板首行只 import 了 `subprocess, sys, json, os, signal, time, traceback`。改动把模板内 `time.strftime('%Y-%m-%dT%H:%M:%S')` 替换成 `_utc_now_iso()`, 但该函数是 cli_top.py 的模块级函数, **子进程命名空间里不存在** → monitor 在 `job['finished_at'] = _utc_now_iso()` 抛 NameError(line 18) → 终态 dump 永不执行 → job 停在 running → `job-status` 惰性判②(pid 消失 + version 无图形 provenance)→ `_job_finish(job, "failed", -1)`。

**机器证据**:
- `~/.config/tbtools-cli/jobs/job_*.err` traceback: `NameError: name '_utc_now_iso' is not defined`
- job JSON: `status: failed, exit_code: -1`, 而 .log 内容完全正常
- test_jobs.py 3 失败(test_submit_success / test_job_result_structured / test_job_clean_keeps_running)

**gate 视角的元问题(比 bug 本身更重要)**: 本轮改动面 = cli_top.py 的 job 代码, 而发布门禁 48/58 两个 targeted 子集**都不含 test_jobs.py**——「改的面 ≠ 跑的面」错配在 v1.5.0 原样重演, 而 v1.5.0 CHANGELOG 第一条恰恰宣称「发布门禁改的面/跑的面盲区实证」已修复。**构成式模板只解决了"数字怎么算", 没解决"跑哪些"——子集选择仍无"改动面 → 必测文件"映射规则。**

**暴露面**: GitHub Release + **PyPI 1.5.0 均已公开**。tool-submit 是 Agent 长任务入口(cli_top docstring 自述), 属核心 Agent 面。

**处置建议**: ① monitor 模板内改回自包含实现(`time.strftime` 或模板内 `__import__('datetime')`); ② 立即 v1.5.1 hotfix(GitHub+PyPI); ③ RELEASING 前置门禁增加规则: **diff 触及的源码文件 → 映射必跑测试文件清单**(最低: cli_top.py ↔ test_jobs.py/test_cli.py, 写入器 ↔ 守卫), 或发版前全量必须绿(有 JAR 本机跑一次, 370s 可接受)。

### P1-2: v1.5.0 HEAD 全量套件红(3 failed)与 CHANGELOG「全量套件修复」宣称矛盾

CHANGELOG v1.5.0 首条:「v1.4.99 全量 pytest 红(661/1 FAILED)已修复」。实测 HEAD 全量 = 660 passed/**3 FAILED**。锚点守卫那个红确实修了, 但同一轮自己引入的 P0-1 造成新的全量红, 且发布前无人跑全量(Release gate 仍是 targeted 子集)。RELEASING.md「前置」节写的 `pytest tests/ -q` 全绿要求**本版未执行**——SOP 存在但没遵守, 与 P2-3 的构成式问题同根: 模板/规则落地后首版即未对照执行。建议 RELEASING checklist 每项加「实跑命令+粘贴输出末行」的强制证据位。

### P2-3(GPT P2 核实: 属实, 且比 GPT 所述更重): 58 vs 48 口径 + 构成式与实际命令不符

GPT 称「Release 58 vs CHANGELOG 48 未说明」。独立复现结论:

- **两个数字都能机器重建**(见核验表 #5/#6): 48 = 守卫15+doc10+metadata15+**packaging7+registry1**; 58 = 守卫15+doc10+metadata15+**parallel11+packaging7**。两 runs 差异 = Release 侧 +parallel_conformance(11) −registry_discipline(1), 48+11−1=58 ✓。
- **但 CHANGELOG 自己的构成式是错的**: 文本写「守卫 15 + doc 10 + metadata 15 + README 结构/计数 + 并行 conformance」——若真含并行 conformance(11 个全过, 本机实测), 总数 ≥51, 不等于 48。「README 结构/计数」对应哪个文件无从指认(实际跑的是 packaging+registry)。即: **构成式要求已写进 RELEASING 模板, 但 v1.5.0 的 CHANGELOG 构成式无法重建所报数字**——读者按文本组命令得不到 48。
- **Release notes 完全没执行模板**: 只一行「pytest 58 passed」, 无构成式、无「与 CHANGELOG 48 的命令/范围差异」说明(RELEASING L27 明文要求)。
- **校验方案**: ① RELEASING 第 2 步加硬规则——构成式每个加数必须写成可执行命令片段(如 `::TestEvidenceWriteGuard(15)`), 发布前把构成式拼成一条 pytest 命令实跑, 末行数字 = N 才准发; ② Release notes 与 CHANGELOG 用**同一条**构成式, 若另跑更大集, 必须附命令与差集说明; ③ 可加机器校验: 小脚本解析 CHANGELOG 门禁行的构成式求和 == N(纯文本 lint, 纳入 doc_consistency 守卫)。

### P2-4(GPT 整体评价核实: 属实): 发布记录内部审查用语

- CHANGELOG v1.5.0 整段以「第十二轮五视角自审全闭环」为标题, 条目含「GPT 没抓到」「gate P1 新发现」「(product/arch P1)」等过程标签; 历史版本同构(十一/十/九轮……)。
- Release notes(v1.5.0)标题与条目同样全是「第十二轮自审」「(P1)/(P2)」——这是**用户可见面**。
- README.md L26 渲染文本残留「成熟度四维显式映射**(product 十一轮 P3)**」; L241「自审 F9」; HTML 注释内的自审标签(如 L12)不渲染, 可接受。
- **评估**: GPT 的分离方案正确且成本低——CHANGELOG 保留完整审计(它对维护者有价值, 不改); **Release notes 改写用户摘要**(Added/Changed/Fixed 三档, 去轮次/视角/P 级标签); README 渲染文本剔除过程标签(保留实质内容)。优先级 P2: 不影响功能, 但 Release 页是项目门面, 「自审/GPT/十二轮」对外部读者是噪声甚至减分项。

### P2-5: test_conformance_verified 单文件全跑顺序依赖红(test_report_counts)

`pytest tests/test_conformance_verified.py`(本机有 JAR)2/2 复现 1 FAILED: 只读校验报 `conf 缺 [] 多 ['volcano']`——提交的报告 conf 名单含 volcano, 而本次会话 `_verified_tools` 未把 volcano 升为 CONFORMANCE_VERIFIED。孤立跑 test_report_counts 过; 全套件(370s)中也过; 单文件全跑必红。怀疑与 6147621「fingerprint 同步(ruff --fix 后源码内容变化)」后金链证据 contract_fp 不同源 → fp 变更不继承 → volcano 不升级有关(未深挖, 交 verified 视角)。无论根因, **同一 HEAD 下"怎么跑"决定红绿灯** = 门禁口径第三种不稳定形态(targeted/full 之外又添"文件级 vs 套件级"差异), 定 P2: 需在 RELEASING 口径表中固定「以哪条命令的红绿为准」。

## 总体结论

**GPT 两条发现均核实属实**, 且 P2-3 比 GPT 所述更重(CHANGELOG 构成式本身无法重建 48, 不只"未说明")。但本轮最重要发现是 GPT 漏掉的 **P0-1**: v1.5.0 的 UTC 统一改动把 `python -c` 子进程模板改出 NameError, **tool-submit 异步链路全断并已上 PyPI**, 全量套件红——且这正是 v1.5.0 自称已修复的「改的面/跑的面」门禁盲区同构复发。建议:

1. **立即**: hotfix v1.5.1(monitor 模板自包含化 + test_jobs 进发版必跑集 + 全量绿再发)
2. **短期**: RELEASING 加「改动面→必测文件」映射 + 门禁行构成式可执行化(求和 lint)
3. **中期**: Release notes 用户化改写, README 去过程标签; 固定全量/文件级/子集三口径的权威命令
